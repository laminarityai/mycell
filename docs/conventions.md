# Conventions

The always-on rules live in `AGENTS.md` ("Invariants", "Writing code"). This file holds the detail behind them. Consistency matters more than any single rule: when this file doesn't cover a case, match the code next to it.

## Inside a feature directory

Every `app/src/features/<name>/` has the same shape. Root files are the public entry points (each optional), and subfolders are private. dependency-cruiser makes it a lint error to import a subfolder from outside its feature.

| File                             | Exports                                                                   | Imported by                                |
| -------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------ |
| `server.ts`                      | server-side functions, each taking `ctx` first                            | Server Components, other features, jobs    |
| `actions.ts`                     | Server Actions (`"use server"`)                                           | client components                          |
| `ui.tsx`                         | the feature's React components                                            | pages in `src/app/`                        |
| `jobs.ts`                        | the feature's Inngest functions                                           | the single Inngest route                   |
| `types.ts`                       | public types and Zod schemas                                              | anyone                                     |
| `connections/delegation.ts`      | `delegatedCtx`: a ctx delegated one connection (ADR-0016)                 | `reviews` only (a dependency-cruiser rule) |
| `runtime/adapters.ts`            | the pending-form adapters (ADR-0013), clear of `reviews` to avoid a cycle | `reviews`                                  |
| `connections/registered-apps.ts` | the registered apps' configuration (ADR-0018): pure, no IO                | anyone, client code included               |
| `connections/gmail.ts`           | Gmail's path, response schemas, header lookup and body text: pure, no IO  | anyone that reads Gmail                    |
| `connections/drive.ts`           | Drive's files path: pure, no IO                                           | anyone that reads Drive                    |
| `custom-actions/description.ts`  | checking a custom action and the action it makes (ADR-0018): pure, no IO  | anyone, client code included               |
| `custom-actions/api-index.ts`    | building a registered app's operation index (ADR-0018): pure, no IO       | `pnpm api-index` and tests                 |
| `orgs/form-action.ts`            | `runFormAction` and `runValueAction`: how every Server Action runs        | every `actions.ts` (a lint rule)           |

- A pure feature (no tables, no IO, no `ctx`, like `spec` and `policy`) has no `server.ts`. Its functions live in root files named for what they hold (`spec/validate.ts`, `policy/catalog.ts`, `policy/engine.ts`), which anyone may import, client code included.
- `server.ts` functions that exist before any `ctx` does (sign-in, resolving the session to `ctx`, the auth route) are the only ones that don't take it first; they live in `orgs`.
- `lib/`: implementation, including `lib/schema.ts` for the feature's tables and `lib/prompts.ts`, which loads its prompt files (see "Prompts").
- `prompts/`: the feature's text for models, as `*.prompt.yml` files.
- `tests/`: tests that import only the feature's entry files.
- `tests/isolation-cases.ts`: a case for every function `server.ts` exports, proving it stays inside the caller's org (see "Tests" below).
- **Tables are private to their feature (ADR-0005).** A feature that needs another feature's data calls that feature's `server.ts`, which also exposes any join a screen needs.
- Import from the file that owns the thing. A directory has no `index.ts` re-exporting it.

`src/app/` holds routes only (pages, layouts, route handlers), kept thin: they call features. `src/db/` holds the Drizzle client, migrations, `forOrg(ctx)`, Better Auth's generated schema (`auth-schema.ts`), and the shared test fixtures in `testing/`, and no feature tables. `src/components/ui/` holds shadcn/ui components, `src/lib/` holds shared helpers that belong to no feature (`ctx.ts`'s role checks, `inngest.ts`'s step helpers, `email-addresses.ts`), and `src/testing/` holds test fakes of external services (the fake Nango). `app/scripts/` holds developer scripts, of two kinds. One that needs nothing from `src/` but `src/env.ts` runs directly on Node's built-in TypeScript support (`pnpm nango:preflight`), so it imports with relative `.ts` paths and never through `@/`, and can run before dependencies or the database are ready. One that calls features (`pnpm credits:grant`, `pnpm capability-requests`, `pnpm api-index`) can't: feature code imports through `@/`, which Node can't resolve. It runs with `node --import tsx --import ./prompt-hooks.cjs` instead (the hooks load prompt files, see "Prompts"), and imports only features' entry files (`server.ts`, `types.ts` and the pure root files) and `src/lib/`, through `@/`, like any other caller. Their tests may import through `@/` either way; lint, typecheck, boundaries and Vitest cover them like `src/`. To start a feature, copy the shape of an existing one, but not the data access of `orgs`, which is the one feature that skips `forOrg` (see below).

## Data access and config

- **Tenant data (ADR-0003):** feature code queries through `forOrg(ctx)`, which always filters by `org_id` and sets it on inserts from `ctx`, never from caller input. A tenant table names its column `orgId` (`org_id` in SQL). Importing the raw Drizzle client outside `src/db/` is a lint error. There is no Postgres RLS. Better Auth's tables are the one exception: they key the org as `organization_id`, aren't reached through `forOrg`, and only the `orgs` feature touches them. Lint lets `src/features/orgs/lib/` import the raw client and `@/db/auth-schema`, and nothing else outside `src/db/`. The one other exception: a feature's `lib/schema.ts` may import `@/db/auth-schema` so its foreign keys can reference a member as `(org_id, user_id)`, which keeps the row in the member's org and deletes it when the member is removed.
- **Counting in the database:** count and sum in Postgres, never by loading rows to count in JavaScript. Besides `select`, `insert`, `update` and `delete`, `forOrg(ctx)` has `count(table, where)`, `sum(table, column, where)` (0 when no row matches) and `countBy(table, { name: column, … }, where)`, a count per distinct value of those columns, named as the object names them, `sumBy(table, column, { name: column, … }, where)`, a `total` per distinct value the same way (spending by purpose or by workflow is one query), and `deleteCount(table, where)`, which deletes like `delete` but returns only how many rows went, for a delete that only counts. Each is filtered to the org like `select`, on a transaction's `tx` too. An `update` that sets each row its own value is one query: a column's new value may be SQL, such as a `case` on the row's ID (memory's `relink`). `select`'s `distinctOn` is Postgres's `DISTINCT ON`: one row per distinct value of its columns, the first in `orderBy`, which must start with the same columns (`latestVersions` keeps each workflow's newest version this way). `select`'s `computed` adds values SQL computes per row beside the columns, under the names it gives them, typed by each `sql<T>` (Ask Mycel's search reads each conversation's highlighted snippet in the same query); SQL there that reaches another tenant table does so in a subquery matching that table's `org_id` to the row's.
- **Query budgets:** a list read must not grow with the number of rows it shows: batch with `inArray` or `countBy`, and pin hot reads with a query-budget test (`src/db/testing/count-queries.ts`). `countQueries(fn)` returns how many queries `fn` sent and how many rows they returned, so a budget test can check both stay the same for 1 row or many (each feature's `tests/query-budget.test.ts`). Read only the columns you use: `select`'s `columns` names them (`columns: ["id", "name"]`), still filtered to the org, and the rows come back typed to just those; a list that doesn't show a spec or an embedding doesn't load one. A job step making several calls to a connection's app opens a source client once (`sourceClient(ctx, connectionId)` from `connections`), which checks access as `proxyGet` and the rest do and binds the calls to that connection, so a backfill page reads the connection once, not once per message. A read that checks who may see what (memory's `Reading`) resolves the reader once and passes it down, rather than each check reading the org's users again.
- **Foreign keys are indexed:** every foreign key's referencing columns lead some index, so deleting a parent row, and the joins along the key, don't scan the child table. `src/db/tests/foreign-key-indexes.test.ts` reads the migrated database's catalog and fails on any foreign key without one: an index whose first columns are exactly the key's, in any order, where a tenant key's `org_id` may be left out (`(org_id, connection_id)` is served by an index led by `connection_id`). Add the index in the table's `lib/schema.ts`.
- **Transactions:** writes that must land together go through `forOrg(ctx).transaction(async (tx) => …)`. `tx` is the same org-scoped handle, bound to one database transaction: every write commits together, or none does when the function throws (the error is rethrown). Publishing a version with its tags is the first user. Keep the transaction to the writes; do reads, validation and calls to other features before it. Inside it, query only through `tx`: a read through `forOrg(ctx)` or another feature takes a second pool connection while the transaction holds one, and doesn't see its writes. When a transaction writes through another feature, that feature offers the write in two parts, like `workflows`' `checkWorkflowSave` (the reads and checks, called before) and `saveWorkflowIn(ctx, tx, checked)` (the writes, through `tx`), which accepting a proposal uses. Pin a transaction with `queriesOnOtherConnections(fn)` (`src/db/testing/transaction-queries.ts`), which lists the queries `fn` sent on another connection while a transaction was open, so a test expects none; `failWrites(table, write)` (`src/db/testing/fail-writes.ts`) makes Postgres refuse a table's inserts, updates or deletes until the test ends, to show a transaction whose last write fails leaves nothing behind.
- **Derived data cascades from its connection (invariant 3):** every table holding data ingested or derived from a connection (events, object refs, embeddings, facts, clusters, …) carries `org_id` and `connection_id`, with a composite foreign key `(org_id, connection_id)` to `connections (org_id, id)` (the `connections_org_id_id_unique` key) `ON DELETE CASCADE`. Deleting the connection row then deletes everything derived from it, whichever path deleted it (disconnect, Nango's deletion webhook, reconciliation, removing a user), and a job still writing for a deleted connection fails on the foreign key instead of leaving orphans. Tables are private to their feature, so this is the one exception: a feature's `lib/schema.ts` may import `connections`' `lib/schema.ts` (or another feature's schema) for its foreign keys, and nothing else may (dependency-cruiser's `schemas-only-from-schemas` rule). `discovery`'s events and object refs are the first. A job treats that foreign-key violation, like `NotFoundError` from `connections`, as "the connection is gone" and stops quietly: `untilGone` from `src/lib/inngest.ts`, given the feature's own foreign keys to the connection. Never delete derived rows by hand on disconnect: the cascade is the one mechanism. Data derived from several connections at once (memory's facts and objects) has no `connection_id` of its own; it hangs off rows that do (`fact_sources`), and database triggers carry the cascade on when the last such row goes.
- **JSON columns:** a table declares a JSON column with `zodJsonb(name, schema)` from `src/db/columns.ts`, never Drizzle's `json` or `jsonb` (a lint error in a feature's `lib/schema.ts`). Its type is the Zod schema's output. A write is checked before its query is sent, and every read parses what's stored, so a row stored in a shape that has since changed fails as it's read, with `InvariantError`, not deep inside a later step. The schema sits in the feature's `types.ts`, next to the type it describes. A shape with older versions still stored takes their union, and the reader upgrades it after: a spec column holds `storedSpecSchema` (specVersion 1 or 2), read through `readStoredSpec`. The SQL type stays `jsonb`, so declaring a column this way needs no migration.
- **Request context:** `ctx` is passed explicitly. There is no AsyncLocalStorage or other hidden request state. A role is checked only through `src/lib/ctx.ts`: `requireAdmin`, `requireSystem` and `requireRole(ctx, ...actors)` throw `ForbiddenError`, and `isAdmin` and `isSystem` answer for a page or a query that differs by role. A job acting as a person (a connection's owner) gets their ctx from `userCtx` in `orgs`, their role read fresh.
- **Gmail and Drive:** every feature reads Gmail's answers with `connections/gmail.ts` (its schemas, picked down to the fields a reader uses, header lookup, and `messageBody`, a message's text), so they read a message the same way, and email addresses with `emailAddressesIn` from `src/lib/email-addresses.ts`.
- **Server boundary:** reads and writes go through Server Components and Server Actions. Add tRPC, a REST layer, or a client-side data cache only when a real need appears, and record it as an ADR.
- **Server Actions** are for writes, plus the few answers a page asks for on demand (a dry run); what a page shows is read by Server Components, and a check the browser can make itself runs there (the editor's live check: the spec schema and the policy engine, with the org-setup checks left to Save). Actions run one at a time, so a read through one waits behind a save. Each one goes through `runFormAction` from `orgs/form-action.ts` (`runValueAction` when a client component calls it with a value rather than a form): it gets `ctx`, parses the form inside its `try` so a stale or tampered form gets "Reload the page" rather than a crash, turns a typed error into the `ActionResult`'s message, and only then runs `after` (`refresh`, or a redirect). `run` returns what the page gets back, if anything. React resets a form after its action even when the action failed, so a failed form's result carries the fields it sent (`values`, and `lists` for those read as lists): a field starts from `state.values?.name ?? initial`, and a Radix checkbox or switch, which resets to how it mounted, is keyed by how it starts.
- **Local database:** `pnpm db:up` starts Postgres with pgvector in Docker on port 5433 (`pnpm db:down` stops it). Copy `app/.env.example` to `app/.env`. Install the browser the e2e tests drive once with `pnpm --filter app exec playwright install chromium`. Tests never use the database in `.env`: each checkout (worktree) gets its own `mycel_test_<suffix>` for Vitest, `mycel_e2e_<suffix>` for Playwright, and an e2e port in 3100–3999, where `<suffix>` is the first 8 hex digits of the sha256 of the checkout's `app/` path (`app/checkout-isolation.ts`). Two worktrees can then run `pnpm verify` at once. `TEST_DATABASE_URL`, `E2E_DATABASE_URL` and `E2E_PORT` override them, for example when two checkouts' ports happen to collide. A removed worktree leaves its databases behind; list them with `docker compose exec postgres psql -U mycel -d mycel -c '\l mycel_*'` and drop one with `docker compose exec postgres dropdb -U mycel mycel_test_<suffix>`.
- **Migrations:** `pnpm db:generate` (`drizzle-kit generate`) writes SQL files to `src/db/migrations/`, which are committed and applied with `pnpm db:migrate` (`drizzle-kit migrate`). Every schema change goes through a reviewed migration file; `drizzle-kit push` is not used. SQL Drizzle can't express (extensions) goes in a `drizzle-kit generate --custom` migration.
- **Times:** a new time column is `timestamp(name, { withTimezone: true })`. A time without a zone reads back shifted when the database's time zone isn't UTC (the local Postgres's may not be), because `now()` and Postgres's comparisons follow the session's zone. M3's tables use it; the tables from before M3 (Better Auth's, tags, connections, connect attempts, events) still have times without a zone, so their `now()` defaults read back shifted on such a database.
- **Config:** environment variables are parsed once by a Zod schema in `src/env.ts`, and everything else imports from there. Reading `process.env` elsewhere is a lint error.
- **Errors:** a small set of typed error classes (`src/lib/errors.ts`) is thrown, and the Server Action or route boundary turns the ones a user can act on (`NotFoundError`, `ForbiddenError`, `ConflictError`, `ValidationError`, `OutOfCreditsError`, …) into messages. The rest are rethrown for the error page and never shown: `InvariantError` for a state that can't happen (an insert returning no row, an API answering against its own documentation), which is a bug, and `NangoRequestError` for a request to Nango's own API that failed or got no answer. Never throw a plain `Error` (a lint rule, outside `src/db/` and tests), so a caller can catch exactly the errors it expects by class, and no bug passes for one of them. A feature may keep its own classes for what only it and its callers handle (`SourceRequestError`, `ModelCallError`, …). Plain `throw`, no Result/Either types, no Effect.

## UI

Tailwind plus shadcn/ui, with component source copied into the repo. shadcn/ui is built on Radix primitives, so new Radix pieces arrive as shadcn components, keeping one component library.

- **Dates:** every date is shown with `<DateTime value={date} />` (`src/components/date-time.tsx`): a fixed `en-US` format in UTC, labeled "UTC", in a `<time>` element. The server renders in its own time zone and the browser in the reader's, so a date formatted anywhere else reads differently in the two (a hydration error) and gives the reader a time they can't place.
- **Apps:** wherever a workflow, a review or a pause names an app it uses, it shows its mark: `<AppMarks apps={…} />`, or `<AppMark>` and the decorative `<AppIcon>` beside the app's name (`src/components/app-mark.tsx`). Apps go by the names the UI gives them (`GOOGLE_APP_NAMES` in `src/lib/google.ts`, a registered app's name); each Google app has its own glyph in its product's colours, never Google's artwork, and any other app a generic one. Every mark is named for screen readers and on hover.
- **Controls:** a form control is a `src/components/ui` component: `Button` with a variant, `Input`, `NativeSelect`, `Textarea`, `Checkbox`, `Switch`, `Tabs`. A lint rule bans a raw `<select>`, `<textarea>` or `<button>` outside `components/ui`; a raw `<input>` stays allowed for hidden fields. What went wrong with a form shows in `<FormError message={…} />` (`src/components/form-error.tsx`), an alert.
- **Shared context:** set a context other components read (the graph's Try it, the proposal it draws) where the event happens, in the handler or the action's callback, or derive it as the page renders. Never sync it from an effect that watches props or state: the screen draws the old value first, and the order effects run in decides what wins.
- **Server code stays out of the browser:** a feature's `server.ts`, `jobs.ts` and `lib/schema.ts`, `src/db/client.ts`, `src/db/for-org.ts` and `src/env.ts` import `server-only`, so a client component that reaches one fails the build. A dependency-cruiser rule (`server-entry-files-import-server-only`) requires it of every `server.ts` and `jobs.ts`, the database client and the env module. Vitest, the prompt hooks (`prompt-hooks.cjs`) and `pnpm nango:preflight` (`--conditions=react-server`) load it as the empty module a server bundle gets.
- **The app shell:** every signed-in page renders `<AppShell current={…} title={…}>` (`src/app/_shell/app-shell.tsx`), the grouped left sidebar with the page's own item marked, rather than its own header. The sidebar's items, their groups and who sees them are in `_shell/nav-model.ts`, and what it reads on each page load (the foot's person and role, and the counts beside its items, such as Reviews waiting) in `_shell/shell-data.ts`. A new page adds its item there. Its `width` is `narrow` (a reading column, the default), `wide` (tables) or `full` (the builder chat, filling the window). The shell's frame also has a full-width banner slot above the page.
- **Error pages:** `src/app/error.tsx` (a page that threw, with a retry), `not-found.tsx` (an unknown address, or `notFound()` for something not in the org) and `global-error.tsx` (the root layout failed) keep the app's look and a way back. They never show the error itself, which may quote someone's mail (invariant 8).

## Prompts

Text written for a model lives in YAML files, never in TypeScript: system prompts, prompt templates, tool descriptions, the `.describe()` text of a schema a model fills in, the builder chat's context sections, and what its tools tell it beside their results. Each feature's prompts are in one place, and they're edited as text.

- **Files:** `features/<name>/prompts/<area>.prompt.yml`, a map of named templates with `{{variable}}` placeholders. Each is a block scalar (`|-`), so its text and line breaks are exactly what the model reads; a line that starts with spaces is quoted instead. A comment says what a template is for and what its variables hold. Like `lib/`, a feature's prompts are private to it.
- **Loading:** prompt files are parsed at build time and bundled, never read at runtime. `prompt-loader.cjs` runs in Turbopack (`turbopack.rules` in `next.config.ts`) and Vitest (a plugin in `vitest.config.mts`), and `prompt-hooks.cjs` does the same for what Node runs itself: the scripts that call features, drizzle-kit (whose config loads the feature schemas), and the end-to-end tests and their fake servers (`playwright.config.ts`). Every value is read as text (YAML's failsafe schema).
- **Rendering:** each feature's `lib/prompts.ts` loads its files with `definePrompts(file, { template: ["variable", …] })` from `src/lib/prompts.ts`, which takes only a prompt file's import (a `PromptFile`, `src/prompt-files.d.ts`). When the module loads, it throws an `InvariantError` unless the file has exactly those templates and each template's placeholders are exactly its variables, so a misspelled placeholder, a missing variable or a `{{ spaced }}` one fails at once. Each template becomes a function, called with no argument when it takes no variables and otherwise with a value for each, which the type checker holds to exactly those. It returns a `PromptText`, a branded string; `joinPrompts` joins several a line or a blank line apart, or with `, ` or `; `. A value is filled in once, so one holding `{{…}}` stays as it is.
- **What takes a PromptText:** a model call's `system` and `prompt`, a classify `question`, the builder chat's instructions and context sections, and a builder tool's description, so a string literal there is a type error. Text not written for the model goes in as a variable: a message, a spec's own question or a draft step's instructions, JSON, a list of IDs. A PromptText is still a string, so it fills a `.describe()` or a tool result's message too.
- **What stays in TypeScript:** text people see as well as the model, which reaches it as a variable: catalog action descriptions (`memory.lookup`'s too), trigger fact labels, `spec/format.ts`, the condition editor's words for a check, validation issues (`spec/validate.ts`, `custom-actions/description.ts`, `body-paths.ts`, workflows' checks, and the builder's taken spec ID), policy refusal reasons (`custom-risk.ts`) and typed errors' messages. So does a message's own framing as data: its `From:` and `Subject:` lines, the `---` between a thread's messages, a sheet's tabs.
- **Guardrails:** ESLint bans `as PromptText` and `as PromptFile` (and `<PromptText>`) outside `src/lib/prompts.ts`. It also lets only `models/lib/{call-model,chat-tools,chat-turn,classify,embed,gateway}.ts` and the models feature's tests import `generateText`, `streamText`, `generateObject`, `streamObject`, `experimental_decide`, `embed`, `embedMany`, `createGateway` or `tool` from `ai`, so every model call is metered (invariant 7): a chat (the builder's) runs its turns through `models`' `streamChatTurn` and defines its tools with `chatTool`. Type imports and the chat's `DefaultChatTransport` are allowed anywhere. `src/lib/tests/prompts.test.ts` fails on a prompt file outside a feature's `prompts/` folder (or a `tests/` folder, for a test's own), on one no code imports, and on one that doesn't match what its code declares.

## Tooling

- **TypeScript:** strict. Typed values at every feature boundary; Zod at every IO boundary.
- **ESLint:** typescript-eslint `strict-type-checked`, plus the Next.js config. It catches bugs and never formats. `max-lines` caps files at 300 lines, and `import/no-default-export` enforces named exports outside the Next.js special files.
- **Version pins:** ESLint stays on 9 and TypeScript on 6.0 until `eslint-config-next`'s plugins support ESLint 10 and typescript-eslint supports TypeScript 7.
- **Prettier:** the only formatter.
- **Tests:** Vitest. Database tests run against real Postgres with pgvector (Docker locally, a service container in CI), in a separate `mycel_test_<suffix>` database per checkout (see "Local database") that the test run creates and migrates. Each test file starts from an empty database, so files run one at a time.
- **End-to-end tests:** Playwright, Chromium only, in `app/e2e/`. They drive the production build through `next start` on the checkout's e2e port (so `pnpm verify` runs them after `pnpm build`; run `pnpm build` before a standalone `pnpm e2e`) against a separate `mycel_e2e_<suffix>` database that Playwright's global setup creates and migrates. Each test that takes the `orgs` fixture starts from an empty database seeded with `seedTwoOrgs()`, and tests run one at a time. Sign-in is Google-only, so `signInAs(user)` stores a Better Auth session and sets its signed session cookie on the browser (`e2e/sign-in-as.ts`); production code has no test login route. A test that needs a Google connection seeds its row with `seedGoogleConnection` (`src/db/testing/seed-connection.ts`), since there's no Connect UI to connect through. The app reaches Nango through `NANGO_API_URL`, which points at a fake Nango that Playwright starts on the app's port plus 2000 (`e2e/fake-nango-server.ts`): it answers with the Vitest fake's own handlers, so the proxy and the fake Gmail behave as in Vitest. A test that needs a mailbox takes the `nango` fixture (`e2e/fake-nango.ts`), seeds a connection there with its messages and drafts, passes that connection's ID to `seedGoogleConnection`, and reads the mailbox back afterwards; a request the fake can't answer fails the test. Model calls reach a fake AI Gateway that Playwright starts as a second web server on the app's port plus 1000 (`e2e/fake-ai-gateway-server.ts`, which the app reaches through `AI_GATEWAY_BASE_URL`); a test takes the `aiGateway` fixture and scripts each streamed model step with `aiGateway.reply(...)` or `aiGateway.fail(...)`, in the same shape as the Vitest fake, and fails if the app made a model call it didn't script. Keep them few and about user-visible behavior through the UI; logic belongs in Vitest.
- **External services in tests:** tests never reach the network. `src/testing/fake-nango.ts` is an in-memory Nango Cloud (connect sessions, connections and their paged listing, integrations, the proxy to each source's API with its own refusals, and signed webhooks) behind msw's fetch interception, installed for every Vitest file, so tests run the real Nango client. A request it doesn't handle fails the test: extend the fake with the endpoint, in the shape Nango documents, rather than mocking the client. Each connection in the fake has a Gmail mailbox (`src/testing/fake-gmail.ts`), a Google Drive (`src/testing/fake-drive.ts`) and spreadsheets (`src/testing/fake-sheets.ts`) that tests seed, and the scopes Google granted it (every app Mycel asks for unless a test unticks some), which Nango's connection read reports as `credentials.raw.scope`. The proxy (`src/testing/fake-nango-proxy.ts`) routes each request by its `Base-Url-Override` host (or the integration's own) and path prefix to that API's fake, which answers 403, as Google does, unless the connection holds a scope it accepts (`src/testing/fake-proxied-sources.ts`; a host it doesn't know fails the test). Every feature's tests connect through the real flow with `src/testing/connect-helpers.ts` (`connectGoogle`, and `connectOldConnection` for the one-app connections from before ADR-0014). The proxy takes POSTs, PUTs, PATCHes and DELETEs too, which an API's fake answers only when the connection holds one of its write scopes. A Microsoft 365 connection reaches the fake Microsoft Graph (`src/testing/fake-microsoft.ts`), which records every request it receives, for a test to check exactly what was sent and how often, and answers `/me`, seeded Outlook messages and replies to them. The mailbox has a history log for `history.list` that a test can expire, and serves messages and threads (`format=full`, `metadata` or `minimal`). It holds labels and drafts (`src/testing/fake-gmail-writes.ts`): `labels.list` and `create`, `messages.modify`, and `drafts.create`, `list`, `get`, `update`, `send` (which removes the draft and adds a sent message with a new ID to its thread) and `delete`, keeping each draft as a DRAFT message in its thread, parsed from the RFC 2822 it was sent so a test can read its headers and text. A test can send or delete a draft itself (`sendDraft`, `deleteDraft`), as the person would in Gmail, and reads what was sent from `writes.sent`. It logs every write, and can be told to make the next write but lose its answer (503), as a retry after a lost response sees. The Drive has files and a changes feed with page tokens that a test can expire (Drive then answers 400), and it answers only the `fields` a request names, failing the test if one asks for a file's name; the spreadsheets answer `values.get` (leaving out trailing empty rows and cells, and `values` for an empty range) and `values.append` (after the last row of the range's table, logging each append with its `valueInputOption`), 404 for a spreadsheet they don't have, 400 for a range they can't parse, and 403 for one a test denies, and can lose an append's answer the same way. The fake can answer 429s (retried as Nango's `Retries` header asks) and run a hook before each proxied request, to delete a connection under a running job. It can revoke a connection's access (the proxy then refuses as Nango does for a failed token refresh), delete a connection with no webhook (as Nango's bulk deletes do), or list nothing (an outage), for the nightly reconciliation, or stop answering altogether (`stopAnswering`), as when Nango is down. `src/testing/fake-inngest.ts` is Inngest Cloud's event API, the same way: it records the events the real Inngest client sends, and runs nothing. `src/testing/fake-ai-gateway.ts` is the Vercel AI Gateway, the same way, so model calls run the real AI SDK: each test scripts the answers it expects in order (a Jev decision with its probabilities or a refusal, a structured output, which may be off the request's schema, a text, a streamed reply for `streamText` with text and tool calls, the vectors for an embedding request, or a failure with a status and generation ID), each with the cost the gateway reports, and can list the requests it received, each marked streamed or not. Its Generation Lookup (`GET /v1/generation`, `src/testing/fake-ai-gateway-generations.ts`, shared with the e2e fake) answers 404 for a generation until a test says what it was billed (a failure's `billedUsd`, or `bill(generationId, costUsd)` later), can fail every lookup with a status (`failLookups`), and lists the generations looked up. A streamed script answers only a streamed request, as the gateway's server-sent events, one model step per `reply`: a reply with tool calls makes the AI SDK run them and ask again, so a test scripts that next step too. A model call with nothing scripted for it fails the test. `src/testing/fake-model-armor.ts` is Google Cloud Model Armor, the injection screen, with the two Google token endpoints in front of it: it passes every text unless a test flags a phrase (`flagText`), can fail or skip its filter once, and lists the texts it screened. `src/testing/fake-kms.ts` is AWS KMS, the same way, so the key store runs the real AWS SDK: it answers the operations the key store makes (making a key, encryption or HMAC, and its alias, data keys, decrypting, MACs, describing a key, scheduling its deletion and deleting its alias, each key only for its usage) with AWS's error types, binds each data key to its key and encryption context as KMS does, and lists its keys, which key each data key came from, and every plaintext data key and HMAC secret, for a test to scan tables and logs for. `src/testing/fake-google-push.ts` is Pub/Sub's authenticated push for Gmail notifications: it serves a test key set at Google's key-set URL, signs push tokens with it (which a test can spoil: another audience, sender or issuer, an unverified or expired one, or another key), and posts a notification to the route as the push subscription would. Tests never run Inngest; they call the `server.ts` function a job calls. A job passes its `step.run` to that function as a `RunStep` (`stepRunner(step)` from `src/lib/inngest.ts`), and the function runs each step straight through (`runInline`) when called without one. The interpreter's tests pass a recording step runner instead (`runtime/tests/run-helpers.ts`), which memoizes results by step ID so a second call replays finished steps, as Inngest does after a crash, and a retry policy that records its waits rather than sleeping. Its step-state recorder keeps what Inngest would store: each step's output as the client's encryption middleware sends it, and `src/testing/inngest-step-state.ts` decrypts that back with a key.
- **Isolation tests:** `seedTwoOrgs()` from `src/db/testing/two-org-fixture.ts` seeds org A and org B, each with an admin and a member and a `ctx` for each. Each feature's `tests/isolation-cases.ts` passes `defineIsolationCases(server, { … })` a case for every `server.ts` export. `src/db/tests/isolation.test.ts` runs every case and fails, as does typecheck, when an export has none. It checks `server.ts` only, so `actions.ts` and `jobs.ts` stay thin and call `server.ts`. Mark a function that touches no org data `notTenantScoped("why")`.
- **Pre-commit (Husky + lint-staged):** Prettier and ESLint `--fix` on staged files, then typecheck. Tests stay out of the hook.
- **Pre-push:** `pnpm verify`.
- **CI:** the GitHub Actions workflow runs `pnpm verify` and nothing else (after installing dependencies and Playwright's Chromium), so a laptop and CI always check the same things.

## Naming

- Files: `kebab-case.ts`.
- Exports: named. Default exports only where Next.js requires them (`page.tsx`, `layout.tsx`, …).
- DB tables: `snake_case` plural (`workflow_versions`). TypeScript types: `PascalCase` singular (`WorkflowVersion`).
- Domain names: `GLOSSARY.md` terms, using the term itself rather than its listed _Avoid_ words (`Enablement`, not `Subscription`).

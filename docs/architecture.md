# Mycel

Mycel connects to a small company's existing tools, finds repetitive work in their data, suggests AI workflows to handle it, and deploys those workflows for the team. It's built for small, non-technical companies, so **frictionless uptake** is the guiding principle: connect accounts with OAuth only, install nothing on anyone's machine, get value in the first session.

`docs/roadmap.md` holds the build order. This file covers architecture, rules, and decisions. Keep it stable, and update it when a decision changes.

## Product in one paragraph

An **admin** connects Google Workspace and describes workflows to the **builder chat**, an agent that knows the org's context. This is the primary way workflows get made (ADR-0007). Alongside it, Mycel backfills recent history and mines it for patterns (repeated questions, templated replies, cross-app handoffs). It ranks those patterns into **suggestions**, each with evidence and a measured shadow-eval result, and feeds what it learns into the builder chat's context. Admins turn a suggestion or a description into a **workflow**. Admins publish workflows to **tags**. **Members** see workflows published to their tags and can enable or disable them. They cannot create or edit them. Discovery runs again continuously.

## v1 scope

- First customer: our own company (dogfood). Mycel **reads** Gmail and Sheets/Drive and **acts** in Gmail, Sheets, Calendar, Docs and Tasks, all through one Google connection per account (ADR-0014). Slack, Outlook and the rest of Microsoft come after v1, through the same four parts (see Adding an app). Discord is not a source.
- The full loop, kept thin at every stage: builder chat (fed by discovery and suggestions) → publish to tags → member toggles → run → observability.
- No admin-level data access: no Admin SDK Reports API and no domain-wide delegation (ADR-0008).
- Workflows may act **autonomously only on read and internal-reversible actions** (e.g. labels, task changes). Anything said in someone's name waits in its app's **pending form** (a Gmail draft, a Calendar event with no guests, suggested edits in a Doc), or, where the app has none, is held by Mycel (ADR-0020), until a human approves it on the Reviews page (ADR-0019). Financial and destructive actions don't exist in v1.

## Stack

- TypeScript, one Next.js (App Router) app, deployed on **Vercel** (layout: ADR-0005)
- **Neon Postgres** with **Drizzle ORM** (pgvector for embeddings)
- **Better Auth**: Google sign-in and the organization plugin, plus a sign-in hook that checks the verified `hd` claim on the server (ADR-0002). Accounts with no Workspace domain are rejected in v1.
- **Inngest**: every background job, i.e. backfill, Gmail and Drive polling, nightly discovery, and deletion reconciliation. It is served from a Next.js route, with concurrency limits keyed by org and connection.
- **Nango Cloud**: OAuth, the proxy, actions (tool calls), webhooks. No syncs (see **Data handling**).
- **Vercel AI SDK**: every model call in code, including the builder chat agent (`streamText` with tools). No agent framework (ADR-0006).
- **Vercel AI Gateway**: every model call goes through it. Jev (TypeSafe AI, `typesafe-ai/jev`) handles classification.
- No email provider: Mycel sends no email in v1, so what waits for a person is shown only in the app (see **Waiting count and the daily check**).
- **AWS KMS**: a key per company for the key store (ADR-0024), reached with the AWS SDK.
- Zod for every schema that crosses a boundary

## Repo layout (ADR-0005; refine during scaffolding)

A pnpm workspace with two members. Features live in one directory each and own their tables, logic, Server Actions, and UI. Features import each other only through their entry files, which dependency-cruiser enforces.

    reviews/                 Reviews of what runs left waiting in pending forms; the Reviews page; the waiting count and the daily check

## Invariants

The eight invariants live in `AGENTS.md`, which is always loaded, so they have a single source of truth. The sections below explain the machinery behind them.

## Roles and permissions

- **Admin**: connects org sources, sees suggestions, uses the builder chat, creates/edits/publishes workflows (in chat or the editor), manages tags, sees observability and credits.
- **Member**: connects their own sources, sees workflows published to any of their tags, enables or disables them, and sees the runs on their own inbox. No editing.
- Tags are created by admins. A user can have many tags. A workflow is visible to a member if it shares any tag with them.
- **Credentials:** a workflow over personal data (e.g. "my inbox") runs on **each enabling member's own connection**. Shared workflows (e.g. a support@ inbox) run on an **org connection** owned by an admin. The spec field is `credentials: "member" | "org"`.
- **Who switches what on:** members enable and disable only `credentials: "member"` workflows; each switch-on is an **enablement**. An org-credential workflow runs once per trigger and has a single on/off switch that only admins control. For those workflows, tags decide who can _see_ the workflow and its reviews (shared reviews), not who runs it.
- **Membership (ADR-0002):** one org per user, Google sign-in only. The first user from a Workspace domain creates the org and becomes admin. Later users from that domain auto-join as members. Admins can promote members.
- **Removing a user** deletes their member connections and everything derived from them (the invariant 3 cascade), along with their enablements. An org always keeps at least one admin, so the last admin can't be removed or demoted.
- **Org connections outlive their owner.** If the admin who made an org connection is removed, the connection keeps working and admins see a "connected by a removed user" warning. Only deleting the connection itself triggers the cascade delete.

## Data handling (option B: derived data plus pointers)

- Raw email and file content is processed in memory and **not persisted**. We keep derived data: cleaned features, entities, cluster assignments, templates (with slots), embeddings, extracted memories, plus `source_ref` pointers (Gmail message/thread IDs, Drive file IDs).
- When raw content is needed later (evidence view, shadow eval), it is **re-fetched through the Nango proxy**. Handle rate limits, and handle deleted sources (evidence goes stale and drops out).
- Embeddings and memory count as sensitive. They are encrypted at rest by the database (Neon: AES-256, keys in a KMS), with a key per company only for what is never searched (ADR-0024); visible through their sources' access lists, and deleted with their source or connection, or after 24 months without a supporting source (ADR-0024). Backups and Inngest's run state age out within 30 days.
- **The key store (`features/key-store`)** protects what Mycel holds but never searches with keys per org: it encrypts held sends (ADR-0020) and hashes the do-not-learn list (ADR-0024). `encryptForOrg(ctx, text)` and `decryptForOrg(ctx, encrypted)` use envelope encryption: AWS KMS holds one symmetric key per org, made on first use under the alias `alias/<KMS_ALIAS_PREFIX>/org/<org ID>`, and each encryption gets a fresh AES-256-GCM data key from it, bound to the org by KMS's encryption context and by the org ID as authenticated data. The stored value carries the data key only in KMS's encrypted form, so no key material reaches a table or a log. Another org's value, or one whose key is gone, is `NotFoundError`. `destroyOrgKey(ctx)` (the org's system ctx only, so no admin can make its waiting held sends unreadable), for an org leaving Mycel, makes the keys unusable at once and deleted after KMS's 7-day wait, so everything encrypted for the org is unreadable. Nothing offboards an org yet, so nothing calls it: wiring it into org deletion is a follow-up. `hashForOrg(ctx, text)` gives a keyed hash for the do-not-learn list: AWS KMS computes HMAC-SHA-256 under a second key per org (`HMAC_256`, `GENERATE_VERIFY_MAC`, alias `alias/<KMS_ALIAS_PREFIX>/org/<org ID>/hash`, made on first use), returned base64url, so the same text always hashes the same in one org and no other, and the key never leaves KMS; `destroyOrgKey` destroys this key too. Config is env only (`KMS_*` in `app/.env.example`; `KMS_REGION` is required at boot unless `INNGEST_DEV=1`, like the Inngest keys, so production never finds it missing at a held send); tests reach a fake KMS (`src/testing/fake-kms.ts`).
- Every read of memory is logged (who, when, which object, never content) and kept for 365 days; admins see their company's log, members the reads of facts from their own sources, and our staff read memory only with an admin's consent for one case, logged in the same place (ADR-0024).
- **Never use Nango syncs.** All content, including the 90-day backfill, goes through the Nango proxy, which doesn't store response bodies. Syncs would keep copies at Nango for up to 60 days that we can't purge.
- Google: dogfood with an **Internal** OAuth app (no verification needed). Before the first external customer, complete Google OAuth verification and the restricted-scope security assessment.

## Scopes and visibility

- Data from a member's personal connection is `owner_scope: member`. Data from org connections is `org`.
- **Memory (ADR-0023):** each source record keeps its access list as Mycel saw it (a Drive file's sharing list; for an email, the mailboxes holding it and, on one the company's own mailbox sent, everyone on it, never the addresses an outside sender wrote), checked whenever someone asks and re-read on the app's change events and nightly. A fact is visible to anyone who can see one of its sources. Company-wide means the app's own sharing, a group list an admin marked company-wide, or an org connection; for other groups only people whose own connected mailbox holds the item count.
- Org-visible surfaces (suggestions, builder chat) may show **aggregates** from member scope: counts, cluster labels and slot-redacted templates.
- **Evidence visibility (ADR-0001):** admins never see raw evidence from a member's mailbox unless that member shares specific examples. Evidence from org connections is shown raw to admins.
- The agent and the MCP server see exactly what the person using them can see.

## Discovery pipeline (`features/discovery`)

1. **Ingest**: backfill 90 days on connect, then incremental updates by polling each app through the Nango proxy, starting from that app's stored cursor: Gmail's `history.list` from the last history ID, Drive's `changes.list` from the last page token. A poll starts in one of two ways (ADR-0026). An app with a watch (Gmail's, through Pub/Sub, and Drive's, through a `changes.watch` channel, where each app's push is configured) notifies Mycel when its account changes, and the notification starts that connection's poll within seconds. And a cron, the sweep, polls each app with no live watch at each run and each watched one every 15 minutes, catching whatever a notification missed; it runs every 5 minutes where both apps have push, and every minute elsewhere. Nothing downstream of the poll changes.
   - **One Google connection per account (ADR-0014).** Each person, and each org account such as support@, connects Google once, through Nango's one `google` integration, which asks for `gmail.modify`, `drive.readonly`, `spreadsheets`, `calendar.events`, `documents` and `tasks`. Google lets people untick apps on the consent screen, so `connections` reads the granted scopes from Nango (`GET /connections/{id}`, `credentials.raw.scope`) when the connection is recorded and on every reconnect, and stores them on the connection (`granted_scopes`); its apps are those whose scope was granted. The account's address is read from Gmail, or from Drive if Gmail wasn't allowed; an account that allowed neither is refused. A missing app shows "reconnect to allow …": a reconnect works on any connection, not only one needing reauth, and its `override` webhook re-reads the scopes (after checking it reached the same account), starting an ingested app it newly allows, or one whose backfill failed (`connections/apps.granted`, which also starts the backfill job), and dropping one it no longer allows. Every proxied call sets its API host with Nango's `Base-Url-Override`, chosen in `connections` from the path's prefix (`/gmail/` on `gmail.googleapis.com`, `/drive/` on `www.googleapis.com`, `/v4/spreadsheets` on `sheets.googleapis.com`, `/tasks/` on `tasks.googleapis.com`), so callers pass Google's own paths.
   - **Before ADR-0014**, Gmail and Drive were separate connections, on Nango's `google-mail` and `google-drive` integrations. Those that remain (`source` `gmail` or `drive`) keep ingesting through their own integration, and the connections page asks to switch: connecting Google for the same account and kind deletes them and everything they ingested (invariant 3), and the new connection backfills again.
   - Each ingested app is one connector (start cursor, backfill page over a window, poll from a cursor); a connection runs the connectors of the apps it may use, each with its own cursor, and nothing outside a connector knows its app's API. The backfill, poll and recovery code is shared, and every event keeps its connection's `connection_id` and records its app as `source`.
   - **Gmail** (on `gmail.googleapis.com`): the cursor is the history ID; the backfill lists messages with `after:` and fetches each in full; polling reads `history.list` (`messageAdded`, `messageDeleted` and `labelAdded`), fetching the messages added and reporting as removed those deleted for good or given the `TRASH` label (deleting in Gmail moves a message to the trash for 30 days). Both skip spam, trash and drafts (each draft save is a new message ID).
   - **Drive** (on `www.googleapis.com`): the cursor is the changes feed's page token (`changes.getStartPageToken`); the backfill is `files.list` with `corpora=user`, `modifiedTime > <since> and trashed = false` and no shared drives; polling follows `changes.list` page by page and stores the last page's `newStartPageToken`; a change Drive marks `removed` (the file deleted, or no longer shared with the account) or whose file is trashed reports that file removed. Every request names its `fields`, and none asks for a file's name. Each file version is one event: `file.created` when its created and modified times are equal, else `file.modified`, with the modified time, the modifying user, the owners and the MIME type. Its `source_ref` is `<file ID>@<modified time>`, so the same version from a backfill and a poll is stored once. Object refs are the file's `drive_file` ID and the modifying user's and owners' `email`s, which is how an email linking a file meets that file's changes. `discovery` reaches a source only through `connections`' `proxyGet(ctx, connectionId, …)`, and `connections` never imports `discovery`.
   - Recording a connection sends `connections/connection.recorded`, which starts the backfill job. It backfills each app still `backfilling` on the connection in turn: that app's cursor is read first, then one page per Inngest step, normalized in memory. Backfill and poll share a concurrency of one per connection and a per-org limit.
   - **The sweep (ADR-0026).** The `poll-connections` cron lists the orgs and, as each org's system ctx (ADR-0009), sends one `discovery/connection.poll-due` event per connection that's due: one with no reconnect pending and an `active` app that's due. An app with no live watch (none started, or its `watch_expires_at` in the past) is due at every run. An app with a live watch is due once its `last_polled_at` is 15 minutes old (`SWEEP_WATCHED_EVERY_MS` in `discovery/lib/poll-all.ts`), or when it hasn't been polled since its backfill. A push's poll moves `last_polled_at` too, so a watched mailbox that notifies is swept only after 15 quiet minutes. The cron runs every 5 minutes where every ingested app has push configured (Gmail's three variables and `DRIVE_PUSH_SECRET`), so an app whose watch failed or lapsed waits at most 5 minutes; anywhere else (local dev, the tests' own choice, an environment with only Gmail push) it runs every minute, so an app without a watch is polled every minute, as before push (`sweepSchedule`, read when the function is registered). The sweep reads each org's connections and their apps' states in the same queries however many connections it has.
   - Polling: whether a push or the sweep started it, the poll job asks each `active` app's connector for what's new since its cursor, normalizes it exactly as the backfill does, and stores the app's next cursor. Events are unique per connection on `source_ref`, so overlaps and re-runs store nothing twice.
   - **Gmail push, the receiving end (ADR-0026).** With `GMAIL_PUSH_TOPIC`, `GOOGLE_PUSH_AUDIENCE` and `GOOGLE_PUSH_SERVICE_ACCOUNT` set (all three or none, checked in `env.ts`), Pub/Sub's push subscription posts each Gmail notification to `POST /api/google/gmail-push`, which calls `discovery`'s `handleGmailPush`. Without them it answers 404. It answers 401 unless the `Authorization: Bearer` token is signed by a key in Google's published key set, issued by Google, for that audience, with the push service account's email, verified. Every verified push is 204, so Pub/Sub doesn't deliver it again: the body is parsed with Zod and its base64 data to `{emailAddress, historyId}` (a malformed one is logged without the address, and dropped); `orgs`' `findOrgIdForAddress` finds the org, from the user whose sign-in address it is, else the org whose Workspace domain is its domain, reading only identity tables; and `connections`' `gmailPushConnectionIds`, as that org's system ctx, lists its connections on that address with an `active` Gmail and no reconnect pending. Each gets one `discovery/connection.poll-due`. The poll job debounces per connection (5 seconds after the last event, at most 30), keeping its concurrency. The history ID is never used: the poll reads from its stored cursor.
   - **Drive push, the receiving end (ADR-0026).** With `DRIVE_PUSH_SECRET` set (at least 32 characters), each Drive channel posts to `POST /api/google/drive-push` (`BETTER_AUTH_URL` plus that path), which calls `discovery`'s `handleDrivePush`. Without it the route answers 404. Drive's notification is empty: the route reads only the `X-Goog-Channel-Token` and `X-Goog-Resource-State` headers. The token is `<orgId>.<connectionId>.<HMAC-SHA256 of the two under DRIVE_PUSH_SECRET, base64url>`, so the route finds the connection without a lookup; it answers 401 unless the HMAC matches, compared in constant time, which also refuses another org's token pointed at this org's connection. Every verified request is 204: a `sync` message (sent when a channel opens) starts nothing; otherwise, as the token's org's system ctx, the connection gets one `discovery/connection.poll-due` if it still exists, its Drive is `active` and it needs no reconnect. Google no longer requires the receiving domain to be verified (API Console Help, "Verifying domains for push notifications"); the address needs HTTPS with a valid certificate, which `*.vercel.app` has.
   - **Watches (ADR-0026).** A connector may watch: its `watch` says whether the environment has the app's push settings, `start(client, { orgId, connectionId, cursor })` starts or renews the app's watch on the account and returns when it runs out (and the channel it opened, if it's a channel), and, for a channel, `stop(client, channel)` stops one. Gmail's is `POST /gmail/v1/users/me/watch` with the topic from `GMAIL_PUSH_TOPIC`, `labelFilterBehavior: "exclude"` and `labelIds: ["DRAFT", "SPAM", "TRASH"]`, so a draft save doesn't notify; the answer's `expiration` (milliseconds since the epoch) is stored as the app's `watch_expires_at` on its ingest state, which cascades with the connection. Asking again renews Gmail's watch in place. Drive's is a channel: `POST /drive/v3/changes/watch?pageToken=<Drive's cursor>` with a new UUID as `id`, `type: "web_hook"`, the route's address, the token above (about 120 characters, within Drive's 256) and an `expiration` 7 days out, Drive's maximum for the changes feed; the channel's ID, the `resourceId` Drive answers and its expiry are stored as `watch_channel_id`, `watch_resource_id` and `watch_expires_at`. When a backfill finishes an app and it turns `active`, a step `<app>-watch` starts its watch, if the connector has one and the app's push is configured. The `renew-watches` cron (04:00 UTC, after the reconciliation) lists the orgs and, one step per org as its system ctx, renews every `active` app that can watch on each connection with no reconnect pending, which also restarts a watch that lapsed, failed or never started. Renewing Drive opens the new channel first, records it, and then stops the old one (`POST /drive/v3/channels/stop` with its ID and resource ID) while the connection's token still works; a failed stop is logged, and the old channel runs out on its own, its notifications costing at most an extra poll. A failed watch call is logged and leaves the app to polling, with the watch stored before (and its channel, unstopped) kept as it was; one connection's failure doesn't stop the rest. A watch is never stopped on disconnect: a deleted connection's runs out on its own within 7 days, its notifications finding no connection. Without an app's push settings, no watch call is made for it.
   - An expired cursor (Gmail answers 404 for a history ID; Drive answers 400 blaming `pageToken`, or 404 / 410) recovers inside the same poll run, which already holds the connection's concurrency slot: read a fresh cursor, backfill the app page by page from a day before its latest stored event, then store the cursor.
   - Each ingested app's state lives in `connections`' `ingest_states` (one row per app the connection may use, cascading from it): `backfilling` with a count of stored messages or file versions, then `active` or `failed`, the cursor, when it last polled, when its watch runs out, and its watch's channel, if it's one. The connections page shows one row per account, with its apps and the furthest-behind app's status. Nango's `auth` / `refresh` webhook with `success: false` sets the connection's `needs_reauth`, which polling skips; reconnecting (a Nango reconnect session, then its `override` webhook, if it reached the same account) or a later successful refresh clears it. `needs_reauth` lives on the connection, apart from its apps' states, so a backfill finishing (or failing) meanwhile doesn't clear it, and the page shows it ahead of any app's status. A reconnect also starts again every app whose backfill failed: the `failed` state is replaced by a new `backfilling` one and announced with `connections/apps.granted`, like a newly allowed app, so the backfill job backfills its 90 days again (events already stored are kept once). If that announcement can't be sent, the started states go to `failed`, which the page shows with a "Reconnect to retry" button, and Nango's redelivery of the webhook starts them again.
   - Every Gmail message a backfill, poll or recovery newly stores (drafts excepted), and every Drive file version, is also sent on as `discovery/item.stored` (`src/lib/events.ts`; connection, app, `source_ref` and time), which memory learns from. Memory, not discovery, decides which files it reads. A poll also sends `discovery/item.removed` (connection, app, and the Gmail message ID or Drive file ID) for each item it found removed, and `discovery/item.changed` (connection and the current `source_ref`) for each Drive file it saw change with no new version: Drive's feed doesn't say what changed, so it may be the file's sharing. Their event IDs name the cursor the poll read from, so a retried send starts nothing new while a later change to the same file does. A backfill or a recovery after an expired cursor lists what's there and reports neither; memory's nightly re-read covers what they miss. `discovery` never imports `memory` (a dependency-cruiser rule).
   - **Ingest persists no text.** Events and object refs hold no subject, body, snippet or file name; the decoded body exists only while its object refs are extracted, and Drive is never asked for names or content.
2. **Normalize** into one event schema: `event_id, source, type, timestamp, actor, counterparty, direction, thread_id, text (cleaned, in memory only), object_refs, attachments_meta`. Strip quoted replies, signatures, and disclaimers.
3. **Object refs** (ADR-0008): deterministic links from structured fields (addresses, attendees, file IDs) and regex for IDs, merged on exact keys. Memory (ADR-0022) builds objects on top of them, adding fuzzy and similarity candidates that a model confirms.
4. **Mine**: embed and cluster into intent clusters. For v1, clustering links events whose pgvector similarity is above a threshold and takes each connected group as a cluster. It sits behind one `clusterEvents` function so the method can change (ADR-0004). Have an LLM label only a few representatives per cluster. Detect templates (near-duplicate outbound messages with their slots), request→response pairs, periodic tasks, and chasing/follow-up patterns.
5. **Rank**: value = frequency × est. minutes × people. Feasibility = trigger type, variance, blast radius, context availability, write-API availability. Map to a starting rung.
6. **Shadow eval**: replay the candidate on held-out past cases (re-fetched) and compare with what the human actually did, using a `judge` model plus edit distance. Show the result on the suggestion.

- Discovery runs **nightly**. A dismissed suggestion comes back only if its frequency reaches **≥2×** the level when it was dismissed.
- Discovery uses credits. Show a cost estimate before the initial scan.

## Solution ladder (rungs)

0 rule/template (no AI) · 1 knowledge answer · 2 skill (human-invoked) · 3 triggered draft for approval · 4 autonomous with guardrails · 5 multi-step across people.

v1 supports rungs **0, 3, and 4 (reversible-internal actions only)**. Earned autonomy, meaning offers to promote a workflow based on how often drafts are sent unedited, comes after v1, but specs carry the `autonomy` block already.

## Workflow spec (`features/spec`)

Specs are JSON, validated by zod, and run by our own interpreter in `features/runtime`: each spec step executes as one Inngest step, so finished steps are never re-run and each step retries on its own (ADR-0006). Primitives: `trigger`, `classify`, `branch`, `extract`, `tool` (Nango action), `draft`, `approval`, `escalate`.

```json
{
  "specVersion": 2,
  "id": "pricing-inquiry-replies",
  "visibility": { "tags": ["sales"] },
  "credentials": "member",
  "budget": { "monthlyCredits": 500 },
  "trigger": { "type": "gmail.message_received" },
  "steps": [
    {
      "id": "classify",
      "type": "classify",
      "role": "classify",
      "question": "Is this a pricing inquiry?",
      "labels": ["yes", "no"]
    },
    {
      "id": "gate",
      "type": "branch",
      "mode": "first",
      "paths": [
        {
          "id": "gate-yes",
          "name": "Pricing",
          "condition": {
            "combine": "all",
            "checks": [{ "classify": "classify", "is": "yes", "minP": 0.85 }]
          },
          "steps": [
            {
              "id": "prices",
              "type": "tool",
              "action": "google-sheet.read-range",
              "input": { "spreadsheetId": "sheet-1", "range": "Prices!A1:C50" }
            },
            {
              "id": "draft",
              "type": "draft",
              "role": "smart",
              "instructions": "Reply with our current prices.",
              "context": ["trigger.message", "prices"],
              "output": "google-mail.create-draft"
            },
            { "id": "approve", "type": "approval", "channel": "gmail_drafts" }
          ]
        }
      ],
      "otherwise": { "id": "gate-otherwise", "steps": [] }
    }
  ],
  "autonomy": { "rung": 3 }
}
```

**Branches and paths** (ADR-0015): a `branch` holds its paths nested inside it and is the last step of its list. Each path has an ID, a name, a condition and its own steps; the `otherwise` path runs when no path's condition holds, and with no steps the run stops there (status `skipped`). A condition is `all` or `any` of its checks: a classify answer (`{ "classify": "<step>", "is": "<label>", "minP": 0.85 }`) or a value (`{ "subject": { "from": "<step>.<field>" | "trigger.<fact>" }, "op": …, "value"? }`, the operator typed by the value: text, number, yes/no, or empty). `mode` is `first` (the first path that holds, left to right) or `every`. Step and path IDs share one namespace. A branch has 1 to 10 paths besides otherwise, each condition at least one check, and branches nest at most 3 deep (checked on save, so a converted v1 spec deeper than that still runs). A value check tests a field something declares, its operator fitting the declared type: a fact the trigger declares (`spec/triggers.ts`; Gmail's are `sender`, `senderDomain`, `subject`, `hasAttachment`, `isReply`), an extract step's field, or a field a catalog action declares in `conditionFields` (`read-thread`'s `messageCount`, `read-range`'s `rowCount`, `memory.lookup`'s `factCount`; a catalog test checks each against the action's output schema). `validateSpec` checks the first two (`spec/conditions.ts`: `subjectType`, `operatorsFor`, `describeCheck`), and `applyPolicy` the third, since only `policy` knows the catalog; `testableFields(spec, branchId, actions)` in `policy/condition-fields.ts` lists them all for a branch. The branch step reads the message's facts through the Nango proxy, only when a check tests one, and holds them in memory. Text checks ignore case and surrounding spaces; a missing or blank value is empty and fails every other check. The branch step (`runtime/lib/conditions.ts`) checks paths left to right and, under first match, stops at the first that holds; under every match it takes every path that holds, and the walker (`runtime/lib/walk.ts`) runs them one after another, left to right. The otherwise path runs only when no path holds. Each path sees the outputs as of the branch plus its own, never a sibling's. A path ends when a step fails, escalates or reaches an empty otherwise path, and the others go on; the run ends `failed` when every path that ran failed (a failure above every branch is one such path), `partly_failed` when only some did, and otherwise `escalated` if any path escalated, `succeeded` if any finished, else `skipped`. A cancelled run and running out of credits stop every path. `partly_failed` counts as a failure wherever failures are counted, and a run's record names the path each step is on (`RunStepRecord.path`, "Pricing › Otherwise"), so the runs table says which path a run failed on. Its record keeps the paths taken and each checked path's ID and pass or fail, never the values tested; an approval records every draft above it on its own path, those an earlier approval recorded too, as a v1 approval recorded every draft before it.

**Triggers** (`spec/triggers.ts`, M11): a spec has one trigger, which says what each run is about. `{ "type": "gmail.message_received", "labelIds": ["INBOX"] }` starts a run on a new Gmail message with one of the labels; `{ "type": "calendar.invite_received" }` on a new invite on the connection's calendar. Each trigger declares the app a connection must be granted (Gmail, or Calendar), its facts (an invite's are `organizer`, `organizerDomain` and `title`), the fields a tool input may read (`trigger.messageId` and `trigger.threadId`, or `trigger.eventId`, which `google-calendar.read-event` takes) and what a draft may read (`trigger.message`, `trigger.thread`, or nothing). `validateSpec` refuses a reference to anything else, and refuses a `draft` or `escalate` step under the Calendar trigger: both act on a Gmail message, its thread and its draft, which a run on an invite doesn't have. Classify and extract steps read the trigger's item (`runtime/lib/trigger-facts.ts`: the message, or the invite's title, organizer, guests, times, place and description, read live from Calendar), and so does a branch that tests one of its facts; none of it is stored. Save, switch-on, enabling, Try it and the policy engine's "what a new version gains" all take the trigger's app where they took Gmail, so a version that moves to the Calendar trigger gains Calendar and pauses members' enablements. The editor picks the trigger in its settings, the graph's first box says what starts a run, and the builder chat's instructions have a Triggers section built from the same declarations.

**Specs from before** (`specVersion: 1`, a gate with `when` and `else`) are converted when read, never migrated: `readStoredSpec` (`spec/stored.ts`) runs `upgradeSpec` (`spec/upgrade.ts`) at every place a stored spec is read, so code past the read sees v2 only, and saving writes v2. A gate becomes a first-match branch with the gate's ID and one path holding every step after it; `else: "stop"` becomes an empty otherwise path, and `else: "escalate"` one escalate step with fixed words. Every v1 step ID is kept, so published v1 versions run with the same step IDs, and a run memoized part-way through one resumes on the matching path (the walker reads a memoized `{ passed }`). `validateSpec` accepts v1 input and returns it upgraded, naming each issue where the input wrote it (`issuesAsWritten`). The graph editor reads a v1 draft's steps upgraded, and its first edit writes them as v2.

**Shape and structure** (`validateSpec` in `features/spec`, pure): the schema refuses unknown step types and misspelled fields; step and path IDs are unique; a branch is the last step of its list; a classify check names a `classify` step above the branch and one of its labels, and a value check a field of a step above the branch on its own path; `tool` inputs are literals, references `{ "from": "<step>.<field>" }` and `{ "from": "trigger.<field>" }`, or lists and records of them with a reference anywhere inside (an app's own request objects, such as the Docs batchUpdate requests `google-docs.suggest-edits` takes; a record whose key is `from` is always a reference, and `spec/input-values.ts` walks them), and a `draft`'s `context` names steps above it on its own path, `trigger.message` or `trigger.thread`. `org_memory` as context is refused until memory exists (M9). Two steps that can run together (their nearest shared branch is every match, and they sit on different paths of it, neither the otherwise path) can't both draft a reply or both escalate, so nobody gets two reviews for one email; two drafts on one path are fine. A `risk` field anywhere is accepted and ignored. Every issue comes back in one list, each with the path of its field.

**Validation before save:**

- every `action` exists in the catalog and the tenant has the connection
- every `role` resolves to a model
- tags exist
- `credentials` is allowed
- the policy engine computes the max risk level and inserts any approvals the spec is missing
- every step type and catalog action has a registered executor in `features/runtime`

**Switching on and triggering:**

- A member-credential workflow is switched on by an **enablement** (`enablements`, unique on workflow and user) on the enabling user's own member connection; an org-credential workflow by its one switch, recorded on `workflows` as the org connection it runs on and since when. Either follows the latest version, and switching on checks that version against the chosen connection alone (the trigger's app allowed, Gmail or Calendar, and every action's scope granted). Switching off deletes the enablement or clears the switch; deleting the connection or removing the user does too.
- Members enable from the Workflows page (`enable(ctx, workflowId)`): the workflow must be visible to them and member-credential (an org switch is admin-only, `ForbiddenError` for anyone else). It finds the caller's own Google connection and checks it against the latest version **by app** (ADR-0014: the trigger's app, Gmail or Calendar, plus each catalog action's app) and by each action's scopes. No connection returns `{ needs: "connect", apps, scopes }`, one short of something returns `{ needs: "reconnect", connectionId, apps, scopes }`, and otherwise the enablement is upserted `on`. The page sends the member through Nango's Connect UI, whose `onDone` (the return target) calls `enable` again, retrying briefly while Nango's webhook records the connection and its grants.
- An enablement is `on` or `paused` (always with `paused_reason`, plus `paused_change` for what a new version needs). A connection in `needs_reauth` is a connection state, not a pause: its enablements stay as they are, the page shows "reconnect Google", and fan-out skips the connection until it's reconnected.
- For the Gmail trigger, only polled mail triggers: when a poll (or an expired-cursor recovery) newly inserts an inbound Gmail message that isn't a draft, `discovery` sends `discovery/gmail.message_received` (`src/lib/events.ts`, shared so `runtime` needn't import `discovery`). The backfill sends nothing, and neither does a re-read.
- `runtime`'s fan-out, as the system ctx, starts one run per startable switch on that connection (`listStartable`: every org switch, and each enablement that is `on` and whose user can see the workflow's latest version at that moment, checked from their tags rather than trusting a cleanup to have run; none while a pause holds, such as the company being out of credits, see "Pausing") whose switch-on came at or before the message's `occurredAt` and and whose trigger is a new Gmail message with one of the labels the message carries (default `INBOX`). A connection in `needs_reauth` starts nothing. Each run is unique on (enablement or org workflow, `source_ref`) through `runs.trigger_key`, and its run event's ID is the run's, so a resent trigger starts nothing twice.
- **The Calendar trigger** (M11, `runtime/lib/calendar-poll.ts`): a cron every minute (`poll-calendars`) lists, as each org's system ctx, every connection granted Calendar, not in `needs_reauth`, with a startable switch whose trigger is a new invite, or in an org where memory has started (`calendarsDue`; memory shares the poll, ADR-0029), and sends `runtime/calendar.poll-due` for each; the poll job (one at a time per connection) lists the connection's primary calendar with `events.list` through the Nango proxy (`www.googleapis.com/calendar/v3/...`). It keeps only Calendar's sync token, in `runtime`'s `trigger_cursors` (one row per connection and trigger, cascading from the connection, so every deletion path removes it), and never stores an event: Calendar isn't a discovery source (ADR-0008). The token is shared: the same poll tells memory what changed (Memory, "Learning from Calendar invites"). The first poll after a switch-on has no token, lists the whole calendar page by page (a full sync) to get one, and starts nothing; a `410` from Google (the token expired) does the same, so invites made in between are missed, never started late. Otherwise it lists what changed since the token, page by page (one Inngest step each), stores the last page's `nextSyncToken`, and in the step after sends `calendar/invite.received` (pointers only: the event ID as `sourceRef` and its `created` time as `occurredAt`) for each listed event whose own guest entry (`self: true`) is `needsAction`, made at or after the earliest switch-on among the connection's Calendar-triggered switches (none when the poll runs for memory alone). It skips a cancelled event (an incremental listing returns deletions as `cancelled`), one Gmail added (`eventType: fromGmail`), one with `attendeesOmitted` (it can't tell which guest is the person), and one the person organised. Every list request, the first included, asks the same parameters (`maxResults` and `fields`, which names no title or description), since Google refuses a sync token with others (`400`), and none adds `timeMin`, `timeMax`, `updatedMin`, `q` or `orderBy`, which Google refuses with a sync token. An invite listed again because its organizer changed it is announced again under the same event ID (`calendar-invite-<connection>-<event>`), and its runs' trigger keys make it start nothing twice. The fan-out (`startInviteRuns`) starts one run per startable switch on the connection whose trigger is a new invite and whose switch-on came at or before the invite was made. Known limit: when a person's "Add invitations to my calendar" setting is "only if the sender is known" or "when I respond", an invite from an unknown sender reaches only Gmail, so it starts nothing; the dogfood check (#72) measures how often.
- **Runs from Ask Mycel (M9)**: a person runs one of their own switched-on workflows on a message in their own mail (one the trigger missed, or that came before they switched it on). `runtime`'s `startRunFromAgent(ctx, workflowId, sourceRef)` (`runtime/lib/agent-runs.ts`) checks first, as `checkRunFromAgent` does without starting anything: `workflows`' `startableEnablement(ctx, workflowId)` (the workflow is one they see, member-credential and switched on by their own enablement, and then `startableVersion` on that enablement's connection, as a retry checks it: published, not archived, still shared with them, and no pause holds on it, failing, budget reached and out of credits included, by the same `pausesOf` and `readHolds` as fan-out), their connection isn't `needs_reauth`, Gmail has the message in that connection's mailbox (`format=minimal`; 404, or 400 for an ID that isn't one, is "not in your mail"), and no run of the workflow on that message is running, however it started. Each refusal is a typed error in plain words. It then records a run of the latest version on that connection with `started_by = agent` and the enablement's ID, and requests it like any other. A partial unique index (`runs_agent_running_unique`, on org, workflow, connection and `source_ref` where `started_by = 'agent'` and `status = 'running'`) lets one agent run of a workflow on a message run at a time, so clicks that arrive together start one run. `agentRunDetails(ctx, offers)` gives the chat each offered run's message (sender, subject and date, fetched through the proxy for display only, on the caller's own connections) and its run's status, in the same queries for one as for many.
- Before each step, a triggered run, or a run from Ask Mycel, checks the enablement or org switch it runs under still exists for its connection (`listSwitchedOn`, which ignores pauses and visibility, so a run under way finishes on the version it started on); if not, it ends `cancelled` after the step it was on. An agent run goes on under its person's enablement, never an org switch; a manual run or a retry checks only that its connection is still there.
- **Losing sight of a workflow (M5)** deletes the enablement rather than pausing it: it isn't one of the pause causes, and the member couldn't see the workflow to resume it. `removeInvisibleEnablements(ctx, { userId?, workflowId? })` (`workflows/lib/lost-visibility.ts`) deletes each enablement in scope whose user can't see the workflow's latest version. `publishWorkflow` calls it for the workflow inside the version's transaction (`removeInvisibleIn`, with the org's users and their tags read before the transaction begins), so publishing to fewer tags takes effect at once. `tags` sends `tags/assignment.removed` (from `unassignTag`) and `tags/tag.deleted` (from `deleteTag`, whose cascade has already removed the tag from every version), and `workflows/jobs.ts` calls it for that user, or for the org, as the system ctx. Fan-out's own visibility check covers the time before a job runs.
- **Renaming a tag** changes nobody's visibility, since versions hold tag IDs (`workflow_version_tags`). But working specs name their tags, and publishing resolves names, so `renameTag` sends `tags/tag.renamed` and `workflows/jobs.ts` calls `followTagRename(ctx, { tagId, from })` (`workflows/lib/tag-rename.ts`) as the system ctx: every working spec naming the old name gets the tag's current name, as a save (its revision moves on), so the next publish, from the dialog or the builder, finds the tag. It reads the current name rather than the event's, so renames followed out of order end on the right one.
- **Archiving** (admin only, `archiveWorkflow`/`restoreWorkflow`) sets `workflows.archived_at`. Members stop seeing the workflow, and `listStartable` skips its enablements and its org switch, which are kept as they are, so restoring brings everyone back on the same latest version without publishing anything. Like a pause, it stops new runs only: `listSwitchedOn` ignores it, so a run under way finishes.
- Reviews already waiting outlive a removed enablement and an archive: the draft is still in the member's mailbox, so the review stays until it ends. Deleting the connection deletes them (the cascade).
- Storing and sending are separate steps. The poll step (or a recovery's page step) hands on the inbound, non-draft Gmail messages its insert newly created, as IDs, times and labels only; the step after it (`gmail-poll-announce`, or `<prefix>page-<n>-announce`) sends them. A failed send is retried with the memoized messages, so none is lost, and only newly inserted rows are ever sent.

**Custom actions** (ADR-0018): when no catalog action fits, the builder describes one call to a registered app (address, where each input goes, which results come back) as a custom action of the admin's org. Mycel's runtime makes the call through Nango; a fixed rule sets its risk (a read is `read`, any other call at least `external_send`; deletes, refunds, voids and writes in accounting or payments apps are refused). When one call can't do the job, the builder drafts code and sends it to our team as a **capability request**; it reaches workflows only once we review it into the catalog.

- **The description** (`custom-actions/types.ts`, `customActionDescriptionSchema`, Zod at the builder tool's boundary): an org-unique name (`microsoft.read-message`) that is no catalog action's and doesn't start with a word the catalog keeps (its actions' `google-mail.`, `google-sheet.`, or any `google-…`), so a catalog action added later never meets a custom one of its name, the registered app, a plain sentence, the call (an HTTP method and a path on the app with `{input}` placeholders, never a host, plus query and body mappings from inputs, a body field being a dotted path of property names and list indexes (`message.toRecipients.0.emailAddress.address`) so a nested body is described one scalar at a time, and the paths checked to make one body; or a GraphQL operation and its variables, mapped the same way), typed inputs (text, number, yes/no, a choice), typed result fields (text, number, yes/no), each with a label and a dotted path into the response (at least one for a read; a write's never reach the run, so it may name none, and none is a branch's condition field), and, for a write, the text inputs a reviewer may edit (`editable`, text inputs only; a read may name none). A `risk` it carries is dropped.
- **Checking it** (`custom-actions/description.ts`, `checkCustomAction`, pure, so the browser uses the same code): every placeholder and mapping names an input, a path placeholder's input isn't optional, the path stays on the app's hosts (`connections`' `appUrl`: one leading `/`, no host, no `.` or `..` segment, no backslash or fragment, and for Google a path one of its APIs serves), a GraphQL call only in a GraphQL app, then `policy`'s `customActionRisk` (`policy/custom-risk.ts`), the only thing that sets the level. A read and a write both pass: a write is `external_send`, so it waits for a person every time it runs. Every issue comes back at once, in words the builder can fix.
- **The fixed rule** (`customActionRisk(call, app)`, pure): `GET`, or a GraphQL document holding exactly one operation that is a query, is `read`; `POST`, `PUT`, `PATCH` or a mutation is `external_send`. Refused: a `DELETE`; a path, a body field (Drive's `trashed`, an event's `isCancelled`) or, for a mutation, the operation's name or a root field's (aliases included; every name in the document when its root spreads a fragment) any of whose words (split at punctuation and camelCase) starts with delete, remove, void, refund, cancel, archive, purge, trash or move. A query's fields are never checked, since it only reads (`cancelledAt`). Also refused: any write in an app registered as accounting or payments; a subscription, or a document with several operations or unbalanced braces.
- **Stored** in `custom_actions` (`org_id`, unique `name`, `app`, the checked description, the rule's `risk`, `accepted_by`, `accepted_at`, the `proposal_id` it came from), only ever inserted: a changed action is a new one with a new name, and storing a taken name that does something else is `ConflictError`. No `connection_id`: it holds nothing from any account. `listCustomActions(ctx)` reads them for any role.
- **Looking up the call** (`custom-actions/lib/api-lookup.ts`, `lookUpAppApi(ctx, { app, search, method? } | { app, type })`, admins only, reading no org data): the builder's `look_up_app_api` tool searches a registered app's published API description so the call it describes is real, never guessed. It reads the app's **operation index** (`app/api-descriptions/<app>/operations.json.gz`), which `pnpm api-index` (`app/scripts/api-index.ts`, through `custom-actions/api-index.ts`' pure `buildApiIndex`) builds from the copied description and which is committed beside it: every operation's method, path from the app's root with its placeholders renamed as input names (`{message-id}` becomes `{messageId}`), operation ID, summary (the vendor's first sentence), path and query parameters (no headers: a custom action sets none), and the types its JSON body and response name, each type flattened to its fields one level deep (inherited ones included). Graph's `$count` paths and `/users/{userId}/…` copies of `/me/…` calls are left out, so Graph's 44 MB of YAML becomes about 0.7 MB gzipped, read and made searchable once per server process (about 0.2 s, 60 MB); the lookup never parses a description itself. A test fails while an index's recorded SHA-256s differ from its description files', so a new copy needs `pnpm api-index`. Searching scores each operation on the search's words (lowercased, split at camelCase, singular) that its path or operation ID says, else its summary, plus what it acts on (its path's last segment), then prefers more words matched and shorter paths; it returns the best 8, each with its parameters, its body's and response's first 30 fields by name and type (a list response's items too) and what `customActionRisk` makes of it (a read, a write that waits for approval every time, or refused and why). A type looked up by name shows up to 60 fields with what each holds. The model reads the whole result; the conversation keeps only each found operation's method, path, summary and rule. `next.config.ts` traces the index files into the builder turn route.
- **Proposals:** the builder's `describe_custom_action` tool checks a description and adds it to the turn (`TurnInfo.customActions`); `propose_spec` checks the spec with them as if stored (`checkWorkflowSpec(ctx, spec, newCustomActions)`) and keeps those the spec uses on the proposal (`builder_proposals.custom_actions`). The card shows each as "New custom action": the app, its sentence, the call (method and path) and its level, "set by rule". Accepting checks the save with `checkWorkflowSave(ctx, { …, newCustomActions })`, then stores the actions (`storeCustomActions`, checking each again) and the spec (`saveWorkflowIn`) in the accept's one transaction: a stale or refused save stores neither, and a rejected proposal stores nothing.
- **The Custom actions page** (`/custom-actions`, admin-only like the builder chat; members are sent home): each of the company's custom actions in the same plain words as the card (`custom-actions/description.ts`' `customActionWords`), who accepted it (`orgs`' `userNames`) and when, and the workflows that use it. `workflows`' `workflowsUsingActions(ctx, names)` (admin-only, since working specs are) names, for each action, the company's workflows whose working spec or latest version uses it, at any depth (`requiredActions`, and the version's stored `required_actions`), archived ones marked.
- **Running** (`runtime/lib/custom-action.ts`, the one generic executor): `runAction` checks the input against the action's schema, then the executor finds the connection to the app (`connections`' `connectionToApp`: the run's own for Google, otherwise the same owner's connection to the app, the org's for an org connection, the oldest when several), fills the path (each value URL-encoded) and query, checks the URL is still on the app's hosts (nothing is sent otherwise), sends the `GET` through `proxyGet` (a GraphQL query would be POSTed with its document and variables through `proxyPost`, though the description check refuses GraphQL while no registered app has a GraphQL API), and picks the result fields out of the response (null when absent); the action's output schema then checks their types. A run whose owner has no connection to the app fails the step `app_not_connected`. Try it runs custom reads for real, like catalog reads. A custom write is never sent by its step: `runAction` hands it to `StepContext.holdSend`, which renders the same request (`renderRequest`, the same host check) and, in a run, holds it (`holdCustomWrite`, through the held-send adapter's `prepare`), or, in Try it, reports it as a `request` effect (the app, the action, the method, the URL and the body, exactly as it would be sent) and holds nothing (`dryRunHoldSend`). The step hands on `{ heldSendId, connectionId }`, never the app's answer.
- **Held sends** (ADR-0020, `runtime/lib/held-sends.ts`, the `held_sends` table): the rendered request (method, path with its query, URL, body) and the checked inputs it was rendered from, as one JSON value encrypted with the company's own key (`key-store`'s `encryptForOrg`, ADR-0024), with `org_id`, `connection_id` (the owner's connection to the app, which sends it; cascading, invariant 3), `run_id` (cascading with the run, so with the run's Gmail connection too), `step_id` (unique per run step, so a retried step holds one), `custom_action` (the name; `custom_actions (org_id, name)`), its run's `source_ref` and `owner_scope` (invariant 2), `review_id` (the review that waits on it, set when the approval step records it, cascading with the review) and `created_at`. Nothing else from it is stored, and no table holds its text in the clear. It's deleted the moment its review ends, whatever the outcome (approving takes it out of storage before sending it), and the daily check deletes any older than 30 days, a held send whose run stopped before its approval step included.
- **Workflows:** a custom action in an app other than Google needs a connection to that app of the kind the credentials name, checked at save (`appConnectionCheck`) and when a member enables (`ValidationError` until they connect it). Its app counts in `appsUsed`, so starting to use an app pauses members' enablements under M5's rules (`newApps`); it needs no scope of the run's Google connection. A custom Google action runs on the run's own Google connection, so it needs the scope of the Google app its path's prefix names (`googleAppOf`, from `GOOGLE_API_PREFIXES`; `CustomAction.scopes`), like a catalog action: the scope check at save (`workflows/lib/scope-check.ts`, which names the app, "needs Calendar … Reconnect it to allow Calendar", when the connection wasn't allowed it, as it does a catalog action's app, such as Tasks, and names the scope only when the app was allowed but not the scope, as on a read-only Gmail connection from before ADR-0011), `missingAccess` when a member enables (the app by name, such as Calendar, and its scope), and `requirementsGained`'s `newScopes`, so publishing a version that adds a custom Calendar read pauses members' enablements until they allow Calendar. In `appsUsed` it counts as that Google app (Calendar, not Google), so the pause names Calendar among its `newApps`, and the workflow's cards show Calendar's mark; one whose path no Google API serves counts as Google.

## Adding an app (ADR-0013)

Every app plugs in through the same four parts, so a new app is mostly catalog work by our team:

1. **Source:** a connector that reads what discovery needs, if anything (start cursor, backfill, poll). An app can act without being a source.
2. **Triggers:** what can start a run, such as a new email or a new Calendar invite.
3. **Catalog actions:** what a workflow may do in the app, each with a fixed risk level.
4. **Pending form:** where an `external_send` action waits for a person, inside the app itself. Mycel's **review** stores only a pointer to it and fetches it live.

| App      | Pending form                                                                  | Approving in Mycel                        |
| -------- | ----------------------------------------------------------------------------- | ----------------------------------------- |
| Gmail    | A draft                                                                       | Sends the draft (or edit it, then send)   |
| Calendar | The event on the person's calendar: no guests yet, private, not blocking time | Adds the guests and sends invitations     |
| Docs     | Suggested edits in the doc                                                    | Accepts the step's suggestions (ADR-0017) |
| Tasks    | None needed: tasks on the person's own list are reversible                    |                                           |

A review ends as approved, edited and approved, declined (which deletes the waiting item, where the app allows), done in the app, or gone. Where an app has no pending form (Slack, Teams, Chat, comments), Mycel holds the waiting send itself, encrypted, and deletes it when the review ends; a held send's review ends as expired after 30 days, or as unconfirmed when it was approved but its app didn't confirm the send (ADR-0020).

### Registered apps (`features/connections`, ADR-0018)

- **A registered app** is configuration our team writes once we've registered Mycel with the app's vendor and added its Nango integration: `connections/registered-apps.ts` (`REGISTERED_APPS`, pure, so anyone may import it, client code included). Each gives its name, Nango integration, allowed API hosts (exact origins; `isAppHost` checks a URL against them), the permissions (OAuth scopes) its connections ask for, whether it's an accounting or payments app, whether its terms ban stored indexes (ADR-0025), and its published API description, copied into `app/api-descriptions/` with where it came from, beside the operation index `pnpm api-index` builds from it for the builder's API lookup (see "Custom actions"). The registry lives in `connections`, not `custom-actions`, because `connections` connects and proxies the apps and `custom-actions` imports `connections`.
- **Registered so far:** Google (Discovery documents for Gmail, Drive, Sheets, Calendar, Docs and Tasks) and **Microsoft 365** (Microsoft's generated OpenAPI description of Graph v1.0, 44 MB, so kept gzipped). Microsoft 365 is the app the most business users use (`docs/research/integrations/ranking.md`: 450M+ paid Microsoft 365 commercial seats, and Okta's #1 app in 2025 and 2026), which is how we pick apps. It is one Nango integration, `microsoft`, on one host, `graph.microsoft.com`, with delegated permissions only, asked for all at once as ADR-0014 does for Google (`docs/research/integrations/microsoft-365.md`).
- **Connecting** one follows ADR-0014's pattern: `startConnect(ctx, app, kind)` opens a session on the app's integration; the creation webhook records what the app granted (`credentials.raw.scope`, space-separated) and the account, read through the proxy (Graph's `GET /v1.0/me`: `mail`, or `userPrincipalName` for a user without a mailbox), under the same account check as Google (a member's own sign-in address, or an org address in the Workspace domain for an admin's org connection). There's one connection per account and app (`connections_org_id_source_account_unique`). Reconnecting, Nango's refresh and deletion webhooks, reconciliation and disconnecting work as for Google, and disconnecting cascades (invariant 3).
- **Microsoft's catches** (`microsoft-365.md`, sections 0, 5 and 8): most of its permissions need one tenant-wide admin consent per customer, and an unverified publisher's app steps every user up to admin consent; a shared mailbox such as support@ can't sign in, so an org connection to one needs a licensed shared account until shared-mailbox access through a member's connection is designed; whether a token's `scope` lists Graph's permissions with the `https://graph.microsoft.com/` prefix is unverified, so check what a connection records in the dogfood check.
- **Not a discovery source:** a connection to an app other than Google records no ingest states and sends no `connections/connection.recorded`, so nothing backfills or polls it.
- **The proxy** (`proxyGet`, `proxyPost`, …) reaches any connection's app: a Google path names its API's host with `Base-Url-Override`; any other app's path goes to the host Nango keeps for the integration (`https://graph.microsoft.com`, so Graph paths start `/v1.0/`). Graph's error codes are strings, like Nango's own, so a Graph refusal makes the client ask Nango whether the connection still exists before reading it as the source's answer.
- **Adding one:** its ID in `registeredAppIdSchema` (`connections/types.ts`), its entry in `REGISTERED_APPS`, its API description, how to read which account it reached (`connections/lib/apps.ts`), its integration in `pnpm nango:preflight`, and a fake of its API in the fake Nango (`src/testing/fake-microsoft.ts` is Graph's, recording every request it receives).

### Pending-form adapters and reviews (`features/runtime`, `features/reviews`)

- **The adapter seam** (`runtime/adapters.ts`, `PendingFormAdapter`): each pending form has one adapter with five operations, each taking the caller's `ctx` and the waiting item's pointers (`PendingItem`: connection, `item_ref`, `thread_ref`, `source_ref`, when its review began, and the review's `details`, what approving needs that the app doesn't show Mycel or doesn't hold yet): `prepare(ctx, input)` creates the waiting item and returns its pointers; `approve(ctx, item, edits?)` carries it out, with any edits held in memory only; `decline(ctx, item)` removes it (a read-only adapter has none); `check(ctx, item)` says `waiting`, `done_in_app` or `gone`; and `view(ctx, item)` fetches it live for the Reviews page. `approve`, `decline` and `view` throw `ItemGoneError` when the item is no longer there. The entry file doesn't import `reviews`, which the interpreter imports to create reviews, so the two features' files never form a cycle.
- **The Gmail drafts adapter** (`runtime/lib/gmail-draft-adapter.ts`): `prepare` is the create-draft action (the catalog action's executor calls it); `approve` is `drafts.update` with the edited text (only when edited, keeping the draft's recipients, subject, place in the thread and marker header) then `drafts.send`; `decline` is `drafts.delete`; `check` finds the draft, or failing that a message sent in its thread since the review began (`done_in_app`) or nothing (`gone`); `view` fetches the draft and the message that started the run. All through the connections proxy (`proxyGet`, `proxyPost`, `proxyPut`, `proxyDelete`).
- **The held-send adapter** (`runtime/lib/held-send-adapter.ts`), for a custom write, whose app has no pending form (ADR-0020): `prepare` stores the held send and returns its ID as both `item_ref` and `thread_ref`; `approve` decrypts it, applies the person's edits (`{ fields }`, by input name) in memory to the action's editable text inputs only (`ValidationError` for any other, or an empty one), renders the request again from the stored custom action when edited, then takes it out of storage (`DELETE … RETURNING`, so only one caller ever holds it) and sends it once from memory through `proxyPost`, `proxyPut` or `proxyPatch`, its errors naming the action's path template rather than the rendered path. An app answering 404 ends the review `gone`. A refusal that certainly never reached the app (the connection gone, or a 4xx other than 408 from the app or Nango) puts the held send back as it was, and the review waits again. Any other failure (a 5xx, a timeout, a dropped connection) may have come after the app carried the request out, so it stays deleted and the adapter throws `SendUnconfirmedError`: the review ends `unconfirmed`, by the approver, and is never sent again; `decline` deletes it; `check` is `waiting` while it exists and `gone` once it doesn't (never `done_in_app`); `view` decrypts it and shows the app, the action and its sentence, the method and URL, and each input it sends with whether it's editable; and `purge(ctx, before)`, an operation only Mycel-held forms have, deletes every held send from before `before`. Its review's connection is the one the request goes through, so a colleague or tagged member acting on it is delegated that connection.
- **The suggested-edits adapter** (`runtime/lib/suggested-edits-adapter.ts`, with `docs.ts` and `suggested-edits.ts`; ADR-0017), for the edits a `google-docs.suggest-edits` step suggests in a Doc: `prepare` is the action (its executor calls it): `documents.batchUpdate` with `writeControl.writeMode: SUGGEST`, so every request is a suggestion and nothing in the doc changes, keeping the IDs Docs returns (`suggestionResponses[].createdSuggestionIds`, one list per request) as the review's `details`; they're the only way to tell the step's suggestions from the person's own, since Mycel writes as the person. Its `item_ref` is the first suggestion's ID and its `thread_ref` the doc's. A batchUpdate isn't idempotent and leaves no marker, so before writing the step notes the suggestion IDs already in the doc (`suggested_edit_writes`, one row per run step, IDs only, cascading with the connection and the run, with the run's `source_ref` and `owner_scope`); a retry whose earlier answer was lost finds the suggestions new since then and records those instead of writing again, and one whose write never landed finds none and writes. A suggestion the person makes in the doc in that moment would be counted as the step's: a known limit. An answer with `commentUpdateState: ALL_FAILED_UNKNOWN_REASON` means the edits may have landed directly, not as suggestions: the step fails `suggestions_not_saved`, isn't retried, and makes no review. `approve` reads the doc (`documents.get` with `suggestionsViewMode=SUGGESTIONS_INLINE` and `includeTabsContent=true`, walking every tab for the `suggested…Ids` lists and the keys of the `suggested…Changes` maps) and sends one batch of `acceptSuggestion` for each of the step's suggestions still there; `decline` sends `rejectSuggestion` the same way; neither touches another suggestion, and with none left they throw `ItemGoneError`. Accepting needs edit access to the doc: a 403 is a `ValidationError` and the review waits on. `check` is `gone` without the doc, `done_in_app` once none of the step's suggestions is left (accepted or rejected in Docs), and otherwise `waiting`. `view` fetches the doc's title, its link, what each of the step's suggestions still in it adds or removes (or that it restyles text), and whether the person may edit it (Drive's `capabilities.canEdit`, null when Drive can't say); without edit access the review offers only the link, and the doc's editors accept or reject in Docs. The edits' text is generated in an earlier step or written in the spec, and passes to the step through Inngest's step state (ADR-0021); a step's run record lists its result's fields by kind and size, and the approval's only the doc's and suggestions' IDs.
- **The Calendar events adapter** (`runtime/lib/calendar-event-adapter.ts`, with `calendar-events.ts`), for a meeting `google-calendar.create-event` booked: `prepare` is the action (its executor calls it): `events.insert` on the primary calendar with `sendUpdates=none`, **no attendees**, `visibility: private` and `transparency: transparent` (who sees an event comes from how the calendar is shared, not its guests: private hides its details from readers, and transparent keeps the held time out of colleagues' "find a time"), and, only when the step sets `meet`, `conferenceDataVersion=1` with a Meet `createRequest`. The event's ID is a SHA-256 of the run step's marker in hex (Calendar takes a client's own base32hex ID), so a retry whose answer was lost gets 409 and finds the event its earlier try made; `item_ref` and `thread_ref` are that ID, and `details` keeps the guests' addresses and how the event shows once approved (the step's `visibility` and `transparency`, `default` and `opaque` unless it says otherwise). `approve` reads the event and patches in only the guests it doesn't have yet, beside any it has, with `sendUpdates=all`, and the visibility and transparency; when every guest is there already (an earlier approval whose answer was lost), it invites nobody again and only sets how the event shows, if it differs, with `sendUpdates=none`. It takes no edits: a meeting is changed in Calendar. `decline` deletes the event (`sendUpdates=all` only if someone added guests meanwhile); `check` is `gone` for an event deleted or `cancelled`, `done_in_app` once it has any guest besides the person (they invited them in Calendar, or an approval did), and otherwise `waiting`; `view` reads the event live: its title, description, times, place, link and Meet link, with the guests from `details`.
- **The escalation adapter** (`runtime/lib/escalation-adapter.ts`) is read-only: `prepare` points at the escalated message itself (`item_ref` is its `source_ref`) and its thread; `approve` is "done" and changes nothing in Gmail; it has no `decline`; `check` is `done_in_app` once a message sent in the thread after the escalated one exists, `gone` once the message is, and otherwise `waiting`; `view` fetches the message and links to its thread in the connection's own Gmail (`authuser` is the connection's account).
- **Creating:** an `approval` step records a `waiting` review for each draft above it on its path (channel `gmail_drafts`), for each `google-docs.suggest-edits` tool step above it that suggested anything (channel `suggested_edits`, kind `suggested_edits`, keeping the suggestions' IDs in the review's `details`; the run records only the doc's and the suggestions' IDs), for each meeting a `google-calendar.create-event` tool step above it booked (channel `calendar_events`, kind `calendar_event`, keeping the step's guests and how the event shows once approved in the review's `details`; the run records only the events' IDs), or for each held send above it, from `tool` steps whose action is a custom write only (channel `held_send`, kind `held_send`, on the held send's own connection, then linked from the held send's `review_id`), through `StepContext.awaitReview` (the interpreter's calls `reviews`' `createReview` as the system ctx; Try it's records nothing). It's unique on `(org_id, run_id, item_ref)`, so a retried step or run makes no second review. The run still ends `succeeded`. An `escalate` step (a v1 gate's `else: "escalate"` is one after the upgrade) records a `waiting` review of kind `escalation` the same way, with the step's `reason`; a run escalates its message once, however many of its steps hand it over, and still ends `escalated`. A message already gone leaves no review.
- **The `reviews` table** holds pointers only (invariant 8): the connection (`(org_id, connection_id)` cascade, invariant 3), the run's own connection (`run_connection_id`, cascading too: the same as `connection_id` except for a held send, whose review is on the app connection while its `source_ref` came from the run's Gmail connection), run, workflow and version, `kind` (`approval`, `escalation`, `held_send`, `suggested_edits` or `calendar_event`; it chooses the adapter), `details` (what approving needs that the app doesn't show Mycel or doesn't hold yet, told apart by its `kind`: suggested edits' IDs, or a meeting's guests' addresses and how its event shows once approved, which Calendar can't hold for an event with no guests, never its title or description; null for every other kind), `reason` (an escalate step's words from the spec; null for an approval), `owner_scope` and `owner_user_id` (the member connection's owner, cascading with their membership; null for an org connection), `item_ref`, `thread_ref`, `source_ref`, `status`, `ended_by_user_id`, `ended_at`, `created_at`, and `handed_to_user_id` and `handed_by_user_id` once it's handed on (plain user IDs, like `ended_by_user_id`).
- **Who sees a review:** a member's review only its owner, so admins never read members' mail (ADR-0001); an org review (a **shared review**) everyone who sees its workflow's latest version through their tags, plus every admin; and either one the colleague it was last handed to. Tags are read on every list, open and action (`workflows`' `reviewSharing`), so a member who loses a tag stops seeing its shared reviews at once; an archived workflow's waiting reviews stay visible. The Reviews page shows a shared review as "Shared with" the workflow's tags the viewer may know: a member's own among them, every one for an admin. Anything else is `NotFoundError`, another org's included.
- **Hand-off** (`handOff(ctx, id, toUserId)`): a spec's `review: { handoff: true }` (default off, set in the editor or the publish dialog, not a risk change) lets a review be handed to a colleague. It needs the workflow's latest version to allow it (`ForbiddenError` otherwise), a target in the caller's org (`NotFoundError` for anyone else, another org's users included; `ValidationError` for the caller), the caller to be the owner for a member's review (`ForbiddenError`; only the member may show their mail to someone) or to see it for an org review, and the review to be waiting (`AlreadyHandledError`). Handing on again replaces the colleague. The colleague sees "Handed to you by …", and everyone else who sees it "Handed to …".
- **Opening** (`openReview`) asks the adapter's `check` first and ends the review as `done_in_app` or `gone` when it says so; otherwise it returns the adapter's live `view`, which is never stored. Asking and ending is one helper, `checkWaiting` in `reviews/lib/acting.ts`, which the jobs that end reviews outside Mycel reuse as the system ctx.
- **Ending in Gmail:** discovery's poll (or recovery) announces each sent Gmail message it newly stores as `discovery/gmail.message_sent` (`src/lib/events.ts`; message ID, thread ID and time only), beside `gmail.message_received`. Reviews' job (`reviews/jobs.ts`) calls `endReviewsInThread` as the system ctx, which runs `checkWaiting` on each waiting review in that thread on that connection, so a draft sent from Gmail, or a reply to an escalated message, ends its review `done_in_app` with nobody named. A sent message in another thread or on another connection checks nothing. A draft deleted in Gmail with nothing sent is caught when the review is opened, or by the daily check.
- **Acting** (`approveReview`, `approveEditedReview`, `declineReview`, and `markDone` for an escalation, which ends it `done_in_app` by the caller) is offered per kind (`reviewActions` in `reviews/types.ts`: approve, edit and decline for an approval or a held send, approve and decline for suggested edits or a meeting, done for an escalation); anything else is a `ValidationError` with nothing changed. It first claims the review with an update conditional on `status = 'waiting'`, recording who and when. If nothing changed, it throws `AlreadyHandledError` without calling the adapter, so the first to act wins and nothing is sent twice. If the adapter then fails, the claim is undone: the review waits again, or ends `gone` with its item (`ConflictError`). A held send whose app may have received it without confirming (`SendUnconfirmedError`) ends `unconfirmed` instead, still by the approver, with a `ConflictError` telling them to check the app. Acting and opening go through the review's own connection, with the caller's ctx delegated that one connection once `reviews` has checked the caller may see the review (`connections/delegation.ts`, ADR-0016), so a colleague or a tagged member sends from the owner's mailbox or the shared inbox. `AlreadyHandledError` names whoever acted first. `reviews` reaches an app only through the adapter of the review's kind; the functions take the adapters as a last argument, so a test can pass fakes.
- **Counts** (`reviewStats(ctx, { workflowId?, userId?, since, groupBy? })`, the ship bar's measurement, `docs/intent.md`): reviews made since a time, or since each workflow's current version (only those whose run was on the latest version, by `workflows`' `currentVersionIds`), counted by status (`expired` and `unconfirmed` among them), approvals, escalations, held sends, suggested edits and meetings apart, with the share approved without edits: `approved / (approved + edited_approved + declined + gone)` over approval reviews (null while none has ended so). A draft sent from Gmail (`done_in_app`) is shown beside the share but left out of it, because Mycel can't tell whether it was edited. A person's reviews are those in their own mailbox (`owner_user_id`); a shared inbox's belong to no member. Admins may count anyone's and, with `groupBy: "user"`, each person's apart; a member gets only their own, and `ForbiddenError` for anyone else's or for counting by person. The counts read only status, owner, kind, version and time, never mail, and call no model, so nothing is debited. The Workflows page shows them over the last 2, 7 (the default) or 30 days, or since the current version: per workflow and per member under it for admins, per visible workflow for a member.
- **The Reviews page** (`/reviews`) is the landing page: `/` and sign-in go there. It lists the caller's waiting reviews oldest first, with workflow and age; `/reviews/[reviewId]` opens one, showing the live message and draft with approve, edit and decline, or, for an escalation, the live message, the step's reason and a link to it in Gmail, with done, or, for a held send, the request's app, action, method and URL and each field it sends, with approve, edit (its editable fields) and decline, or, for suggested edits, the doc's title and link and what each of the step's suggestions changes, with approve (accept them) and decline (reject them), or the link alone when the person can't edit the doc, or, for a meeting, the event as it is on the calendar now (title, description, times, place, links), the guests approving invites and how it will then show, with approve and decline.

### Waiting count and the daily check (`features/reviews`)

- **Mycel sends no email in v1.** What waits for a person lives only in the app: the Reviews page is the landing page after sign-in, and every signed-in page's navigation shows how many reviews wait. There's no email provider, no notification setting and no unsubscribe link. Admins' alerts are in the app too (see **Failures and observability**).
- **The count:** `countWaitingReviews(ctx)` counts the reviews `listReviews(ctx)` lists, through the same visibility filter, so shared and handed-on reviews count and other people's don't. Every signed-in page renders the app shell (`src/app/_shell/app-shell.tsx`) itself, passing its title and its sidebar item, so the count is read on each page load, following a link included; it's not a shared layout, since a layout isn't rendered again on navigation. There's no live push.
- **The daily check** is an Inngest cron (`checkWaitingReviewsJob` in `reviews/jobs.ts`, `check-waiting-reviews`, 07:00 UTC) that acts inside each org as its system ctx (ADR-0009), one step per org, so an org whose step fails is retried alone. It runs `checkWaitingReviews`, which calls `checkWaiting` on each waiting review in the org and ends the ones `done_in_app` or `gone` with no one named, so the count and the Reviews page drop what was finished or deleted in Gmail even if nobody opens it. A draft sent from Gmail is usually ended sooner by the sent-message job; the daily check is what ends a draft deleted with nothing sent. A review whose app can't be asked now (a connection needing reauthorization) waits on and still counts. A review of a kind Mycel holds the item of (`REVIEW_EXPIRY_DAYS`: a held send, 30 days) that has waited longer ends `expired`, by nobody, and its adapter's `decline` deletes the item (if that fails, it waits on until the next check); then that adapter's `purge` deletes whatever it still holds from before the cutoff. Reviews of items an app holds never expire. Only the system ctx may run it (`ForbiddenError` for anyone else). It sends nothing.

## Risk policy (`features/policy`)

Each catalog action has a fixed level: `read` < `internal_reversible` < `external_send` < `financial` < `destructive`.

- `read`, `internal_reversible`: may run autonomously.
- `external_send`: must wait in the app's pending form for a person's review (ADR-0013). M3 approves by sending the Gmail draft; from M5 on, every review also appears on the Reviews page.
- `financial`, `destructive`: not available in v1.

The catalog is code (`features/policy/catalog.ts`), each action with its risk level, integration, the API host its proxy calls reach, the scopes that allow it, and input and output schemas. An action on what Mycel itself holds (`integration: "mycel"`, app `Memory`) calls no app, so it has no host or scopes and needs nothing of the connection: `scopesOf(action)` (`policy/action-set.ts`, over any action in the action set) gives a Google action's scopes and none for it or for a custom action, and `appsUsed` counts Google and custom actions' apps, never Memory. An action's output may carry content to later steps (ADR-0021), but never into its run record.

Nothing looks an action up in the catalog directly. An org's **action set** (`policy`'s `ActionSet`: its actions in order, and `find(name)`) is what its workflows may use: `custom-actions`' `getActionSet(ctx)` resolves it once per request (the catalog, then the org's custom actions, each an `Action` of kind `custom` built by `actionSetWith` from its stored record; the first action of a name wins, so the catalog's does), and everything else takes it as an argument: the policy engine, saving, checking and publishing (`workflows`' validation, scope check, requirements and version pauses), the runtime's step context (`StepContext.actionSet`, set by runs and Try it), and the builder's context and proposal cards (`getWorkflow(ctx, id, actions)` takes one already resolved, so the builder's context doesn't resolve it per workflow). The graph, the step menu and the side panel read it in the browser through `workflows`' `useActionSet()`: a page passes the org's custom actions, as plain records (Zod schemas can't cross to the client), to `ActionSetProvider` at its client root (the workflow page, the new-workflow page and the builder page, which also draws a waiting proposal with the custom actions it brings); without one, it's the catalog.

| ------------------------------ | --------------------- | -------------------------------------- | ---------------------------------------- |
| `google-mail.read-message`     | `read`                | Gmail                                  | `gmail.readonly` or `gmail.modify`       |
| `google-mail.read-thread`      | `read`                | Gmail                                  | `gmail.readonly` or `gmail.modify`       |
| `google-mail.add-label`        | `internal_reversible` | Gmail                                  | `gmail.modify`                           |
| `google-mail.create-draft`     | `external_send`       | Gmail                                  | `gmail.modify` or `gmail.compose`        |

`maxRisk(spec, actions)` is the highest level among the spec's `tool` actions and `draft` outputs; model steps count as `read`, and a `risk` field in the spec is ignored. `applyPolicy(spec, actions)` refuses actions not in the action set, an `external_send` catalog action in a `tool` step whose approval channel is a draft's (`gmail_drafts`: a Gmail send goes through a draft), and a `draft` output of any other action (a booking, suggested edits or a custom write included). A catalog send names the channel that reviews it (`CatalogAction.channel`): `gmail_drafts` for create-draft, `suggested_edits` for suggest-edits and `calendar_events` for create-event, the last two run by a `tool` step. It inserts an `approval` step directly after any send with no approval of its channel after it in its own list, and reports each insertion: `channel: "gmail_drafts"` after a draft, `channel: "suggested_edits"` after a `google-docs.suggest-edits` tool step, `channel: "calendar_events"` after a `tool` step booking a meeting, and `channel: "held_send"` after a `tool` step using an `external_send` custom action (ADR-0018, ADR-0020). It also refuses, at the request's path, each Docs request a suggest-edits step names that Docs refuses in suggest mode (`addDocumentTab`, `createNamedRange`, `deleteFooter`, `deleteHeader`, `deleteNamedRange`, `deleteTab`, `updateDocumentTabProperties`, `updateTableColumnProperties`, and an `updateDocumentStyle` of `documentFormat`, `useEvenPageHeaderFooter` or `useFirstPageHeaderFooter`), any that accepts, rejects or deletes a suggestion or comments, which would act without the review, and any that isn't a Docs request (`policy/docs-requests.ts`, part of the action's input schema, so a run checks them again once references are resolved). Only that approval counts, since every run that makes the send reaches it: one above the send ran before the send was made, and one on a sibling path, or on a path below the send, which a run may not take, doesn't count either; nor does an approval of another channel. Max risk covers every path.

## Models (`features/models`)

- Roles: `classify` (Jev via AI Gateway, with structured-output LLM fallback), `fast`, `smart`, `judge`, and `embed` (text to vectors). A step may name any role but `embed`.
- Jev is called through the AI SDK's experimental `experimental_decide`, so its version is pinned exactly. An adapter normalises Jev's two output shapes into one `{ label, p }`. Specs never see Jev's own format.
- Use Jev's probabilities as confidence gates: high confidence proceeds, low confidence goes to a human. Treat a gate threshold (e.g. `0.85`) as a number tuned per workflow by shadow eval, not as a trusted calibrated probability.
- The per-org role→model table lives in the DB, with a global default table in config. `embed`'s default (`openai/text-embedding-3-small`, 1536 dimensions) is the one with a fallback in config, since stored vectors must keep one size.
- Model calls live in their own feature, `models`, which `runtime`, `builder` and `memory` import, so `runtime` can read memory without a cycle. Every call goes through one gateway client (`callModel`, `classify` and `embed` in `models`), which resolves the role, checks credits, calls with the SDK's retries off (the caller's step retries instead), records the cost, and turns any failure into a `ModelCallError` holding only codes, never the model's output (invariant 8). A call that takes several gateway requests (`embed` sends at most 2048 texts a request, one request at a time) records one entry with their summed cost. A caller that streams opens `openMeteredStream` instead: the same role resolution and credit check, then one usage entry with the summed cost of the steps it metered, however the stream ended.
- **A chat's turn** (`streamChatTurn`, the builder chat's and any other chat's) is that metered stream with tools: one `streamText` call on the chat's role, capped at the chat's number of steps, with the SDK's retries off. Out of credits it calls no model, and the chat stores and streams an `out_of_credits` notice; a step that fails ends the turn with the chat's own `failed` notice. It hands the page and the chat's storage each tool result as that tool stores it, and each tool error as our typed error's message or a generic line (a prompt in `models/prompts/`), since the SDK's errors may quote the model's input. Tools are defined with `chatTool`, generic over the chat's own turn context, and run with the person's ctx. A chat stores the shared parts (text, tool, notice; `chatPartSchemas`) beside kinds of its own, and reads its messages back with `chatModelMessages` (saying what its own kinds read as to the model) and `chatUIPart`. The chat keeps its conversations, instructions, prompts, UI parts and route.
- `models` also holds the injection screen (`screenForInjection`, Model Armor; see "Memory"), metered the same way but outside the gateway, its ledger entry naming the service instead of a role.
- `classify` falls back to a structured-output call on `fast` when Jev fails, refuses, answers without probabilities or with a label it wasn't offered, or when the org's classify model isn't a decision model. The answer is marked as a fallback, and its `p` is the model's stated confidence.

## Credits (`features/credits`)

- Every org has a credit balance. All model calls, discovery jobs, and evals debit the ledger.
- When the org balance is exhausted, **hard stop**: every workflow is paused, out of credits (see "Pausing"). Mycel sends no email in v1 (ADR-0010): admins get an alert in the app and a banner across every page (see **Failures and observability**).
- **Out of credits (M7)** means the balance is at or below zero (`isOutOfCredits(ctx)`), read from the ledger whenever it's needed: at fan-out and when a page shows a switch. Nothing is written when it starts or ends, so a grant lifts it at once, with no job. A run already under way still checks credits before each model call and ends "out of credits" as before; the builder chat and Try it keep refusing on their own pre-flight check.
- Admins can set **per-workflow monthly budgets** (the spec's `budget.monthlyCredits`). **Budget reached (M7)** means the workflow's live run usage this calendar month (UTC) is at or above its latest version's budget: usage entries with its `workflow_id` and a `run_id`, not `dry_run`, so Try it and builder turns never count. It's read from the ledger like out of credits (`budgetsReached(ctx, budgets)`, for any role, since it says only what members are shown, and `spentThisMonthByWorkflow(ctx, workflowIds)`, admins and jobs only, for the Health tab), one query however many workflows, over an index on `(org_id, workflow_id, created_at)`. A new month, or a published version with a higher budget or none, lifts it with no job. A run already under way isn't stopped, so the run that crosses the budget finishes and may overshoot it by its own cost.
- **M3's thin slice** (ADR-0010): `credit_ledger` holds grants and one usage entry per model call; the balance is their sum. Before each call, `checkCredits` needs the balance to cover a per-role estimate from config, or throws `OutOfCreditsError` and nothing is sent. After it, the call's gateway cost (`providerMetadata.gateway.cost`, US dollars) is converted at the config's credits-per-dollar ratio and recorded, failed calls included. Our team grants credits with `pnpm credits:grant <orgId> <credits> <note>`: the note ("October allowance") is required, kept on the grant's entry and shown on the Credits page, and the script sends `credits/granted`. A usage entry made by "Try it" is marked `dry_run`.
- **What each entry was for:** every usage entry says, in the attribution its call passes, and so falls in one of the kinds of use the Credits page splits spending into (`spendingKindOf` in `credits/types.ts`): a **workflow** run's names its `workflow_id` and `run_id`; **Try it**'s is marked `dry_run` (with the workflow, no run); the rest carry a `purpose`. `builder` is the builder chat's: each turn, and anything the chat asks for (a summary read as `builder`). `agent` is a person's Ask Mycel's: each turn, and the injection screens of what its tools read, a kind of its own on the Credits page. `memory` is memory's learning: every model call and injection screen learning makes. `memory_summary` is a person's own summary, which the Credits page counts as memory's too, but which is kept apart so memory's budget can cap learning alone. An injection screen is attributed to whatever called it (memory's learning today), so it has no kind of its own. `getSpending(ctx, { purpose, since })` adds up a purpose's credits from a time on, for memory's monthly budget (`memory` only; see "Memory"), and `forOrg`'s `sumBy` adds up spending by purpose or by workflow in one query.
- **The Credits page (M7, admins only):** `/credits`, in the sidebar's Company group, shows the balance and the runway now (labelled so, whatever the range), and over the range chosen beside its title: what was spent and granted, one chart with three lenses (the balance, each grant a step up, with a dashed projection to zero at the 7-day rate while the range includes today; spending stacked by kind, by day up to 45 days, by week up to 125, then by calendar month; and each workflow's live-run spending for its month, a running total against its budget with a red dot where it reached it, which across months is one row per workflow restarting on each 1st), the breakdown by kind and by workflow beneath it, and the range's newest 25 ledger entries. The sidebar's foot shows admins the balance and runway; members get neither, and the page redirects them.
- **The Credits page's range:** This month (the default), Last month, Last 3 months, Last 12 months (whole months from the 1st, since budgets and grants are monthly) or Custom (a first and a last day), kept in the address (`?range=this_month|last_month|3m|12m|custom&from=&to=`, read by `creditsQuerySchema`, a bad value falling back rather than failing) so it survives a reload; the presets are links and Custom a GET form. `resolveRange` (`credits/range.ts`, pure) turns it into whole UTC days, both ends kept between the day of the org's first entry (`getLedgerStart`) and today, so a range from before the org's history or into the future is clamped, never an error. The page reads it once per request (React's `cache`) for both the control beside the title and the body.
- **Summing a range:** `getSpendingSummary(ctx, range)` adds up any range (from, up to `to`; `monthRange(now)` is this calendar month, UTC) in two queries whatever the number of workflows, entries or days: one `sumBy` grouped by UTC day, kind, `dry_run`, `purpose`, `workflow_id` and whether a run made it, starting on the 1st of the range's first month so each workflow's month-to-date spending before a mid-month range comes back too (`monthBefore`), and the balance before the range. Each group falls in its kind by `spendingKindOf`, and a workflow's spending is only its live runs'. Weeks, months and running totals are added up from those daily sums (`credits/range.ts`). `getRunway(ctx)` is the balance over the last 7 days' average daily usage, or none when nothing was used. `listLedger(ctx, filter)` takes a limit, kind, workflow and range. The page is 9 queries for 1 workflow or 20, over a month or 12. Workflow names and budgets (the latest published version's `budget.monthlyCredits`, from `listWorkflowBudgets`, applied to every month of the range) are joined on the page (`app/credits/credits-data.ts`), since `workflows` reads `credits` for its pauses and the reverse import would be a cycle; while the range includes today, a workflow that reached its budget is marked "Paused: budget reached" by `budgetsReached`, the pause's own rule (see above), so the page and the fan-out agree; it's asked whatever the range, so the page's queries don't depend on it. A past month says instead on which days its running total reached the budget, worked out from the summary's daily sums (`budgetReachedOn`), since `budgetsReached` answers only this month. The page's own spending lines come from the summary, whatever its range; the Health tab's spent-this-month comes from `spentThisMonthByWorkflow`. The entries mark a failed call "Failed call" and its later correction "Failed call's cost".
- **Failed-call costs:** a call that fails with a gateway error carries no cost, so it's recorded at 0 with its `generationId`, though the gateway may still bill it. A streamed call's failed step reports no cost either: the caller hands its error to the metered stream's `meterError`, which takes the generation ID the AI SDK's gateway error carries (read off the gateway's error body), so the entry names the failed generation. A stream whose earlier steps reported a cost is recorded above 0, though, so its failed step's billed cost isn't looked up (a known gap). Recording such an entry (in `models`: `meteredCall` and a metered stream's `finish`) sends `models/failed-call.recorded`. Its job (`models-failed-call-cost`) waits 3 minutes, then looks the generation up in the gateway's Generation Lookup API (`GET /v1/generation?id=…` on the gateway's origin, a plain fetch beside the gateway client, reading `total_cost`) through `correctFailedCallCost`, and `credits`' `recordFailedCallCost` writes a correcting `usage` entry: the billed cost, with the original's role, model, workflow, run, `dry_run` and purpose, at the original's time (so it counts in the call's month), its `corrects_id` naming the original. A unique key on `corrects_id` makes it one correction per failed call, however often the step is retried. While the gateway answers 404 (its usage events are ingested late), 429 or 5xx, or can't be reached, the job waits twice as long as before (up to two hours) and looks again, and a day after the call it gives up; a refusal (401, 403, 400) throws `GenerationLookupError`. Calls with no generation ID stay at 0, and so does one whose event couldn't be sent (the call's own error is kept). `LedgerEntry.correctsId` lets the Credits page tell a correction from the failed call it corrects.

## Versioning

- Publishing an edited workflow creates a new **workflow version**. Members' enablements **auto-upgrade**.
- **Exception:** if the new version raises the max risk level or needs a new connection or data source, members' enablements **pause until they re-enable**. Keep everything else simple and automatic.
- **How (M5):** `policy`'s `requirementsGained(before, after, actions)` compares the new version's max risk, apps and scopes (all from the company's action set) with the latest version's. A scope counts as new when no earlier action was allowed by a subset of the new action's scopes. If anything was gained and the workflow is member-credential, `publishWorkflow` pauses every `on` enablement with `needs_reenable` and `paused_change` (`maxRiskRaised`, `newApps`, `newScopes`) in the same transaction as the version (`workflows/lib/version-pauses.ts`); an enablement already paused gets the new gains added to what it waits for. Org switches always follow: the admin publishing would be the one to switch it on again. `previewPublish(ctx, workflowId, spec)` returns what's gained and how many enablements publishing would pause, for the publish dialog. Re-enabling goes through `enable`, so a new app or scope sends the member through reconnecting first. Runs pin their version at fan-out, and `listSwitchedOn` ignores pauses, so a run under way finishes on the version it started on.

## Pausing

"Paused" is one state with four causes. The reason is always shown with it (e.g. "paused: out of credits").

| Cause                                             | What's paused             | How it resumes                                                                  |
| ------------------------------------------------- | ------------------------- | ------------------------------------------------------------------------------- |
| Org credits exhausted                             | every workflow in the org | automatically, once credits are added                                           |
| Workflow budget reached                           | that workflow             | automatically next month (UTC), or once a raised or removed budget is published |
| 3 consecutive failed runs                         | that workflow             | only when an admin resumes it manually                                          |
| New version raises risk or needs a new connection | each member's enablement  | only when that member re-enables                                                |

**One pause model (M7, `workflows/lib/pauses.ts`).** Every pause that holds on a switch is listed in one order, `PAUSED_REASONS`: `out_of_credits`, `failures`, `budget_reached`, then `needs_reenable`. The first is the switch's effective state, the one its badge shows; the notice under it explains each that holds (what it means, whether the switch stays on, what lifts it). `pausesOf(stored, holds)` joins what the switch stores (an enablement's `paused` status and `paused_reason`, only ever `needs_reenable`) with what holds over its workflow (`readHolds(ctx, workflowIds)`: whether the company is out of credits, which of the workflows are paused for failing, and which workflows' latest versions have a budget their live runs have reached this month, in the same queries however many workflows there are; a workflow without a budget has no spending read). `listStartable` starts nothing for a switch with any pause, and `WorkflowSwitch.pauses` and `EnablementSummary.pauses` carry the list to the members' cards, the admin's switch badge, org switch and "enabled by" list. Pauses that are worked out never change an enablement's stored status, so nobody re-enables after one. A message that arrives during a pause is never run later: nothing is queued.

**Paused: failing (M8).** The workflow stores it (`workflows.paused_reason = failures`, with `paused_at` and `paused_by_run_ids`, the three runs that paused it), for every enablement and the org switch alike; the enablements stay `on`. Runtime decides it (see "Failures and observability") and asks `workflows`' `pauseForFailures`, since `workflows` can't read runs. Only an admin lifts it, with Resume (`resumeWorkflow`) on the Health tab, which records `resumed_at`; publishing a new version keeps it. Members see "Paused: failing, an admin will look at it".

**The workflow page's tabs (M7).** An admin's workflow page has three tabs (`workflows`' `WorkflowTabs`): Editor (the editor, Try it, the switch, archiving and builder conversations), Runs (running it on a message, its latest runs and a link to the Runs page) and Health (`WorkflowHealthChecks`, from `getWorkflowHealth`). Health lists one check per thing that can stop the workflow, in `PAUSED_REASONS`' order: the company has credits; its runs aren't failing, or, while paused for failing, since when, the three runs that paused it (when each ended, whose inbox, the failed step and the error, each linked to its run page, read through runtime's `pausingRuns`) and Resume; and spent X of Y credits this month against the latest version's budget, with the budget's help and a way to its field in the editor's settings (a budget changes with a published version, like the rest of the spec). A published, unarchived workflow that a pause holds over, failing included, opens on Health, and the tab carries a dot then. Every tab stays mounted, so an unsaved edit survives a look at Health.

A connection that needs reconnecting (`needs_reauth`, when Google refuses its token) is not a pause. It's a connection state: its enablements and org switches stay as they are, the Workflows page says "reconnect Google" rather than "paused", fan-out starts nothing on the connection meanwhile, and reconnecting it resumes everything at once, with no one re-enabling.

## Failures and observability

- Steps retry with backoff (3 attempts). The attempts run inside the step's Inngest step, so each step's record counts them, and a step whose last attempt fails records the failure and ends its path `failed` instead of throwing (the run `failed`, or `partly_failed` when other paths finished). Some failures aren't retried: out of credits, a connection that's gone (the run ends `cancelled`), a token the app refused (`needs_reconnect`), an action whose executor isn't built yet, a bad reference, and Gmail having no such message. Every failure is recorded in observability.
- **Checks:** a step may carry `checks: { schema?, minP?, requiredFields? }`, run on the output it hands on. `schema` is a JSON Schema subset (`type`, `enum`, `properties`, `required`, `additionalProperties`, `items`, `minimum`/`maximum`, `minLength`/`maxLength`, `minItems`/`maxItems`); validation refuses any other keyword, `minP` off a classify, and a required field the extract doesn't have. A failed check records the step `check_failed` with `check_schema`, `check_min_p` or `check_required_fields`, isn't retried, and fails the run. A model answer that doesn't fit the step's own schema is a failed `schema` check when the step has one, and a retried `model_off_schema` otherwise.
- **Failure records:** each failed step keeps an error code, a message built from codes, field paths and value types (never values), its attempt count and when its last attempt began (`last_attempt_at`). The step returns `{ ended: "failed" }` to Inngest rather than throwing (with `endsRun` when it ran out of credits, which stops every path), so the step state holds no error at all.
- **A run that crashes ends.** Inngest retries the `run-workflow` job twice for infrastructure errors; once those run out, its `onFailure` handler (`failCrashedRun`) ends a run still `running` as `failed`, with the run-level error code `internal_error` on `runs.error_code`, once. An unexpected error, a crashed run's or a step's `internal_error`, is logged with `console.error` by code, run ID and step ID only (`internal_error run=<id> step=<id>`), never the error's message, so our team finds it in Vercel's logs. Wherever it's shown, an `internal_error` reads "Something went wrong on our side. Nothing in the workflow needs changing."
- **Run records** (`runs`, `run_steps`) cascade from their connection and hold derived data only: labels and probabilities, IDs, an `extract` step's field names and whether each was filled (never the values), a `tool` step's result fields each with its kind (`text`, `number`, `yes_no`, `list`, `record`, `empty`) and size (characters, items or fields) instead of the result itself, error codes and messages built from codes, the model role and ID, and cost. Run history, traces and admin views show only what run records hold. Who sees a run's record follows the Runs page's rules below.
- **Content between steps** (ADR-0021): a step's output may carry content to later steps, such as `read-message`'s sender, subject and body, which a later `tool` step's input references (`{ from: "read.body" }`) or a `draft` step names as context. It passes through Inngest's step state, which the client's encryption middleware (`@inngest/middleware-encryption`, in `src/lib/inngest.ts`) encrypts under one app key (`INNGEST_ENCRYPTION_KEY`, held in a KMS in production), function results included, so Inngest stores and shows only ciphertext until its retention ends. Model steps still fetch the triggering message through the Nango proxy inside themselves.
- **Writes are idempotent per step.** Nango's proxy doesn't retry a POST (`proxyPost`), since a write whose answer was lost may still have happened; instead each write action checks for its own earlier result before acting. `add-label` finds the label by name before creating it and skips `messages.modify` when the message already has it. A `draft` step fetches its context, generates on its role and creates the draft in one step, so the text never reaches Inngest's state or the run records; the draft carries an `X-Mycel-Draft: <run ID>/<step ID>` header, and a retry that finds a draft with its marker in the thread (via `threads.get` with `format=metadata`, then `drafts.list` for the draft's ID) records that draft instead of generating again. The draft replies to `Reply-To` or else `From`, with `Re:` on the subject and `In-Reply-To` and `References` from the original. `append-row` writes `RAW` (so a value is never read as a formula), with a marker cell `mycel:<run ID>/<step ID>` after the row's last value; before appending it reads the range's whole sheet for a row holding its marker and records that row instead. Both Sheets actions take a range that names its sheet (`Sheet1!A:C`); save-time validation refuses a literal range without one, at the input's path, as it does any literal input the action's schema refuses. A `read-range` step records the range and its row and column counts, never the values; a `draft` step that names it as context re-reads the range inside the draft step. A `memory.lookup` step (`runtime/lib/memory-lookup.ts`; `about`: `sender`, `sender_company` or `topic` with a `topic`) searches memory by the triggering message's sender address or domain, read inside the step, or by the topic's words, and hands on up to 10 facts (`factCount` and each fact's ID, subject and statement, with `disputed` on one only someone outside the company states against a fact from inside, which the draft step marks as disputed); a `draft` step that names it reads them as a list marked as data. It reads in the view of whoever the run acts for: a member connection's owner (the enabling member, read fresh with their role) or, on an org connection, the org's system ctx, which sees only company-wide facts (ADR-0023); each read is logged as `workflow_run` with the run and workflow. Its run record lists only its fields' kinds and sizes, never the facts, since admins browse run records and a member's facts are theirs (ADR-0001). Executors get the run (`id`, `workflowId`, `sourceRef`) as their last argument. A Sheets or Docs 404 (`source_item_missing`), 400 (`invalid_input`) or 403 (`source_forbidden`) isn't retried. `suggest-edits` notes where the doc stood before it writes, and a retry finds what an earlier write created (see the suggested-edits adapter). The Tasks actions (`runtime/lib/tasks.ts`) act on the person's default list, the first `tasklists.list` gives (the REST reference doesn't document `@default`), and run with no review, like adding a label. A task's title and notes come into the step from its input, literal or from an earlier step (an extract's fields, say), and only the task's ID leaves it, so the run record keeps the ID's kind and size (ADR-0021). `create-task` writes its notes with a blank line, then a marker line `mycel:<run ID>/<step ID>` and `Added by the Mycel workflow “<name>”`; before inserting, it lists the default list (completed and hidden tasks included) for a task whose notes carry its marker, and records that task instead. `update-task` patches only the fields it's given (title, notes, due date, `done`), new notes ending `Updated by the Mycel workflow “<name>”`; a patch sets the same fields however often it's tried. A task assigned to the person from Docs or Chat (one with `assignmentInfo`) is left alone, since the API can change one and the change shows where it was assigned: `list-tasks` asks with `showAssigned=false` (Google's default) and drops any that come anyway, and `update-task` reads the task first and fails the step with `task_assigned`, unretried, changing nothing; the API can't create an assigned task. `list-tasks` hands on the open tasks (`taskCount`, which a branch may test, and each task's ID, title, notes and due date). A due date is a date only (`YYYY-MM-DD`), since Tasks drops the time of day; save-time validation refuses a literal one with a time. A Tasks 404 (`source_item_missing`), 400 (`invalid_input`) or 403 (`source_forbidden`) isn't retried. An `approval` step (`gmail_drafts`) records the drafts above it on its own path that await a person, who approves by sending one; a `held_send` approval records the held sends above it the same way. It doesn't end the run: a run never sends a Gmail draft, so the draft is itself what awaits approval, and the steps after the approval (a log row, say) still run, as does a draft after an approval.
- **Auto-pause (M8, `runtime/lib/failure-streak.ts`).** Three counted failures in a row pause the workflow, **paused: failing** (see "Pausing"), until an admin resumes it. Mycel sends no email in v1 (ADR-0010); M8's in-app alerts tell admins. Whenever a run ends `failed` or `partly_failed` (in `executeRun`, and in `failCrashedRun`), runtime reads the workflow's runs that ended since it was last resumed or its latest version was published, whichever is later (`failureStreakStart`), newest first, a page at a time until the streak is decided. No counter is stored, so it can't drift.
  - **Counted:** `failed` and `partly_failed`, and a crashed run (`internal_error`).
  - **Reset:** `succeeded`, `escalated`, `skipped`.
  - **Ignored:** `cancelled`, and a failure whose failed steps all failed for one connection's or the credits' reason: `out_of_credits`, `connection_gone`, `app_not_connected`, `source_forbidden` or `needs_reconnect` (Nango's proxy answering 424: the app refused the connection's token mid-run; not retried). One person's broken connection mustn't pause everyone, and running out of credits pauses every workflow anyway.
  - The third counted failure pauses it with those three runs. Pausing is idempotent: a paused workflow isn't counted again, and a run job that ends a run again works it out again.
- Observability is built in our UI on our own `runs` and `run_steps` tables, written by the interpreter. Inngest's dashboard is for development and debugging only.
- **The Runs page** (`/runs`, `runtime`'s `listRuns(ctx, filters, page)`) lists runs across every workflow, newest first, filtered by workflow, status and connection (kept in the address) and keyset-paged on `(started_at, id)` (`runs_org_id_started_at_id_idx`), Newer and Older. An admin sees every run in the org; a member the runs on their own member connection. A run is shown in full (its message's subject and sender, or a Calendar-triggered run's invite's title and organizer, fetched through the proxy for display only; which one comes from the trigger of the version it ran) only to its connection's readers, the owning member or any admin for an org connection; to anyone else it's redacted: status, failed steps with their error codes and messages, cost and times, its inbox named by its owner alone (`connections`' `connectionOwners`), with no source ref, subject, sender or step outputs (ADR-0001). A page makes the same queries for 1 run as for 100: whose each connection is, the page, its failed steps, their versions (`workflows`' `versionsById`), the workflows' names and the readable connections' source clients (`sourceClients`). The workflow page shows its latest 10 runs and links to the Runs page filtered to it. Each row opens its run's page. A run started from Ask Mycel (`started_by = agent`) is marked "From Ask Mycel" beside its workflow.
- **A run's page** (`/runs/<run ID>`) follows the same rules. `runtime`'s `getRun(ctx, runId)` gives the run, its steps in order (status, attempts, model, cost, times, each check's outcome, and the error), the version it ran with its spec, and its trace: the steps it reached and the paths each branch took, built from the records (a branch records the paths it took and each check's pass or fail), which the workflow graph lights up as it lights a Try it. Redacted, it has no source ref and no step outputs, and its trace no path's checks, since which check passed says something of the message; a member asking for anyone else's run gets `ForbiddenError` ("This run isn't yours to see"). `getRunMessage` fetches the message's subject and sender through the proxy, with a link to its thread in Gmail (`connections/gmail.ts`'s `gmailLink`, which escalation reviews use too), or, for a Calendar-triggered run, the invite's title and organizer with its `htmlLink` (never its description), for its connection's readers only. `reviews`' `reviewsOfRun` lists the reviews the run created, kind and status only: every one for an admin, linked when they may open it; a member's own for a member. A failure reads the same on both pages (`runtime/failure-texts.ts`): what went wrong and what to do, from its code, with an `internal_error` ours to fix. The page makes the same queries however many steps the run has.
- **Retrying a run** (`runtime`'s `retryRun(ctx, runId)`, Retry in the run page's summary strip): a `failed` or `partly_failed` run is retried by its connection's reader, the member who owns it or an admin for an org connection, never an admin on a colleague's inbox (ADR-0001). It records a new run of the workflow's latest version on the same connection and `source_ref`, `started_by = retry` with `retry_of_run_id` naming the run it retries, and sends `runtime/run.requested` as the trigger does. It's refused while the workflow is archived, no longer shared with a member, or paused there (`workflows`' `startableVersion`: the fan-out's pauses, what holds over the workflow and the caller's own enablement's on that connection), so out of credits refuses it too (`OutOfCreditsError`), and while Google refuses the connection. A run is retried at most once (`runs_retry_of_run_id_unique`): asked again while its retry runs, it asks for that retry again rather than starting another, so a lost event or a second click starts nothing twice; a retry that fails is retried in turn. `checkRetry` says whether the caller may, and why not in the words `retryRun` refuses with, so the button is disabled with the reason. Like a manual run, a retry goes on while its connection does, whatever its switch. The run page links a retry and the run it retries both ways, and the Runs page marks a retry.
- **Alerts (M8, `features/alerts`)** tell admins in the app when something needs them; Mycel sends no email. `listAlerts(ctx)` and `countAlerts(ctx)` (admins only, `ForbiddenError` for members) work them out from current state on every read, so nothing is stored, nothing goes stale and there's nothing to dismiss: an alert goes away by itself once its cause is fixed. Each has a kind, a subject (the company's credits, a connection, or from #176 a workflow), a start time where Mycel records one, a sentence, what clears it and one fix link. The kinds, most urgent first: **credits out** (the balance at or below zero, as `isOutOfCredits` reads it; cleared by a grant), an **org connection or the admin's own needing reconnecting** (`needs_reauth`), its **backfill failed** (both from `connections`' `listConnectionsToFix`, which lists what the caller may reconnect; a reconnect clears either, the backfill once it's read again), and **credits low** (a runway under 7 days at the last 7 days' rate, `getRunway`). A colleague's own connection is theirs, shown on their Connections page. #176 adds workflows paused for failing and at their budget. `countAlerts` is a fixed four queries however many alerts are open (the runway's two, then the failed backfills and the connections to fix), since the app shell counts them on every page for admins: the Alerts item in the sidebar's Company group, with its count. The `/alerts` page lists them in one table grouped by urgency ("Stops everything", "Stops a workflow or an inbox", "Can wait a day"); a member following a link there lands on Reviews. While credits are out, the shell's banner slot shows admins an out-of-credits banner on every page. `alerts` imports other features' entry files, and no feature imports it (a dependency-cruiser rule).

## Builder chat (`features/builder`)

- Admin-only chat (not an agent, which is one person's own; see "Agent"). Its output is always a **proposal** for an admin to accept or reject, never a direct publish or an automatic merge. The same working spec can also be edited in a visual/JSON editor.
- **Builder conversations** belong to the org, record the admin who started one, and may be about one workflow. Any admin can open and continue any of the org's conversations; members get `ForbiddenError` on the page, the route and every `builder` function.
- **A turn** is `models`' metered chat turn (`streamChatTurn`, see "Models"): one `streamText` call on the `smart` role (resolved per org, invariant 6), at most 8 model steps, run by the streaming route `POST /api/builder/turn`, which resolves the session to `ctx` and calls `streamTurn(ctx, conversationId, message)`. `models`' `openMeteredStream` resolves the role and passes the credit pre-flight before the first model call; the turn sums each step's `providerMetadata.gateway.cost` and records one ledger entry, `purpose: "builder"`, when it ends, including a turn that fails partway (the failed step reports no cost; when its gateway error names a generation and no earlier step reported a cost, the failed-call job adds what it was billed, see "Credits"). Out of credits, no model is called, and the conversation and the stream get an `out_of_credits` notice. The turn runs to its end even if the page goes away, so its reply is still stored.
- **Context providers** (`builder/lib/context.ts`) are functions `(ctx, turn, actions) => { title, content }` called when a turn starts, given the company's action set resolved once for the turn, each a section of the agent's instructions: org settings, the action catalog (each action's app, description, inputs, outputs, fixed risk level and, for an external send, its pending form), the fields a condition may test (a classify step's answer, and an extract step's fields with the checks each declared type allows; trigger facts and catalog actions' result fields join it as they're declared), the org's workflows (each summarized with its branches' paths, and the conversation's workflow's whole working spec), the admin's own and the org's connections with their granted apps (other members' connections as a count only, ADR-0001), the registered apps a custom action may call, each with the admin's own and the org's connections to it and never another member's (`connections`' `registeredAppOf` maps a connection's source to its app), and tags, what became of the conversation's proposals, and company memory: up to 10 facts a memory search for the admin's message finds, in the company-wide view only (`builder/lib/search-memory.ts`, `searchCompanyWideMemory`, logged as `builder` with the admin as the person reading). Discovery's suggestions and mined patterns join in M2 as more providers.
- **Tools** (`builder/lib/tools.ts`) run with the admin's `ctx`, so the agent reaches only what the admin could. Each says what the conversation stores of its result. `get_workflow` reads the current working spec, hand edits included. `look_up_app_api` searches a registered app's published API description (see "Custom actions"). The instructions tell the agent to prefer catalog actions, to write a custom action only for one call to a registered app, found with `look_up_app_api` rather than guessed, and never for a job needing several calls, an unregistered app or a call the rule refuses; otherwise to say plainly what it can't do and file a capability request. `propose_spec({ workflowId?, spec, summary })` takes a whole spec, never a patch, v1 or v2 (a v1 spec, as an earlier conversation may replay, is upgraded and stored as v2), and validates it as saving would (`workflows`' `checkWorkflowSpec`: the schema, the policy engine, the org's connections and scopes) plus a spec ID no other workflow has. Its issues go back to the model to repair; after 3 failed calls in a turn it tells the model to stop and explain, and the admin sees the issues. A spec that passes is stored as a **proposal**; nothing else is. `read_examples` (`builder/lib/read-examples.ts`) runs a live Gmail search through runtime's `searchMessages` and `readMessage` on the admin's own connection or an org connection granted Gmail, and hands the model up to 5 messages' sender, date, subject and truncated body. Any other member connection, another admin's own included, is `NotFoundError` (ADR-0001), and the connections context lists exactly the IDs it accepts. `search_memory({ query, limit? })` searches company-wide memory only (`searchCompanyWideMemory` with reader `builder`), the view an org-credential run has, never the admin's own private mail, and hands the model the objects and facts found. Builder conversations are shared among admins and store the agent's replies and proposals whole, so a fact from one admin's private mail must never reach the agent (ADR-0023); the conversation also stores only the IDs of what was found, never what a fact says. Try it's `memory.lookup` on the admin's own connection reads in the admin's own view, but its result goes only to that admin's page, and the conversation keeps only Try it's content-free summary.
- **Capability requests** (ADR-0018; `custom-actions/lib/capability-requests.ts`): when one call can't do what the admin described, the instructions tell the agent to say plainly what it can't do, call `file_capability_request({ app, operation, inputs, outputs, reason, codeDraft? })`, and propose the rest only if it still makes sense. `app` is a registered app's ID (or name) or the free-text name of an unregistered app; the SDK checks the input against `custom-actions`' `capabilityRequestInputSchema` first, so a malformed request goes back to the model as an error and stores nothing. A request (`capability_requests`) is unique per org on its app and operation, both normalized (case and spacing), and each ask is a row of `capability_request_asks` naming its builder conversation and admin: asking again adds an ask, which raises the count and lists one more conversation, and the request's details become the latest ask's (an ask without a code draft keeps the earlier one). Its status (`open`, `building`, `shipped`, `declined`) and note are our team's: `setCapabilityRequestStatus` takes only the system ctx, which `pnpm capability-requests` (`app/scripts/`) acts as in each org to list every company's requests, show one with its code draft, and set a status (ADR-0009). Admins read their org's on the Capability requests page (`/capability-requests`); members get `ForbiddenError` and are sent home. Requests hold the agent's words and code, never source content (invariant 8), and no `connection_id`.
- **Proposals** (`builder_proposals`) hold the proposed working spec, the workflow it changes (none for a new one), the revision and working spec it was made against, what the policy engine made of it (max risk, inserted approvals), and a status: `proposed`, `accepted`, `rejected` or `stale`. The instructions (`builder/prompts/rules.prompt.yml`) describe branches, paths, conditions, first match, the otherwise path and the limits, and ask for a whole first version, then one change per proposal. The conversation shows each proposal as a card: the tree diff of base and proposal (`spec`'s `diffSpecs`: steps paired by ID within each list, paths by ID within each branch, a path changed when its name or condition is) grouped by path in plain words (`spec`'s `describeSpec` and `describeCondition`): the steps before any branch, then each path that changed or holds a changed step, under its name and condition (with its words before when it changed), listing only what changed (everything, for a new workflow), each step's catalog risk level, and "waits for review (required by policy)" on the approvals the engine inserted, which can't be removed. Accepting a new-workflow proposal creates the workflow unpublished and links the conversation to it; accepting one for an existing workflow saves its working spec with the base revision (`saveWorkflow`'s `baseRevision`), never its published version. The save, the decision and the link are one transaction, so a failure in any leaves the proposal `proposed` and nothing saved, and accepting it again works. A working spec saved since (by hand or by another proposal) has a newer revision, so the save throws `ConflictError`, the proposal becomes `stale`, nothing is merged, and the next turn's context ("Proposals in this conversation") tells the agent to propose again from the current spec. The conversation shows M3's Publish once the workflow's working spec differs from its latest version (`unpublishedChanges`).
- **The workflow editor** (`workflows/lib/spec-editor.tsx`, on the workflow page and New workflow) shows the working spec as a graph with its settings (spec ID, credentials, trigger labels, rung, budget), or edits it as JSON, switchable at any time; JSON that doesn't parse, or isn't an object with a list of steps (`spec`'s `readSpecJson`), can't switch back to the graph. The steps are edited on the graph (`workflows/lib/graph-editor.tsx`): clicking a step or a path opens a 360px side panel over the graph's right edge (a bottom sheet under 768px) whose fields change it in place, and "+" on a line opens a menu of the model steps, each catalog action grouped by its app with its risk level, and a branch, inserted where the line runs (the layout's `insert` on each line: its list and the step before it, past the reviews the policy engine inserts). Edits are `spec`'s ID-addressed tree edits (`spec/edit.ts`: insert a step into the root or a path, update or remove one, add, remove or move a path, set a branch's mode; inserting a branch moves the steps below it onto its otherwise path, and removing one moves its otherwise path's steps back where it stood and removes the steps on its named paths), and new steps and paths (`spec/new-step.ts`) get fresh IDs and blanks that validate. A branch's panel sets first or every match and orders its paths; a path's panel edits its name, all of or any of, and its checks, each offering only `policy`'s `checkChoices` for its branch (the classify answers and `testableFields` above it on its own path) with the operators its type allows. The graph draws once the steps are valid whatever the settings say (`readDraftTree`), and goes on drawing them as edited while an edit leaves them invalid; each issue shows on the box or path it's about (`issuesByTarget`). A debounced Server Action runs `checkWorkflowSpec` as the admin types, and its issues are listed with their paths; a spec with issues can't be saved. Saving passes the revision the editor opened, so a working spec saved since (by another admin or an accepted proposal) is refused with `ConflictError`, never overwritten.
- **The workflow graph** (`workflows`' `WorkflowGraph`) draws a valid spec top to bottom with React Flow. `spec`'s pure `graphView(spec, { action, insertedApprovals, proposal?, trace? })` builds a tree of view steps and view paths: each step's kind, one plain line (`describeStep`) and catalog risk level; the approvals the policy engine inserts (the graph runs `applyPolicy` itself, so they show as "waits for review (required by policy)"); each path's condition in words (`describeCondition`), left to right in the order they're checked, the otherwise path last; a proposal's changes, read from `diffSpecs`' tree diff (`spec/graph-changes.ts`), with removed steps and paths struck through where they stood and a step that moved drawn only where it went; and what a Try it ran (its steps, and each path's status and checks), read from a structural trace type the dry run's result satisfies, since `workflows` can't import `runtime`. `layoutTree(view)` places it as a tidy tree, with no layout library: each list a column, a branch's paths side by side, each as wide as its subtree, the same view always at the same positions. It opens at full size, shrunk to fit only when that keeps it at 90% or more, and otherwise at full size for the admin to scroll; zooming out is on its controls. On the workflow page, `workflows`' `GraphTraceProvider` wraps the editor and the Try it panel: the panel shows each result on the graph (`useShowOnGraph`), which lights up the steps that ran and says on each path why it did or didn't run. A graph can `fill` its parent's height, draw a `placeholder` under the trigger when there are no steps, and takes children drawn over it inside its frame (a caption, a panel sliding over its right edge).
- **The builder conversation page** (`builder`'s `BuilderWorkspace`) is a split screen: the chat on the left, and on the right the conversation's workflow's graph (its working spec; before the conversation has a workflow, the trigger and "Your workflow will appear here"). The newest waiting proposal is drawn on the graph as its changes to the spec it was made against (`Proposal.spec` and `baseSpec`), with a caption saying so; its card's "Show it on the graph" and "Hide it on the graph" toggle it, and Accept and Reject stay on the card (`builder/lib/proposal-on-graph.tsx`). A Try it from the chat lights up the graph through the same `GraphTraceProvider`, putting a shown proposal away until one is shown again; a new proposal, or a new working spec, puts the Try it away. Under 768px the split becomes two tabs, Chat and Workflow, both kept mounted, and the page turns to Workflow when a proposal or a Try it is newly shown. The working spec is edited on the graph here too (`workflows`' `WorkingSpecEditor`: the same side panel and "+", and a save bar under the graph once something changed, saving over the revision the page read). While a proposal is drawn the editor is hidden, its unsaved edits kept, so nothing is edited that's about to change. The conversation list is a column from 1024px, and a page of its own (`/builder`) below.
- **Try it** (`runtime`'s `dryRun(ctx, spec, { connectionId, sourceRef, workflowId? })`) runs a working spec on one message in memory: no Inngest, no `runs` or `run_steps`. It validates the spec as saving would and runs the policy-applied spec with the interpreter's own step executors, but with a dry action registry (`runtime/lib/dry-run-actions.ts`, typed so a new catalog action needs an entry): read actions run for real (`memory.lookup` in the view a run on the connection would have, logged as `builder`), and `add-label`, `append-row`, `create-draft`, `create-task` and `update-task` read only what they need and report what they would have done (the label, the row, the draft's recipient, subject and generated text, the task's title, notes and due date, or what would change on a task, which `update-task` reads first so an assigned task is refused here too), writing nothing. Approvals, the policy engine's included, are reported as "would wait for a review" and the run goes on. The connection must be the admin's own (member credentials) or an org connection (org credentials), granted Gmail; any other member's is `NotFoundError`. Out of credits it's refused before anything runs; each model call passes the usual pre-flight and its ledger entry is marked `dry_run`, with no run ID. The picker (`recentMessages`) lists each such connection's 20 newest inbox messages, their subjects and senders fetched through the proxy for display only, and only once the admin opens the panel (`?try`). The whole result goes back to the page and is never stored; it ends as a run would, `partly_failed` included, and a branch's entry lists its paths (`taken`, `not_taken`, `not_checked` after an earlier path ran, or `not_needed` for an otherwise path another path made unnecessary), each check in words with whether it passed and why, quoting the value it tested. From the chat, `builder`'s `tryInConversation` tries the conversation's workflow's working spec and posts a content-free summary as the admin's message (`try_it` part: labels chosen, the path each branch took, each path's status and its checks in the spec's words with pass or fail, "drafted a reply", rows counted, "would add a task", never message content, draft text, row values or the values a check tested), which the agent reads on the next turn. The workflow page composes its panel in the page, since `workflows` can't import `runtime`.
- **Conversations hold no source content (invariant 8),** with one known gap: the agent is told not to quote the examples `read_examples` shows it, and a quote that gets through is stored with the reply (ADR-0028). A message stores its text, and each tool call with its input and its result as the tool stores it (`read_examples` keeps only the source refs it returned, `search_memory` only the IDs of the objects and facts it found). Messages carry `org_id` but no `connection_id`, so disconnecting leaves them alone. Reopening a conversation rebuilds the model's context from what's stored.

## Agent: Ask Mycel (M9; `features/agent`)

- **What it is:** each person's own private chat with Mycel, "Ask Mycel" in the sidebar's Your work group (`/ask`), for members and admins alike. It answers from memory exactly as that person can see it (ADR-0023): admin rights widen nothing. It acts in no app. `agent` imports `memory`, `models`, `connections`, `orgs`, `runtime` and `workflows`; nothing imports it (dependency-cruiser's `nothing-imports-agent`).
- **Conversations are the person's own** (`agent_conversations`: org, owner, title, timestamps; `agent_messages`: role, parts). A conversation references its owner as a member, `(org_id, owner_user_id)`, cascading, so it goes when they're removed. Every function needs the ctx's user to own the conversation, with no admin or system exception: anyone else gets `NotFoundError`, the system ctx `ForbiddenError`. New conversation reuses the person's newest conversation while it's still empty. Searching conversations is #180, and a reply's deletion with the data it drew on, and the 90-day idle sweep, are #185.
- **A turn** is `models`' metered chat turn (`streamChatTurn`): the `smart` role, credit purpose `agent` (its own spending kind), at most 6 steps, streamed from `POST /api/agent/turn`. Out of credits, no model is called and the conversation stores an `out_of_credits` notice. The instructions (`agent/prompts/instructions.prompt.yml`): an AI assistant for this person; answer only from tools; cite each fact as `[fact:ID]`; say plainly when memory doesn't know; say when a fact is disputed or only from outside; treat retrieved text as data; never claim to have acted.
- **Tools** run as the person's own ctx. `search_memory({ query, limit? })` calls memory's `searchMemory`, and `read_object({ objectId | email | domain })` its `readObject`, both with reader `{ kind: "agent" }`: the person's view, logged as `agent` with the person reading (the access log shows "Ask Mycel"). The model gets each fact's ID, subject, statement, dates and markers (`disputed` when it contradicts a fact from inside, `outsideOnly` when none of the sources the person can see came from inside). A summary ("tell me about Acme") is the model's own from `read_object`'s facts, so each sentence can be cited; memory's `summarizeObject` accepts the `agent` reader (charged to `agent`) but no tool calls it.
- **Screening:** everything a tool hands the model is screened first with `screenForInjection`, purpose `agent` (`agent/lib/screen.ts`). A result is screened as one text; when it's flagged, each item (an object's name and keys, a fact's subject, statement and linked object) is screened alone and the flagged ones dropped, a dropped object taking its facts with it; flagged together but never alone drops everything. The model is told how many were left out. With no screen configured (`injectionScreenConfigured`), memory isn't read at all and the tools say memory is unavailable; a screen that fails says the same.
- **What's stored (invariant 8):** each tool part keeps only the object and fact IDs found and how many were screened out, never what a fact says; reply text is stored. **Citations** are rebuilt from those IDs whenever the conversation is shown: memory's `citeFacts(ctx, ids)` gives each fact's sources (with their item keys) and markers in the person's view now, never its words, and isn't logged again, since the facts were logged when the reply read them. Only facts the conversation's own tools returned are cited, so a guessed ID cites nothing, and a fact since deleted or no longer visible loses its footnote. A source in the person's own mailbox links to it there (`#all/<Gmail ID>` in that account); any other copy, a colleague's or an org inbox's, links by the email's Message-ID (`#search/rfc822msgid:<id>` in the person's own account), never the other mailbox's own ID; an email with no Message-ID in someone else's mailbox has no link. A Drive source links to the doc. A Calendar invite in the person's own calendar links to the event there (Calendar's `event?eid=`, the event's ID and the account's primary calendar, base64); a copy on someone else's calendar has no link.
- **Running a workflow on a message** (#182): the agent never acts itself. `propose_run({ workflowId, messageId })` (`agent/lib/pending-runs.ts`) checks what a run would need (`runtime`'s `checkRunFromAgent`: one of the person's own switched-on member workflows, not paused for any reason, on a message in their own mail, not already running) and records a **pending run** (`agent_pending_runs`: conversation, workflow, the person's member connection, `owner_scope`, `source_ref`, and `run_id` once started), cascading with its conversation, workflow and connection. Nothing starts. A refusal goes back as `{ proposed: false, why }` in the typed error's words, which the model relays. The conversation keeps only the pending run's ID or the refusal; the message's sender, subject and date are never stored (invariant 8) but fetched for display each time the conversation is shown (`runtime`'s `agentRunDetails`), with the run's status once it started. The card's **Run** button is a Server Action (`runPendingRunAction`, through `runFormAction`) calling `runPendingRun(ctx, id)`: only the conversation's owner may (anyone else `NotFoundError`), a pending run that started one already returns it (a second click starts nothing), and otherwise `startRunFromAgent` checks everything again and starts it (Runtime, "Runs from Ask Mycel"). The run's drafts wait on the person's Reviews page like any run's. The card then shows its outcome and links to the run's page (`/runs/<run ID>`), which says it was started from Ask Mycel, and to Reviews.
- **The page** (variant A of the prototype): the rail (titles, New conversation as a pencil icon button, delete, "Only you can see these"), the thread with footnoted answers, Disputed and Only from outside badges, and the composer pinned below with the AI disclosure. A turn's end refreshes the page for its citations.

## Memory (M14; `features/memory`; ADR-0022 to ADR-0025)

- **What it is:** objects (people, companies, deals, projects, documents), the links between them, and facts about them, in Postgres with pgvector. A fact is a short statement stated in a source or told by a person ("remember this"), linked to its source records; no source text is stored, and judgements are never stored.
- **Extraction:** the injection screen skips anything that tries to instruct a model, before any model reads it; `classify` skips newsletters, marketing, notifications and personal mail; facts are extracted from business items in Gmail, Drive docs and Calendar, within a monthly extraction budget per company. People outside the company keep work facts only. Admins set company-wide exclusions (labels, folders, addresses, domains); members can't switch memory off.
- **The settings page** (`/memory`, "Memory settings"; admins only: `getMemorySettings` and every write below are `ForbiddenError` for anyone else, and members are sent home) brings together the estimate and budget, exclusions, company-wide lists, the retention window, forgetting a person, and a link to the access log (`/memory/access-log`):
  - **Estimate and start:** nothing is learned until an admin starts memory (`learnFromItem` skips with `not_started`). `getMemorySettings` shows the estimate: the items discovery has stored that memory reads (`countStoredItems`: Gmail messages but drafts, and every stored version of each Google Doc, since each new version is learned again; Calendar invites aren't stored, and memory learns only those made or changed after it starts, so none is counted), times the most one item costs (two injection screens of the most text memory reads, since a doc is screened again before extraction, plus the `classify`, `fast` and `embed` credit estimates), so it's an upper bound. `startMemory(ctx, { monthlyBudget })` records the start with the budget (`memory_settings`, one row per org) and sends `memory/started`, whose job (`queueStoredItems`) pages through `listStoredItems` (the same items) and queues each as `memory/item.queued`, which the learning job takes like `discovery/item.stored`.
  - **Budget:** every model call and injection screen learning makes is tagged `purpose: "memory"` in the ledger. The budget caps learning only: a person's summary (below) is tagged `memory_summary`, so it neither counts toward the budget nor waits on it. Before learning an item, step one compares this calendar month's (UTC) tagged spending (`getSpending`) with the budget; once it's reached, the item is postponed (`memory_postponed_items`, a pointer cascading from its connection, with its `reason`: `budget`) and skipped with `postponed`, so the item in progress may take spending past the budget by one item's cost. An item is also postponed, not lost, when either step finds the org out of credits (`OutOfCreditsError` from any model call or screen: reason `credits`), or when the injection screen still fails (`InjectionScreenError`) on the learning job's last attempt (reason `screen`; earlier attempts throw so Inngest retries). On the 1st of each month a cron sends `memory/postponed.due` for every org, and so does `setMemoryBudget`; its job (`resumePostponed`) queues the postponed items again, every reason, and any still stopped are postponed again. Granting credits (`pnpm credits:grant`, after `grantCredits`) sends `credits/granted`, whose memory job resumes the `credits` items, and `memory-retry-screen-hourly` (minute 15 of every hour, UTC) sends `memory/postponed.due` naming `screen` for every org.
  - **Exclusions** (`memory_exclusions`): a Gmail label (by name, matched regardless of case, since each mailbox has its own label IDs), a Drive folder (by ID, or pasted as its link; folders under it count too), an address, or a domain (subdomains included). Step one skips an item an exclusion covers (`excluded`) right after reading it, before any model call: an address or domain on an email's From, To, Cc or Bcc or on a doc's sharing list, a label the email carries (read from that mailbox's `labels.list`), or a folder the doc is in, followed up through each folder's `parents` (`files.get` with `fields=parents`); a doc's older versions on that connection go too. Adding one sends `memory/exclusion.added`, whose job (`forgetExcluded`) deletes the source records it covers: for an address or domain, those whose access list names a matching address; for a label, each connection's learned messages that Gmail lists under the label now; for a folder, each connection's learned docs that are in it, or under it, now. The cascade and migration 0026's triggers then remove each fact left with no source and each object left with no fact; a fact another item still supports stays. Removing an exclusion lets new items be learned again; what it kept out stays unlearned. The forgetting and resuming jobs share the learning job's one-at-a-time-per-org concurrency key, which Inngest applies to executing steps, not whole runs: an exclusion's job can run between an item's two learning steps, so step two checks the exclusions again (`excluded`) before any extraction, and nothing an exclusion covers is stored.
- **Matching** (`memory/lib/match.ts`, after embedding and before the store transaction): an object the item states is the object with one of its exact keys (email, domain; CRM ID and file ID later). Otherwise up to three **match candidates** of its kind are found in the org: objects with a similar name (pg_trgm trigram similarity, at least its 0.3 threshold, through a GIN trigram index; migration 0030 adds the extension) first, then the subjects of current facts whose stored embeddings lie within cosine similarity 0.75 of a fact the item states about it. A `fast` call confirms or rejects each, best first, seeing only both sides' names, keys and short fact statements, never the item; the first it confirms is the object (given the keys it lacked), and with none confirmed it's a new object. A similar name alone never merges, and each confirmation is a model call with its credit check and ledger entry (invariant 7). Every query runs through `forOrg`, so nothing is matched across companies.
- **Tables** (`memory/lib/schema.ts`): a **source record** (`source_records`) is one item as one connection holds it (an email, a Drive file version or a Calendar invite version), with `org_id`, `connection_id`, `owner_scope` and owner, the app, its `source_ref`, an item key shared by every copy of the item (an email's `Message-ID`, a Drive file's ID), when it happened, when its access was last read, and whether it came from inside the company (`from_inside`: an email the mailbox holding it sent, or a doc a colleague at the Workspace domain owns). Its **access list** (`access_list_entries`) is one row per principal: an `address` (a person's or a group's), a `domain` or `anyone`, each `confirmed` or not. Only confirmed entries widen who sees the record: a doc's sharing list as Drive gives it, for an email the address of the mailbox holding the copy and, when that copy is one the mailbox sent, everyone on it; and for an invite the calendar holding the copy and, when that calendar's account organised it, everyone on it. The rest of an email's addresses (From, To, Cc, and Bcc as its headers say) are kept unconfirmed, for exclusions only (Outside senders, below). **Objects** (`memory_objects`: kind and name) and their exact **object keys** (`object_keys`: `email`, `domain`, unique per org) belong to the org. A **fact** (`facts`) has a subject object, a short statement, optionally a predicate with a value or a linked object, valid time (`valid_from`, `valid_until`) and recorded time (`recorded_at`, `superseded_at` with `superseded_by_id`), the fact it contradicts when it was stated only from outside (`conflicts_with_id`, Time below), an origin (`source`, or `told_by` for M9's "remember this"), a 1536-dimension embedding (the `embed` role's default model; HNSW, cosine) and a generated `tsvector` with a GIN index. `fact_sources` links each fact to the source records that support it. Source records, access lists and links cascade from the connection; two triggers (migration 0026) delete a `source` fact when its last link goes and an object when no fact is about it or links to it, so any deletion of a connection removes what only it taught, in the same transaction.
- **Learning from Gmail** (`learnFromItem`, called by `memory/jobs.ts` on `discovery/item.stored` as the org's system ctx, one item at a time per org so two items never race to create one key): step one skips everything before memory started and postpones it once the month's budget is spent (above), skips an item already learned on that connection, fetches the message through the proxy (held in memory only), skips it if an exclusion covers it or its sender is on the do-not-learn list (`forgotten`, below), and, if another copy under the same item key taught facts already, links this copy's new source record to them with no model call; otherwise the injection screen checks the message's text (below), and only text it passes goes on to `classify` (`business` or not). An item it flags is skipped (`skipped`, reason `flagged`), and so is every item when no screen is configured (`unscreened`), so no model reads unscreened content. Gmail never changes a message, so step two's second fetch is the text the screen saw. Step two, for business mail, fetches the message again and asks `fast` for objects and facts as structured output, the email marked as data, never instructions. Each answer is checked against the email before anything is stored: an object's email address must be on the email and its domain in it (webmail domains give no company key), each fact must quote the email word for word (the quote is never stored), a statement is at most 280 characters and never copies eight or more of the email's words in a row (it would be source text, invariant 8), and a personal fact about anyone but a colleague (a person at the org's Workspace domain) is dropped. The kept statements are embedded (`embed`) and the objects matched (above); a fact with the same subject and statement as a current fact links to it instead of duplicating it, and a new fact takes its place in its timeline (Time, below). The source record, its access list, objects, keys, facts and links are stored in one transaction. Every model call goes through `models`, so it passes the credit check and leaves a ledger entry, tagged `memory`.
- **Learning from Drive docs** (the same `learnFromItem` and steps, `memory/lib/drive.ts`): memory reads only Google Docs (`application/vnd.google-apps.document`); any other file (Sheets, Slides, PDFs, images, uploaded text files) is skipped (`unsupported`) with no model call. A Drive `source_ref` is `<file ID>@<modified time>`, one per version, and the item key is the file ID. Each step reads the file's metadata with its sharing list (`files.get` with `fields=id, mimeType, modifiedTime, trashed, parents, owners(emailAddress), permissions(type, emailAddress, domain, deleted)`, its `parents` for exclusions and its `owners` for whether it came from inside the company, never its name) and then its text (`files.export` as `text/plain`, through `connections`' `proxyGetText`, held in memory only, the first 24,000 characters). A version that's no longer the file's current one is skipped (`outdated`): its newer version has its own `discovery/item.stored`. A doc can change between the two steps, so step two screens what it read again before `fast` reads it. The sharing list becomes the access list: people and groups (`user`, `group`) as `address`, `domain` as `domain`, `anyone` as `anyone`, owners included. **Drive shows a file's `permissions` only to an account that may share it** (an owner, or a writer while writers may share); read through anyone else's connection a doc has an empty access list, so only people whose own Drive holds it see what it taught. `classify` asks whether a doc is about the company's work (`business`, `personal`, `template` or `other`), and extraction is the email's, with the doc as the data. A copy of the same version in another connection's Drive (same `source_ref`) takes the facts its first copy taught with no model call, as a Gmail copy does; a copy at another version is learned on its own. A connection keeps only the latest version it decided on: storing a newer one, or skipping it as not business, flagged or stating nothing, deletes that connection's records of older versions, and with them the facts only they supported; an older version arriving later is `known`.
- **Learning from Calendar invites** (ADR-0029; the same `learnFromItem` and steps, `memory/lib/calendar.ts`): memory has no stored events to learn from (Calendar isn't a discovery source), so runtime's Calendar poll (Workflows, "The Calendar trigger") runs for every connection granted Calendar once memory has started (`hasMemoryStarted`), and from each incremental listing sends `calendar/event.changed` (`app: "calendar"`, `sourceRef` `<event ID>@<sequence>`, `occurredAt` its `updated`) for every ordinary event made or changed (`eventType` `default`: not one Gmail added from an email, nor focus time, out of office or a working location) and `calendar/event.removed` (`itemId`, the event ID) for every one cancelled, each event ID naming the token it listed from. The learning job takes `calendar/event.changed` like `discovery/item.stored`, and the access re-read takes it too (below). A full sync (the first poll, or after a `410`) tells memory nothing, so past invites aren't learned. Each step reads the event (`events.get` with `fields=id, status, sequence, updated, iCalUID, recurringEventId, originalStartTime, eventType, summary, description, location, start, end, organizer(email, self), attendees(email, self, resource)`), and the text a model reads is its title, organizer, guests, times, place and the first 8,000 characters of its description, held in memory only. One that's gone or cancelled is `gone`; one with no one on it but the calendar's own account (an event of the person's own) is `unsupported`, with no model call; one whose `sequence` is past the version's is `outdated`, since its newer version has its own event. **Versions:** `sequence` goes up when the organizer changes what the event says, not when a guest answers, so each sequence is a version, learned again and replacing the connection's older ones (with the facts only they supported), as a Drive doc's versions do; an edit that leaves it alone (Google doesn't document which) teaches nothing new until one that doesn't. The item key is the iCalUID (plus the original start time of an instance of a recurring event, since every instance shares the series' iCalUID), and a copy on another calendar at the same sequence takes the facts its first copy taught with no model call. **Access list** (Outside senders, below): the address of the calendar holding the copy and, when that calendar's account organised the event (`organizer.self`), everyone on it (rooms aside), and only then is it from inside the company; otherwise the organizer and guests are kept unconfirmed, for exclusions, and each guest sees its facts once their own calendar holds a copy. The organizer counts as its sender for the do-not-learn list. `classify` asks whether it's a meeting about the company's work (`business`, `personal` or `other`), and the extraction, told that an invite's meeting is itself a fact (who meets whom, when, about what), is the email's, with the invite as the data.
- **The injection screen** (`models`' `screenForInjection(ctx, { text })`): Google's user data policy (updated 2026-09-03) requires apps on restricted scopes to protect against prompt injection "by either using Google Cloud Platform's Model Armor or other prompt injection protection", so content fetched for a model is screened before any model reads it. The service is **Google Cloud Model Armor**, called as `POST https://modelarmor.<location>.rep.googleapis.com/v1/<template>:sanitizeUserPrompt` with the text as `userPromptData.text`; only the prompt-injection and jailbreak filter's result is read (`filterResults.pi_and_jailbreak.piAndJailbreakFilterResult`: `MATCH_FOUND` flags, and a filter that didn't run fails the call rather than passing the text). Why Model Armor:
  - the policy names it, which makes the restricted-scope assessment simplest;
  - it costs $0.10 per million tokens after 2 million free a month, about $0.0003 for a 12,000-character email (Azure AI Content Safety's Prompt Shields, the runner-up, charges $0.375 per 1,000 records of 1,000 characters, about $0.0045, though its `documents` field is built for indirect injection in emails; Lakera Guard publishes no price);
  - it takes 65,536 tokens a request, far above the 12,000 characters memory reads of an email or the 24,000 of a doc, and 1,200 requests a minute per project;
  - it fits Vercel with no stored key: Workload Identity Federation trusts the Vercel project's OIDC token (`@vercel/oidc`), which Google's Security Token Service swaps for a federated token and IAM Credentials for a short-lived token of a service account holding `roles/modelarmor.user` (`models/lib/google-cloud-token.ts`, which keeps it until five minutes before it expires).

  It sits behind a small interface (`InjectionScreen` in `models/types.ts`: a service name, a cost estimate and `isInjection(text)`), so another service can replace it. It's metered like a model call (invariant 7): the credit check first, with the text's estimated cost (four characters a token at list price, since Model Armor reports no token count, and the free tier belongs to Mycel's project, not an org), then one ledger entry with no role and `google/model-armor` as its model (a failed call records 0). Failures throw `InjectionScreenError`, built from codes only. Configuration is `MODEL_ARMOR_TEMPLATE` (the template's full resource name), `GCP_WORKLOAD_IDENTITY_PROVIDER` and `GCP_SERVICE_ACCOUNT_EMAIL`, all optional at startup; with none, the verdict is `unavailable` and memory learns nothing. The text is sent in the request and held nowhere else (invariant 8): the template's logging must stay off, since Model Armor's sanitize-operation logs write "the full payload, such as the prompt or response text" to Cloud Logging. Its tests reach a fake Model Armor (`src/testing/fake-model-armor.ts`), which also plays the token exchange and flags text holding a phrase a test names. Sources, read 2026-10-21: [the policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy), [Model Armor's API](https://docs.cloud.google.com/security-command-center/docs/sanitize-prompts-responses), [pricing](https://cloud.google.com/security/products/model-armor#pricing), [limits](https://docs.cloud.google.com/model-armor/quotas), [logging](https://docs.cloud.google.com/model-armor/configure-logging), [Vercel to Google Cloud](https://vercel.com/docs/oidc/gcp), [Prompt Shields](https://learn.microsoft.com/en-us/azure/ai-services/content-safety/concepts/jailbreak-detection) and [its pricing](https://azure.microsoft.com/en-us/pricing/details/cognitive-services/content-safety/).

- **Following the apps** (ADR-0023, ADR-0024; `memory/lib/source-changes.ts`, all as the org's system ctx, sharing learning's one-at-a-time-per-org concurrency): `discovery/item.removed` and the Calendar poll's `calendar/event.removed` run `deleteRemovedItem`, which deletes that connection's source records of the item (a Gmail message by its ID, every version of a Drive file by its file ID, every version of a Calendar event by the event ID its `source_ref` starts with); migration 0026's triggers then delete the facts left with no source and the objects left with no facts. A colleague's copy of the same email or doc keeps its own record, so a fact another source supports survives. `discovery/item.changed` runs `rereadAccess`, which, when the connection holds a record of the file, reads its sharing list again (`files.get`, the same `fields` as learning, never the export) and rewrites the access lists of the connection's records of it, setting `access_checked_at`; a file Drive no longer gives the account (404, or trashed) has its records deleted as if removed. `calendar/event.changed` runs it too: when the connection holds a record of the event (any version), it reads the event's organizer and guests again (`events.get` with `fields=status, organizer(email, self), attendees(email, self, resource)`) and rewrites the access lists the same way, so a guest added, removed or answering costs no model call; an event gone or cancelled has its records deleted. Read through an account that may no longer share the file, the list is empty, as when learning. `memory-reread-access-nightly` (04:30 UTC nightly, `rereadAllAccess`) is the backstop: for each org it re-reads every Drive and Calendar record not re-read since the run began (a Calendar change hidden by an expired sync token included), 100 records a step, keyed by record ID so each is visited once, skipping connections that need reconnecting until the next night. Gmail messages never change who is on them, so only their deletions are followed; a message in the trash also reads as gone when learning, so one trashed before memory reads it is never learned.
- **Visibility** (`memory/lib/visibility.ts`, the one rule every read uses, written as SQL so a search filters by it before it ranks or limits anything): a viewer sees a source record when their own member connection holds the item (that copy, or another copy under the same item key, so for a group that isn't marked only members whose own mailbox or Drive holds the item count), when its confirmed access list names their address, or when it's company-wide: from an org connection, or with a company-wide list, the org's Workspace domain (a doc shared with the company) or `anyone` (a doc shared with anyone who has the link) on its confirmed access list. Only the Workspace domain counts as the company's: a viewer's own address at another domain widens nothing. A fact is visible when any of its source records is, and an object when any of its facts is; admin rights widen nothing, and the system ctx (an org-credential run) is no one, so it sees only company-wide sources.
- **Outside senders** (review of M14, finding 1): anyone can email the company and write any address in an email's headers, so an outsider who mails one member and puts all@ or a colleague on Cc must not reach everyone, or that colleague, through memory. An email's access list is therefore only what Mycel itself saw (`memory/lib/gmail.ts`): the address of the connected mailbox holding the copy, and, when that copy carries Gmail's `SENT` label (which only the mailbox's owner can cause), everyone on it, since one of the company's own people chose them. Anyone else an inbound email names counts once their own connected mailbox holds a copy (the held-copy rule above), and a company-wide list only through an email a colleague's mailbox sent to it, or a copy in a mailbox at the list's address (connected as an org connection, it's company-wide anyway). An inbound email whose `From` is at the company's domain is still treated as from outside unless the sender's own sent copy is learned: `From` is as easy to forge as `Cc`. The headers' other addresses are kept unconfirmed, so excluding an address still finds every email it was on. A Calendar invite follows the same rule (ADR-0029): its organizer wrote its guest list, so the calendar holding the copy counts, and everyone on it only when that calendar's own account organised it (`organizer.self`); each other guest counts once their own calendar holds a copy. An org connection such as support@ stays company-wide by design, and what an outsider tells it is kept from overwriting the company's facts by the superseding rule (Time, below). Migration 0037 marks every email access list entry learned before it unconfirmed; each mailbox's own copies still count.
- **Company-wide lists** (`company_wide_lists`: a lowercased address per row, an org setting with no connection): admins mark group addresses such as all@ on the settings page (`markCompanyWideList(ctx, address)`) and take the mark off with `unmarkCompanyWideList`, and list them with `listCompanyWideLists` (all `ForbiddenError` for anyone else). Only an address at the org's Workspace domain that isn't a user's own can be marked (`ValidationError` otherwise), since marking a person's address would show everyone their mail; a marked address that later becomes a user's own stops counting as a list. Marking and unmarking take effect on the next read: nothing is copied. An email with no `Message-ID` gets an item key of its own connection and Gmail ID, so no other mailbox's copy can match it.
- **Reading:** `readObject(ctx, { id } | { key: { kind, value } })` returns the object, its keys, its facts current for the caller and its `history` (below), each with its linked object and only the sources the caller can see (app, connection, `source_ref`, time). An object with no visible fact, or in another org, is `NotFoundError`.
- **Searching** (`searchMemory(ctx, { text } | { key: { kind, value } }, limit?)`, `memory/lib/search.ts`): the facts current for the caller (Time, below), best match first (20 by default, at most 50), each with its subject, linked object and visible sources, and the objects they're about. It makes **no model call, so the query is never embedded**: embedding it would be an `embed` call with a ledger entry, and searches must be fast and free. Instead it fuses three ranked lists by weighted reciprocal rank: **keywords** (the facts' `tsvector` index matched against any word of the text, English stemming), **links** (facts about or linking to the objects the search names, by an exact key, given or found in the text as an email address or domain, or by a word of their name) and **meaning** (for a text search, the facts closest by stored embedding, cosine similarity at least 0.5, to the best three facts the first two lists found, so a fact that shares no word with the text but means the same as a match is found too). Facts about an object named by its exact key come first. Each list's query applies the visibility rule before it limits its candidates (100 per list, 10 neighbours per seed), so a fact the caller can't see never shows, crowds out, pulls in or pushes down one they can, however many of them match. A fact the text reaches by meaning alone, with no keyword, key or name match anywhere, isn't found; a query embedding would find it, and joins when a caller can pay for one.
- **The access log** (ADR-0024; `memory/lib/access-log.ts`, table `access_log_entries`): `readObject` and `searchMemory` take a third argument naming the reader, `{ kind: "person" }` by default, `{ kind: "builder" }` for the builder chat's admin, `{ kind: "agent" }` for a person's Ask Mycel, or `{ kind: "workflow_run", runId, workflowId }`; the ctx stays whose view is read (a member-credential run passes its member's ctx, an org-credential run the system ctx). `searchCompanyWideMemory(ctx, search, reader?)` searches in the system ctx's view whoever the ctx is, and logs the read with the ctx's user as the person reading: the builder chat's reads. Every search, and every object read that finds something, writes one entry: the reader's kind (`person`, `builder`, `agent`, `workflow_run`, `staff`, or `system` for a system ctx that names no reader), the user whose view was read, the run and workflow or the staff consent, the operation, and the IDs of the objects and facts returned, never the query or what a fact says. It also records whose member connections held a source of a fact read (`source_owner_ids`, GIN-indexed), so it still answers after the facts go. `listAccessLog(ctx)` gives an admin the company's 200 newest entries and a member those that read a fact from their own sources; each object's name shows only if the viewer can see one of the facts read about or linking to it (the visibility function again), so the log widens no one's view, and the system ctx is `ForbiddenError`. The log has no `connection_id`: it isn't derived from a source, and outlives the facts it names. Entries are kept for 365 days (`ACCESS_LOG_RETENTION_DAYS`; ADR-0024 asks for at least 90): `memory-prune-access-log` runs `pruneAccessLog` for each org at 04:00 UTC, which also deletes staff consents that expired before then.
- **Summaries** (`summarizeObject(ctx, { id } | { key }, reader?)`, `memory/lib/summarize.ts`): the object read as above (logged as the reader named; `NotFoundError`, with no model call, when the caller can see no fact about it), then one `fast` call over its visible facts, marked as data, which passes the credit check and leaves a ledger entry charged to the reader: a workflow run's to its run, the builder's to `builder`, and a person's to `memory_summary` (memory's on the Credits page, outside memory's budget). It returns the object, the summary and how many facts it was built from, and stores nothing.
- **Using memory:** workflows read it through the `memory.lookup` catalog action (see "Writes are idempotent per step" under Runtime), the builder through its memory context section and `search_memory` tool, in the company-wide view only, since builder conversations are shared among admins, and each person's agent in their own view (see "Agent"). `runtime`, `builder` and `agent` import `memory`'s entry files; `memory` imports none of them.
- **Staff consent** (`memory/lib/staff-consent.ts`, table `staff_consents`): our staff read memory only under a consent an admin gives for one case (`grantStaffConsent`: the person at Mycel by email address, the case, 1 to 30 days), which any admin can revoke at once. `staffReadObject` and `staffSearchMemory(ctx, { consentId, staffEmail }, …)` run as the org's system ctx (our tooling, never a person in the org) and read in the view of the admin who gave the consent, so staff never see more than that admin can; a missing, revoked or expired consent, another staff member, or an admin who has left or lost the role is `ForbiddenError`. Each staff read is logged as `staff` with its consent, so admins, and members whose sources it read, see who read under which case. The page is `/memory/access-log`: everyone sees their part of the log, and admins also give and revoke consents there (the full memory settings page is #115).
- **Time** (`memory/lib/supersede.ts`): facts about one subject with one predicate form a **timeline**, since the extraction gives a predicate only for something its subject has one value of at a time (role, renewal_date). Facts without a predicate are never superseded. A timeline is ordered by when each fact became true: its `valid_from`, else when the first item stating it happened, so an older email learned after a newer one (backfills read newest first) goes into history rather than over the newer fact; on a tie the new fact is the newer. Once an item's facts are linked to its source record, storing them (or linking another copy) relinks each timeline they're in: each older fact gets `superseded_at` (when memory recorded it as replaced), `superseded_by_id` (the next one) and `valid_until` (the next one's `valid_from`, when it says), and stays as history; the newest is current. `superseded_by_id` has no foreign key: when a fact is deleted, a trigger (migration 0032) points whatever it replaced at its own first surviving replacement, or makes it current again when none is left, so deleting a connection never leaves a gap or a fact replaced by nothing. **Who stated a fact counts:** a fact stated only from outside the company (none of its source records is `from_inside`) never supersedes one that a source from inside, or a company-wide source (an org connection, a company-wide list, the Workspace domain or `anyone` on its confirmed access list), supports. Both stay current, and the outside fact records the one it contradicts (`conflicts_with_id`; readers get it as `conflictsWith`, only when they can see that fact), so a stranger's email to a member or to support@ shows as a conflict rather than replacing the company's fact. An outside fact still supersedes an older one that only private, outside sources support (the same customer writing again), and a fact from inside supersedes anything older. **Superseding is per reader** (ADR-0023, each person's own view): a fact is history for a reader only when a newer fact in its timeline is one they can see (`visible-facts.ts`, `overTime`); one replaced only by facts they can't see stays current for them, with no end time, so it never hints at what they can't see. `readObject` returns history as `HistoricFact`s (`supersededBy`: the newer fact they can see; `supersededAt`), and search ranks only the facts current for the caller.
- **Reading:** stored embeddings, keyword search and object links, with no model call. Summaries are built per person when asked, from the facts that person can see. Apps whose terms ban stored indexes, such as Slack, are searched live and never stored (ADR-0025).
- **Retention** (ADR-0024; `memory/lib/retention.ts`): each org has a retention window (`memory_settings.retention_months`, 24 by default; `setRetentionWindow(ctx, { months })` shortens it to 1 to 24 whole months, admins only, once memory has started, else `ConflictError`). Every night at 03:30 UTC `memory-retention-nightly` sends `memory/retention.due` for every org, and its job (`applyRetention`, as the org's system ctx, sharing learning's one-at-a-time-per-org key) deletes the source records whose item occurred more than the window ago (calendar months, UTC). The cascade and migrations 0026 and 0032's triggers remove each fact left with no source, superseded history included (relinking what's left), and each object left with no fact; a sweep then deletes any learned fact still without a source and any object still without a fact. A fact another, newer item still supports stays. A shortened window applies on the next night's run. A `told_by` fact (M9) has no source and isn't touched.
- **Forgetting a person** (ADR-0024; `memory/lib/forget.ts`): `forgetPerson(ctx, { email })` (admins only) puts a keyed hash of the lowercased address (`hashForOrg`) on the do-not-learn list (`memory_do_not_learn`: `org_id`, `address_hash`, `forgotten_at`; never the address), then deletes, in one transaction, the objects whose email key is the address. Their facts, those about them and those linking another object to them, go by the facts' cascading foreign keys, embeddings included, and the triggers remove objects left with no fact and relink history. Source records stay: they're pointers, and what else their items taught still stands. It returns only how many facts went, and the settings page shows only that and how many people were forgotten. Learning checks the list without the address: step one skips an email whose From is on it (`forgotten`) before any model reads it, and the extraction step drops any object keyed by a listed address with every fact about it or linking to it, so other people's mail doesn't rebuild them. While the list is empty nothing is hashed. An item already being learned may have checked the list just before; so forgetting also sends `memory/person.forgotten` with the address encrypted for the org (`encryptForOrg`, never plain in Inngest), whose job (`forgetPersonAgain`, the system ctx, on the per-org key) runs once that item is stored and deletes the objects keyed by the address again. Forgetting is by address only: it removes the person's objects keyed by their address, with their facts, and blocks future mail from that address. It doesn't remove facts or objects that name them without their address (a person object the extraction made from a name alone, or a fact about someone else whose statement names them), and later mail that names them without their address can teach memory about them again. The address itself also stays where it's a pointer or a setting outside memory's facts: source records' access lists, discovery's events, and an exclusion an admin added.

# Memory reads Calendar through the trigger's poll, and trusts only what Mycel saw

Memory learns from Calendar invites (ADR-0022), but Calendar isn't a discovery source (ADR-0008, M11), so nothing stores its events for memory to learn from, as discovery does for Gmail and Drive. The Calendar trigger (#70) already polls a calendar every minute with Calendar's sync token. So that one poll also serves memory: it runs for every connection granted Calendar once memory has started in the org, not only for those with a Calendar-triggered workflow switched on, and keeps its one sync token per connection. From each incremental listing it sends `calendar/event.changed` for every ordinary event made or changed (its version as `<event ID>@<sequence>`) and `calendar/event.removed` for every one cancelled, and memory learns, re-reads who may see it, or deletes what it taught, as it does with discovery's events. An invite is learned like an email: the injection screen, `classify`, the same extraction, matching and storing, and only its pointers, item key and access list are kept, never its title or description (invariant 8). We chose this over memory running its own Calendar poll, which would list every calendar twice a minute and keep a second token for the same feed, and over making Calendar a discovery source, which ADR-0008 still gates.

## Considered options

- **Memory's own poll and cursor.** Rejected: two pollers per calendar, each a call a minute, and two tokens that must each recover from a `410`.
- **Calendar as a discovery source**, storing events for memory as Gmail and Drive do. Rejected: ADR-0008 keeps Calendar out of mining until the discovery-lens experiment asks for it, and memory needs no stored event.
- **Everyone on an invite on its access list.** Rejected for an invite someone outside organised, for the reason ADR-0023 gives for email headers: its organizer wrote that list. An invite from an `.ics` email, or one from an outsider who names all@ or a colleague, would reach people Mycel never saw it reach.

## Consequences

- **Access list:** the calendar holding the copy, and, when that calendar's own account organised the event (`organizer.self`, which only its owner can cause, like Gmail's `SENT`), everyone on it, since a colleague chose them; that copy also counts as from inside the company. A guest on an invite someone else organised sees its facts once their own connected calendar holds a copy (the held-copy rule). The other addresses are kept unconfirmed, for exclusions only. So an invite's facts reach its organizer and guests, and no one else. Copies match on the iCalUID, which the organizer sets, an accepted risk between colleagues like the Message-ID's (ADR-0023).
- **Versions:** an event changes. Its version is its `sequence`, which goes up when its organizer changes what it says, and not when a guest answers. A new sequence is learned again, and that connection's older versions go with the facts only they supported. A changed event at the same sequence (an answer, a guest added or removed) costs no model call: memory reads its guests again (`events.get`) and rewrites its access lists. A copy on another calendar takes the facts its first copy taught only at the same sequence. Google's documentation doesn't list which edits raise `sequence`; one that doesn't (a description edited alone, perhaps) leaves the older facts until the next edit that does.
- **What memory reads:** ordinary events with guests (an event of the person's own, with no one invited, is `unsupported`, with no model call); not ones Gmail added from an email, which memory learns from the email, nor focus time, out of office or working locations.
- **No backfill:** the first poll, and the poll after a `410`, is a full sync that tells memory nothing, as it starts no runs. Memory learns invites made or changed after it starts; past invites aren't learned, and memory's estimate counts none.
- **Deletion:** a cancellation is followed from the poll, a deleted connection takes every source record by the cascade (invariant 3), and the nightly re-read of access (`rereadAllAccess`, Drive's until now) also reads every Calendar record again, which catches what a `410` hid.
- **Cost:** every connection granted Calendar is polled every minute once memory has started, as discovery polls Gmail and Drive. It can move onto `events.watch` with ADR-0026's push.

# A change and the events it sends are saved together

Several Server Actions save a change and then send its Inngest event: renaming, deleting and unassigning a tag, starting a run by hand, and memory's start, budget, exclusion and forget actions. When the send fails, the change is already saved, and retrying the action sends nothing: the rename finds the name already changed, the delete finds no tag, and a retried run starts a second run while the first stays "running" forever. So such an action writes its events to an **outbox** table in the same transaction as the change, sends them right after the commit, and deletes them once Inngest has them. A job every minute sends whatever is left. Every event then reaches Inngest at least once, under a fixed event ID, so Inngest drops a copy it has seen in the last 24 hours, and every function an event starts must be idempotent: handling it twice changes nothing the first time didn't. We chose an outbox over making each action re-send when retried, because that relies on a person retrying, and a retry often can't tell its earlier send failed. We chose it over sending inside the transaction, before the commit, because Inngest can start the function before the commit lands; the function then finds nothing, and a run it can't find it skips, leaving the run "running".

## Consequences

- **The outbox** is a tenant table: `org_id`, the event's name, its data and ID, and when it was written. Event data are IDs and names, never content (invariant 8); the event's Zod schema checks them when they're written and again when they're sent.
- **Sending:** the outbox is the one place a Server Action or server function sends events. Two kinds of send stay as they are. Inngest functions send with `step.sendEvent`, which Inngest already retries. Connections' webhook handlers send before they settle the attempt, so Nango redelivers a webhook whose send failed (`connections/lib/record.ts`, `reauth.ts`). Lint bans `inngest.send` everywhere else.
- **Every event has an ID.** Tag events have none today and get one, derived from the change (the tag and its revision, the assignment), so the outbox's send and the job's send of the same event are one event to Inngest.
- **The job** lists the orgs with waiting events (a cross-org read, like `listOrgIds`, ADR-0009) and sends each org's in its own step as that org's system ctx. It sends only events more than a minute old, so it doesn't race the action's own send; a race would be harmless anyway.
- **Delay:** none normally. When the send right after the commit fails, the event goes out within about two minutes.
- **Runs stuck "running":** the outbox covers a run whose event was never sent, and #170 covers a run whose job crashed. Neither covers Inngest losing an event it accepted; we don't guard against that.
- **The functions these events start** are already idempotent: following a tag rename rewrites working specs to the tag's current name, removing enablements a user lost sight of removes only what's still there, and a run that isn't "running" any more is skipped. A new event's function must be too.

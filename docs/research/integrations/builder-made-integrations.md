# Builder-made integrations: facts for the design discussion

Researched 2026-10-21. The product owner wants **the builder chat to create integrations itself, even for apps with no catalog actions**. That reverses invariant 5 ("Specs, not code … Integration code is written by our team") and intent non-goal 4 ("The builder chat never writes code"), and puts pressure on invariant 4 (only the catalog decides risk), invariant 8 (no stored content) and ADR-0013 (every `external_send` waits in the app's own pending form). Today's escape hatch is the `capability_request` queue (docs/architecture.md, "Capability requests"), whose interface was kept stable "so an auto-builder can take over later".

Primary sources only; every claim links to one. "Unverified" means the docs were silent or I could not reach them.

## 1. Auth for arbitrary apps via Nango

**Coverage.** Nango's machine-readable catalog lists **1,059 providers** ([api-catalog.txt](https://nango.dev/docs/api-catalog.txt), fetched 2026-10-21); marketing pages say "1,000+ APIs" ([intro](https://nango.dev/docs/getting-started/intro-to-nango.md)). Every app in our list has an OAuth provider: `google-mail`, `google-calendar`, `google-docs`, `google-sheet`, `google-drive`, `google-tasks` (plus the umbrella `google` we use), `microsoft`, `slack`, `hubspot`, `pipedrive`, `quickbooks`, `xero`, `monday`, `asana`, `notion`, `zendesk`, `helpscout-mailbox`, `shopify` (same file).

**A new provider is config, not code.** Providers are entries in [`providers.yaml`](https://github.com/NangoHQ/nango/blob/master/packages/providers/providers.yaml): `auth_mode`, `authorization_url`, `token_url`, `default_scopes`, and a `proxy` block with `base_url`, headers, retry and pagination rules ([API configuration reference](https://nango.dev/docs/integrations/api-configuration.md)). Some entries name a `post_connection_script` or `webhook_routing_script`, which is code inside Nango. To add one you fork the repo, edit `providers.yaml`, validate, and open a PR; requirements are a test account and a public HTTP or SOAP API; "all authorization types (OAuth, API key, basic), including custom ones" are supported ([contribute or request an API](https://nango.dev/docs/integrations/contribute-or-request-api.md)). Requests are delivered "according to the SLAs on our pricing page" (same page; the overview page says "<48h", [overview](https://nango.dev/docs/integrations/overview)). Adding a provider at runtime from our product, without an upstream PR or self-hosting, is not documented. **So the builder can't connect a brand-new app on its own; it can use any of the ~1,059 that exist, and Mycel still needs an OAuth client registered with each vendor (and the vendor's app review, where one applies).**

**Generic MCP auth (no provider entry needed).** Nango's MCP Auth connects users to remote MCP servers: 37 catalog entries use `MCP_OAUTH2` (e.g. `hubspot-mcp`, `notion-mcp`, `slack-mcp`, `asana-mcp`, `linear-mcp`; [catalog](https://nango.dev/docs/api-catalog.txt)), and a **generic `mcp-generic` integration** where "the Connect UI prompts for **MCP Server URL** … Nango automatically discovers the OAuth endpoints" — but it "currently only works with MCP servers that support automatic client registration (DCR, or CIMD)". Some servers (HubSpot MCP) need a pre-registered client instead. Calls go through the Nango proxy as JSON-RPC `tools/call` ([MCP Auth guide](https://nango.dev/docs/guides/auth/mcp-auth.md)). Scopes for generic MCP integrations became configurable in a 2026 changelog entry ([changelog](https://nango.dev/docs/updates/changelog.md)).

**Proxy.** `nango.proxy({ method, endpoint, baseUrlOverride, providerConfigKey, connectionId, retries, data })` or `https://api.nango.dev/proxy/<endpoint>` makes an authenticated request on a connection ([proxy guide](https://nango.dev/docs/guides/platform/proxy-requests.md)). The guide documents no method, path or host allowlist; `baseUrlOverride` exists. Nango logs proxy calls with "URL, method, status code, and headers — **never request or response bodies**"; logs are kept 15 days on Nango Cloud and "are not removed when you delete a connection" ([security](https://nango.dev/docs/guides/platform/security.md)).

**Functions (TypeScript integration code hosted by Nango).** Nango now positions itself as "the integration layer for AI-built, code-owned product integrations … You generate and customize TypeScript functions with your favorite coding agent" ([intro](https://nango.dev/docs/getting-started/intro-to-nango.md)). Three ways to get a function ([functions guide](https://nango.dev/docs/guides/functions/functions-guide.md)):

1. **Catalog actions** maintained by Nango, "available out of the box and update automatically. Their input schema, output shape, and behavior may change … If deterministic application code needs a stable contract, pull the action into your functions project and deploy it."
2. **Local CLI** (`nango dryrun`, `nango deploy`): "the default path for production integrations … reviewable diffs, local tests, CI/CD". This is what Mycel's `nango-integrations/` folder is.
3. **Functions API, for "just-in-time integrations where users describe behavior in text and an agent publishes the matching function"**: `POST /functions/compile` → `POST /functions/dryruns` (against a real connection) → poll `GET /functions/dryruns/{id}` → `POST /functions/deployments`. Scoped API keys: `environment:functions:compile`, `environment:functions:dryrun`, `environment:deploy`. Nango's own caveat: it "intentionally skips a local Git workflow. For production integrations that need code review, tests, ownership, and CI/CD, prefer local development." A deployed function can later be pulled into a repo with `nango pull <integration> <fn> --env <env>`. Launched as "Remote function builder" in the changelog between the April and May 2026 roundups ([changelog](https://nango.dev/docs/updates/changelog.md)).

An action function declares `description`, `version`, Zod `input`/`output`, optional `scopes` (the integration scopes it needs), and `exec` ([action functions](https://nango.dev/docs/guides/functions/action-functions.md), [SDK reference](https://nango.dev/docs/reference/functions/functions-sdk.md)). **There is no risk, read-only or destructive field** in the documented shape. Output is capped at 2 MB.

**Isolation.** "Function executions now run in isolated AWS Lambda environments rather than using a single VM per customer" (changelog, early 2026); actions/webhooks migrated first, syncs follow with a 10-minute limit ([changelog](https://nango.dev/docs/updates/changelog.md)). Egress restrictions inside a function: not documented (unverified).

**Agent-facing surfaces.**

- **Agent sessions** (changelog, ~Sept 2026): our backend `POST /sessions` with a tenant (connection-tag selectors that must resolve to exactly one connection per integration), a `toolset` (`allow`/`deny` lists per integration), `pinned_tools`, meta tools and `expires_in` (60 s to 15 d). Nango returns a per-session MCP URL and token; "the agent never sees raw credentials, and cannot change the scope of its own session". Meta tools: `nango_tool_search`, `nango_execute` (on by default), `nango_proxy` and `nango_create_connection` (off by default). Warning in the docs: "`allow` and `deny` limit which tools the agent can call, not which API endpoints it can reach. With `nango_proxy` on, the agent can call any endpoint of a connected integration." Third-party MCP server tools join the session "with the server's annotations" ([agent sessions](https://nango.dev/docs/guides/agent-sessions.md)). No approval / human-in-the-loop setting is documented; the docs' own OpenAI example sets `require_approval: "never"`.
- **Connection MCP** (older per-connection MCP server) is deprecated on **2026-12-14** in favour of agent sessions ([changelog](https://nango.dev/docs/updates/changelog.md)).
- **Management MCP** at `https://mcp.nango.dev/mcp` (beta mid-2026, OAuth later, listed in Claude's connector directory): lets a coding agent configure integrations, trigger actions/syncs and deploy functions ([management MCP](https://nango.dev/docs/reference/backend/management-mcp.md), [changelog](https://nango.dev/docs/updates/changelog.md)). Plus a docs MCP (`https://nango.dev/docs/mcp`) and builder skills (`npx skills add NangoHQ/skills …`) ([functions guide](https://nango.dev/docs/guides/functions/functions-guide.md)).

**Data held by Nango that matters for invariant 8.** Synced records (records cache) are kept encrypted: payload 30 days, record 60 days. Logs 15 days, no bodies. Deleting a connection hard-deletes credentials, metadata and synced records 31 days later; logs age out on their own ([security](https://nango.dev/docs/guides/platform/security.md)). Function logs are whatever the function writes; Nango advises against logging "raw payloads that may contain sensitive customer data" ([logging](https://nango.dev/docs/guides/functions/logging.md)).

**Takeaways.**

- **Third-party access.** Many of these servers are not open to an app like Mycel today. Slack takes only Marketplace or internal apps. QuickBooks is a partner pilot. Google Workspace is a Developer Preview whose terms bar public apps before GA. Pipedrive allowlists redirect URIs, and Xero gates by plan.
- **Annotations are rarely published.** Only Google documents per-tool annotations, and only Notion is confirmed to set `destructiveHint`. For the rest it is undocumented, not confirmed absent.
- **Server-side write controls exist and are stronger than hints.** Examples: Google Cloud's IAM deny on `tool.isReadOnly`, Work IQ blocking writes by default, Help Scout's and Linear's read-only modes, Gmail MCP having no send tool, and Stripe's own human confirmation for money movements.
- **Pending forms.** No vendor server offers a general approve / decline / check flow. Where a pending form exists, it is the app's own: Gmail MCP's `create_draft` produces the same Gmail draft Mycel already uses. Stripe's approval URL is the only vendor-side confirmation step found.

## 4. How others let AI build actions on the fly, and keep them safe

**Pattern across all eight.** None of them lets an AI create a lasting action whose risk level the AI sets, and none runs such an action with no person in the way. They fill gaps in four ways:

1. A generic authenticated HTTP request, with the credential injected on their side and the call pinned to the app's own domain.
2. AI-written code that runs in a sandbox, for one-off calls.
3. Code that a person writes or reviews before it is saved for reuse.
4. Tools the operator generates from an OpenAPI spec.

**Takeaways.**

- Every generic-request path pins the host and injects the credential on the platform's side.
- Anthropic goes further: reads and writes must be separate tools.
- Self-declared hints are treated as hints. Composio calls its tags "best-effort", and the MCP spec calls annotations untrusted.
- Where generated code is saved for reuse, a person tests or reviews it first (Zapier Custom Actions, Pipedream registry, Anthropic directory).
- Fully on-the-fly code (Zapier `write_code_action`, the Composio sandbox) runs as one-off sandboxed calls, never as a saved catalog entry with a risk level.

**Summary of section 5.** No machine signal maps an arbitrary operation onto Mycel's five levels. The two signals a fixed rule can trust are (a) the **scopes granted to the connection** (enforced by the vendor: a read-only connection cannot write) and (b) **our own code's constraints on what a function may call** (method + host + path allowlist, argument checks). Method, GraphQL operation type, OpenAPI and MCP annotations are author promises: usable to _raise_ a level (e.g. "any non-GET is at least `internal_reversible`", "any `destructiveHint` not explicitly false is `destructive`"), unsafe to _lower_ one. "Reaches people outside" and "moves money" have no standard marker anywhere.

## Implications for Mycel

These are facts and options, not a decision.

### Facts that constrain any design

- **"Any app" really means "any app our team has already enabled".** The builder can use any of Nango's ~1,059 providers, but only after Mycel has registered an OAuth client with that vendor and passed any app review. Gates include Google verification, Slack Marketplace, Intuit's partner pilot and Xero's plan tiers. Adding a provider Nango lacks takes a `providers.yaml` PR. The exception is MCP servers that support DCR or CIMD (Notion, monday, Linear): Nango's `mcp-generic` can connect those from just a URL.
- **Nango already ships the machinery for builder-made code.** The Functions API runs compile → dry run on a real connection → deploy. Functions run in isolated Lambdas. Agent sessions give scoped MCP access with allow/deny lists. What Nango doesn't supply: a risk field, a human approval step, or a host/method/path allowlist inside a function. Mycel would have to add all three.
- **The only signals a fixed rule can trust are these three:**
  - **The scopes granted to the connection.** The vendor enforces them, so a read-only connection cannot write.
  - **The exact HTTP or GraphQL calls a builder-made action is allowed to make,** if that list is checked at run time by our code rather than by the generated code.
  - **A vendor's server-side controls.** Examples: Google Cloud's IAM deny on `tool.isReadOnly`, Linear's `/mcp/readonly` endpoint, Help Scout's read-only connections.

  Method, OpenAPI fields and MCP annotations are promises by the author. They can safely raise a risk level, never lower it.

- **No signal identifies "reaches people outside the company" or "moves money"** for an arbitrary operation. Calendar's `sendUpdates` shows the same call can be either internal or external depending on its arguments.

### Keeping invariant 4 (only a fixed rule decides risk)

| Option                                                  | What it is                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Keeps invariant 4?                                                                                | What it gives up                                                                                                                                                                                                                                                                                      |

| **A. Builder drafts, a person catalogs**                | The builder writes a Nango function (Functions API), dry-runs it, and files it with a _proposed_ risk as an upgraded `capability_request`. Options can be combined. For example: B for reads and simple writes, A for anything that needs logic, C as the default for brand-new apps.

### Keeping ADR-0013 (an `external_send` waits in the app's own pending form)

- **Block until designed.** Builder-made actions can reach `internal_reversible` at most, and `external_send` stays team-built, one pending form per app. This matches ADR-0013's existing rule that "an app with no natural pending form, such as Slack, waits until we design one".
- **Builder-proposed pending form, reviewed.** Where an app has a native draft state (invoices in DRAFT status, an unsent message), the builder proposes four calls (prepare, approve, decline, check). Each call is classified separately by the fixed rule, and a person approves the adapter once (option A). Only `prepare` runs unattended.
- **Mycel-held pending item.** Mycel holds the prepared request and performs it on approval. ADR-0013 considered and rejected this because it stores content (invariant 8). Variants:
  - Store only the validated _inputs_, not the rendered body, and rebuild the request at approval time. This only works if the template is deterministic (option B), so the approver sees exactly what will be sent.
  - Hold an encrypted body with a short time limit. That still stores content.
- **Approve the action once, not each call.** A person approves the action's shape, and later calls run without review. This conflicts with non-goal 1 ("nothing leaves the company without a human sending or approving it").

### Keeping invariant 8 (pointers, not content)

- **Outputs.** Builder-made action outputs pass between run steps and are stored by Inngest (ADR-0012), and Nango caps action output at 2 MB. A fixed check on the output schema could allow only IDs, enums, numbers, booleans and dates, plus string fields our team has marked as derived. Free-text fields would need the same "read and use within one step" handling as the `draft` step.
- **Nango syncs.** Nango's records cache stores sync payloads (payload 30 days, record 60 days). Builder-made integrations would need to avoid sync functions, or treat the cache as stored content.
- **Nango logs.** Proxy logs carry no bodies (15 days). But logs in generated function code are whatever the code writes, so generated code would need a lint or rule: no `nango.log` of response data.
- **Dry runs.** Dry-run results come back to the builder. They are fine in memory, but they become stored content if the builder chat transcript or `capability_request` record keeps them. Store only the pass/fail result and the output _shape_.
- **Deletion (invariant 3).** Nango hard-deletes a connection's records 31 days after the connection is deleted, but its logs age out separately. Deployed functions are per integration, not per connection, so deleting a connection doesn't remove builder-made code. Decide whether that code is org-owned.

### Other invariants touched

- **Invariant 7 (credits).** Builder code generation and each dry run cost credits. Dry runs also make real API calls on the user's connection, which for a write means a real write. Dry runs of writes would need a sandbox account or a read-only rule.
- **Invariant 6 (model roles).** Code generation needs a role (probably `smart`).

# Conventions

The always-on rules live in `AGENTS.md` ("Invariants", "Writing code"). This file holds the detail behind them. Consistency matters more than any single rule: when this file doesn't cover a case, match the code next to it.

## Inside a feature directory

Every `app/src/features/<name>/` has the same shape. Root files are the public entry points (each optional), and subfolders are private. dependency-cruiser makes it a lint error to import a subfolder from outside its feature.

| File                             | Exports                                                                   | Imported by                                |
| -------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------ |
| `server.ts`                      | server-side functions, each taking `ctx` first                            | Server Components, other features, jobs    |
| `actions.ts`                     | Server Actions (`"use server"`)                                           | client components                          |
| `ui.tsx`                         | the feature's React components                                            | pages in `src/app/`                        |
| `jobs.ts`                        | the feature's Inngest functions                                           | the single Inngest route                   |
| `types.ts`                       | public types and Zod schemas                                              | anyone                                     |
| `connections/delegation.ts`      | `delegatedCtx`: a ctx delegated one connection (ADR-0016)                 | `reviews` only (a dependency-cruiser rule) |
| `runtime/adapters.ts`            | the pending-form adapters (ADR-0013), clear of `reviews` to avoid a cycle | `reviews`                                  |
| `connections/registered-apps.ts` | the registered apps' configuration (ADR-0018): pure, no IO                | anyone, client code included               |
| `custom-actions/description.ts`  | checking a custom action and the action it makes (ADR-0018): pure, no IO  | anyone, client code included               |
| `custom-actions/api-index.ts`    | building a registered app's operation index (ADR-0018): pure, no IO       | `pnpm api-index` and tests                 |

- A pure feature (no tables, no IO, no `ctx`, like `spec` and `policy`) has no `server.ts`. Its functions live in root files named for what they hold (`spec/validate.ts`, `policy/catalog.ts`, `policy/engine.ts`), which anyone may import, client code included.
- `server.ts` functions that exist before any `ctx` does (sign-in, resolving the session to `ctx`, the auth route) are the only ones that don't take it first; they live in `orgs`.
- `lib/`: implementation, including `lib/schema.ts` for the feature's tables.
- `tests/`: tests that import only the feature's entry files.
- `tests/isolation-cases.ts`: a case for every function `server.ts` exports, proving it stays inside the caller's org (see "Tests" below).
- **Tables are private to their feature (ADR-0005).** A feature that needs another feature's data calls that feature's `server.ts`, which also exposes any join a screen needs.
- Import from the file that owns the thing. A directory has no `index.ts` re-exporting it.

`src/app/` holds routes only (pages, layouts, route handlers), kept thin: they call features. `src/db/` holds the Drizzle client, migrations, `forOrg(ctx)`, Better Auth's generated schema (`auth-schema.ts`), and the shared test fixtures in `testing/`, and no feature tables. `src/components/ui/` holds shadcn/ui components, `src/lib/` holds shared helpers that belong to no feature, and `src/testing/` holds test fakes of external services (the fake Nango). `app/scripts/` holds developer scripts that Node runs directly with its built-in TypeScript support (`pnpm nango:preflight`), so they import with relative `.ts` paths and never through `@/` (their tests may); lint, typecheck, boundaries and Vitest cover them like `src/`. To start a feature, copy the shape of an existing one, but not the data access of `orgs`, which is the one feature that skips `forOrg` (see below).

## Data access and config

- **Tenant data (ADR-0003):** feature code queries through `forOrg(ctx)`, which always filters by `org_id` and sets it on inserts from `ctx`, never from caller input. A tenant table names its column `orgId` (`org_id` in SQL). Importing the raw Drizzle client outside `src/db/` is a lint error. There is no Postgres RLS. Better Auth's tables are the one exception: they key the org as `organization_id`, aren't reached through `forOrg`, and only the `orgs` feature touches them. Lint lets `src/features/orgs/lib/` import the raw client and `@/db/auth-schema`, and nothing else outside `src/db/`. The one other exception: a feature's `lib/schema.ts` may import `@/db/auth-schema` so its foreign keys can reference a member as `(org_id, user_id)`, which keeps the row in the member's org and deletes it when the member is removed.
- **Transactions:** writes that must land together go through `forOrg(ctx).transaction(async (tx) => …)`. `tx` is the same org-scoped handle, bound to one database transaction: every write commits together, or none does when the function throws (the error is rethrown). Publishing a version with its tags is the first user. Keep the transaction to the writes; do reads, validation and calls to other features before it.
- **Derived data cascades from its connection (invariant 3):** every table holding data ingested or derived from a connection (events, object refs, embeddings, facts, clusters, …) carries `org_id` and `connection_id`, with a composite foreign key `(org_id, connection_id)` to `connections (org_id, id)` (the `connections_org_id_id_unique` key) `ON DELETE CASCADE`. Deleting the connection row then deletes everything derived from it, whichever path deleted it (disconnect, Nango's deletion webhook, reconciliation, removing a user), and a job still writing for a deleted connection fails on the foreign key instead of leaving orphans. Tables are private to their feature, so this is the one exception: a feature's `lib/schema.ts` may import `connections`' `lib/schema.ts` (or another feature's schema) for its foreign keys, and nothing else may (dependency-cruiser's `schemas-only-from-schemas` rule). `discovery`'s events and object refs are the first. A job treats that foreign-key violation, like `NotFoundError` from `connections`, as "the connection is gone" and stops quietly. Never delete derived rows by hand on disconnect: the cascade is the one mechanism. Data derived from several connections at once (memory's facts and objects) has no `connection_id` of its own; it hangs off rows that do (`fact_sources`), and database triggers carry the cascade on when the last such row goes.
- **Request context:** `ctx` is passed explicitly. There is no AsyncLocalStorage or other hidden request state.
- **Server boundary:** reads and writes go through Server Components and Server Actions. Add tRPC, a REST layer, or a client-side data cache only when a real need appears, and record it as an ADR.
- **Local database:** `pnpm db:up` starts Postgres with pgvector in Docker on port 5433 (`pnpm db:down` stops it). Copy `app/.env.example` to `app/.env`. Install the browser the e2e tests drive once with `pnpm --filter app exec playwright install chromium`. Tests never use the database in `.env`: each checkout (worktree) gets its own `mycel_test_<suffix>` for Vitest, `mycel_e2e_<suffix>` for Playwright, and an e2e port in 3100–3999, where `<suffix>` is the first 8 hex digits of the sha256 of the checkout's `app/` path (`app/checkout-isolation.ts`). Two worktrees can then run `pnpm verify` at once. `TEST_DATABASE_URL`, `E2E_DATABASE_URL` and `E2E_PORT` override them, for example when two checkouts' ports happen to collide. A removed worktree leaves its databases behind; list them with `docker compose exec postgres psql -U mycel -d mycel -c '\l mycel_*'` and drop one with `docker compose exec postgres dropdb -U mycel mycel_test_<suffix>`.
- **Migrations:** `pnpm db:generate` (`drizzle-kit generate`) writes SQL files to `src/db/migrations/`, which are committed and applied with `pnpm db:migrate` (`drizzle-kit migrate`). Every schema change goes through a reviewed migration file; `drizzle-kit push` is not used. SQL Drizzle can't express (extensions) goes in a `drizzle-kit generate --custom` migration.
- **Times:** a new time column is `timestamp(name, { withTimezone: true })`. A time without a zone reads back shifted when the database's time zone isn't UTC (the local Postgres's may not be), because `now()` and Postgres's comparisons follow the session's zone. M3's tables use it; the tables from before M3 (Better Auth's, tags, connections, connect attempts, events) still have times without a zone, so their `now()` defaults read back shifted on such a database.
- **Config:** environment variables are parsed once by a Zod schema in `src/env.ts`, and everything else imports from there. Reading `process.env` elsewhere is a lint error.
- **Errors:** a small set of typed error classes (`NotFoundError`, `ForbiddenError`, `OutOfCreditsError`, …) is thrown and caught at the Server Action or route boundary. Plain `throw`, no Result/Either types, no Effect.

## UI

Tailwind plus shadcn/ui, with component source copied into the repo. shadcn/ui is built on Radix primitives, so new Radix pieces arrive as shadcn components, keeping one component library.

## Tooling

- **TypeScript:** strict. Typed values at every feature boundary; Zod at every IO boundary.
- **ESLint:** typescript-eslint `strict-type-checked`, plus the Next.js config. It catches bugs and never formats. `max-lines` caps files at 300 lines, and `import/no-default-export` enforces named exports outside the Next.js special files.
- **Version pins:** ESLint stays on 9 and TypeScript on 6.0 until `eslint-config-next`'s plugins support ESLint 10 and typescript-eslint supports TypeScript 7.
- **Prettier:** the only formatter.
- **Tests:** Vitest. Database tests run against real Postgres with pgvector (Docker locally, a service container in CI), in a separate `mycel_test_<suffix>` database per checkout (see "Local database") that the test run creates and migrates. Each test file starts from an empty database, so files run one at a time.
- **End-to-end tests:** Playwright, Chromium only, in `app/e2e/`. They drive the production build through `next start` on the checkout's e2e port (so `pnpm verify` runs them after `pnpm build`; run `pnpm build` before a standalone `pnpm e2e`) against a separate `mycel_e2e_<suffix>` database that Playwright's global setup creates and migrates. Each test that takes the `orgs` fixture starts from an empty database seeded with `seedTwoOrgs()`, and tests run one at a time. Sign-in is Google-only, so `signInAs(user)` stores a Better Auth session and sets its signed session cookie on the browser (`e2e/sign-in-as.ts`); production code has no test login route. A test that needs a Google connection seeds its row with `seedGoogleConnection` (`src/db/testing/seed-connection.ts`), since there's no Connect UI to connect through. The app reaches Nango through `NANGO_API_URL`, which points at a fake Nango that Playwright starts on the app's port plus 2000 (`e2e/fake-nango-server.ts`): it answers with the Vitest fake's own handlers, so the proxy and the fake Gmail behave as in Vitest. A test that needs a mailbox takes the `nango` fixture (`e2e/fake-nango.ts`), seeds a connection there with its messages and drafts, passes that connection's ID to `seedGoogleConnection`, and reads the mailbox back afterwards; a request the fake can't answer fails the test. Model calls reach a fake AI Gateway that Playwright starts as a second web server on the app's port plus 1000 (`e2e/fake-ai-gateway-server.ts`, which the app reaches through `AI_GATEWAY_BASE_URL`); a test takes the `aiGateway` fixture and scripts each streamed model step with `aiGateway.reply(...)`, in the same shape as the Vitest fake, and fails if the app made a model call it didn't script. Keep them few and about user-visible behavior through the UI; logic belongs in Vitest.
- **External services in tests:** tests never reach the network. `src/testing/fake-nango.ts` is an in-memory Nango Cloud (connect sessions, connections and their paged listing, integrations, the proxy to each source's API with its own refusals, and signed webhooks) behind msw's fetch interception, installed for every Vitest file, so tests run the real Nango client. A request it doesn't handle fails the test: extend the fake with the endpoint, in the shape Nango documents, rather than mocking the client. Each connection in the fake has a Gmail mailbox (`src/testing/fake-gmail.ts`), a Google Drive (`src/testing/fake-drive.ts`) and spreadsheets (`src/testing/fake-sheets.ts`) that tests seed, and the scopes Google granted it (every app Mycel asks for unless a test unticks some), which Nango's connection read reports as `credentials.raw.scope`. The proxy (`src/testing/fake-nango-proxy.ts`) routes each request by its `Base-Url-Override` host (or the integration's own) and path prefix to that API's fake, which answers 403, as Google does, unless the connection holds a scope it accepts (`src/testing/fake-proxied-sources.ts`; a host it doesn't know fails the test). Every feature's tests connect through the real flow with `src/testing/connect-helpers.ts` (`connectGoogle`, and `connectOldConnection` for the one-app connections from before ADR-0014). The proxy takes POSTs, PUTs, PATCHes and DELETEs too, which an API's fake answers only when the connection holds one of its write scopes. A Microsoft 365 connection reaches the fake Microsoft Graph (`src/testing/fake-microsoft.ts`), which records every request it receives, for a test to check exactly what was sent and how often, and answers `/me`, seeded Outlook messages and replies to them. The mailbox has a history log for `history.list` that a test can expire, and serves messages and threads (`format=full`, `metadata` or `minimal`). It holds labels and drafts (`src/testing/fake-gmail-writes.ts`): `labels.list` and `create`, `messages.modify`, and `drafts.create`, `list`, `get`, `update`, `send` (which removes the draft and adds a sent message with a new ID to its thread) and `delete`, keeping each draft as a DRAFT message in its thread, parsed from the RFC 2822 it was sent so a test can read its headers and text. A test can send or delete a draft itself (`sendDraft`, `deleteDraft`), as the person would in Gmail, and reads what was sent from `writes.sent`. It logs every write, and can be told to make the next write but lose its answer (503), as a retry after a lost response sees. The Drive has files and a changes feed with page tokens that a test can expire (Drive then answers 400), and it answers only the `fields` a request names, failing the test if one asks for a file's name; the spreadsheets answer `values.get` (leaving out trailing empty rows and cells, and `values` for an empty range) and `values.append` (after the last row of the range's table, logging each append with its `valueInputOption`), 404 for a spreadsheet they don't have, 400 for a range they can't parse, and 403 for one a test denies, and can lose an append's answer the same way. The fake can answer 429s (retried as Nango's `Retries` header asks) and run a hook before each proxied request, to delete a connection under a running job. It can revoke a connection's access (the proxy then refuses as Nango does for a failed token refresh), delete a connection with no webhook (as Nango's bulk deletes do), or list nothing (an outage), for the nightly reconciliation. `src/testing/fake-inngest.ts` is Inngest Cloud's event API, the same way: it records the events the real Inngest client sends, and runs nothing. `src/testing/fake-ai-gateway.ts` is the Vercel AI Gateway, the same way, so model calls run the real AI SDK: each test scripts the answers it expects in order (a Jev decision with its probabilities or a refusal, a structured output, which may be off the request's schema, a text, a streamed reply for `streamText` with text and tool calls, the vectors for an embedding request, or a failure with a status and generation ID), each with the cost the gateway reports, and can list the requests it received, each marked streamed or not. A streamed script answers only a streamed request, as the gateway's server-sent events, one model step per `reply`: a reply with tool calls makes the AI SDK run them and ask again, so a test scripts that next step too. A model call with nothing scripted for it fails the test. `src/testing/fake-model-armor.ts` is Google Cloud Model Armor, the injection screen, with the two Google token endpoints in front of it: it passes every text unless a test flags a phrase (`flagText`), can fail or skip its filter once, and lists the texts it screened. `src/testing/fake-kms.ts` is AWS KMS, the same way, so the key store runs the real AWS SDK: it answers the operations the key store makes (making a key, encryption or HMAC, and its alias, data keys, decrypting, MACs, describing a key, scheduling its deletion and deleting its alias, each key only for its usage) with AWS's error types, binds each data key to its key and encryption context as KMS does, and lists its keys, which key each data key came from, and every plaintext data key and HMAC secret, for a test to scan tables and logs for. Tests never run Inngest; they call the `server.ts` function a job calls. A job passes its `step.run` to that function, which runs each step straight through when called without one. The interpreter's tests pass a recording step runner instead (`runtime/tests/run-helpers.ts`), which memoizes results by step ID so a second call replays finished steps, as Inngest does after a crash, and a retry policy that records its waits rather than sleeping. Its step-state recorder keeps what Inngest would store: each step's output as the client's encryption middleware sends it, and `src/testing/inngest-step-state.ts` decrypts that back with a key.
- **Isolation tests:** `seedTwoOrgs()` from `src/db/testing/two-org-fixture.ts` seeds org A and org B, each with an admin and a member and a `ctx` for each. Each feature's `tests/isolation-cases.ts` passes `defineIsolationCases(server, { … })` a case for every `server.ts` export. `src/db/tests/isolation.test.ts` runs every case and fails, as does typecheck, when an export has none. It checks `server.ts` only, so `actions.ts` and `jobs.ts` stay thin and call `server.ts`. Mark a function that touches no org data `notTenantScoped("why")`.
- **Pre-commit (Husky + lint-staged):** Prettier and ESLint `--fix` on staged files, then typecheck. Tests stay out of the hook.
- **Pre-push:** `pnpm verify`.
- **CI:** the GitHub Actions workflow runs `pnpm verify` and nothing else (after installing dependencies and Playwright's Chromium), so a laptop and CI always check the same things.

## Naming

- Files: `kebab-case.ts`.
- Exports: named. Default exports only where Next.js requires them (`page.tsx`, `layout.tsx`, …).
- DB tables: `snake_case` plural (`workflow_versions`). TypeScript types: `PascalCase` singular (`WorkflowVersion`).
- Domain names: `GLOSSARY.md` terms, using the term itself rather than its listed _Avoid_ words (`Enablement`, not `Subscription`).
